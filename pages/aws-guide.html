Part 0 — Mental model & global infrastructure CORE

AWS is the largest and most mature cloud provider, with the broadest service catalog. Its strengths are breadth, depth, market share, and a vast ecosystem. The trade-off: sheer size means a steeper learning curve and many overlapping services.

The geographic hierarchy

AWS GLOBAL +-- REGION (e.g. "us-east-1" N. Virginia) — isolated | geographic area, has its own services & pricing | +-- AVAILABILITY ZONE us-east-1a (1+ discrete DCs) | +-- AVAILABILITY ZONE us-east-1b | +-- AVAILABILITY ZONE us-east-1c | +-- EDGE LOCATIONS (100s, for CloudFront CDN / Route 53) Deploy across AZs (multi-AZ) to survive a DC failure. Deploy across REGIONS for disaster recovery / latency. Edge locations cache content close to users globally.
ConceptWhat it isProtects against
Availability Zone (AZ)One or more discrete DCs with independent power/networkDatacenter failure
RegionA cluster of AZs in one geography(multi-region) regional outage
Edge locationCDN/DNS PoP near users(latency — not a failure domain)
Multi-AZ is the baseline for production Spreading resources across at least two AZs is the single most important availability practice on AWS. Managed services (RDS, ELB, etc.) make this easy. Most regional services let you go multi-AZ with a checkbox or by placing resources in multiple AZ subnets. us-east-1 is the oldest/largest region and where new services launch first.

How you interact with AWS

  • AWS Management Console — the web GUI.
  • AWS CLI (aws) — command line for scripting.
  • CloudShell — browser terminal with the CLI pre-configured.
  • CloudFormation / CDK / Terraform — infrastructure as code.
  • SDKs — boto3 (Python), AWS SDK for JS/Java/Go, etc.

Part 1 — Accounts, Organizations & governance CONCEPT

The AWS account is the fundamental boundary for billing, security, and resource isolation. Mature setups use many accounts, managed centrally with AWS Organizations.

AWS ORGANIZATION (management/payer account at the root) | ORGANIZATIONAL UNITS (OUs) — group accounts by | team / env / function ACCOUNTS (prod, dev, staging, security, logging...) | RESOURCES (EC2, S3, RDS, etc., live inside an account and a region) Service Control Policies (SCPs) set guardrails at the OU/account level — they LIMIT what even admins can do.
ToolPurpose
AWS OrganizationsManage many accounts, consolidated billing
Service Control Policies (SCPs)Org-wide permission guardrails (max allowed)
AWS Control TowerSet up & govern a secure multi-account landing zone
AWS ConfigTrack resource configuration & compliance
Tags + Cost AllocationOrganize resources & attribute cost
Multi-account is the AWS best practice Rather than one big account, use separate accounts per environment/team (e.g., prod, dev, security, logging) under Organizations. This gives hard isolation of blast radius, billing, and access. Control Tower automates setting this up with sensible guardrails. SCPs enforce rules no one in the account can override.

Part 2 — Identity & access (IAM) CORE

IAM controls authentication and authorization for everything in AWS. It's the most important service to understand deeply — most security incidents trace back to IAM misconfiguration.

The IAM building blocks

EntityWhat it is
UserA person or app with long-term credentials (avoid for apps)
GroupA collection of users sharing policies
RoleAn identity assumed temporarily; no long-term keys
PolicyJSON document granting/denying permissions

How a policy is evaluated

request: "principal X wants to do ACTION on RESOURCE" | 1. explicit DENY anywhere? --yes--> DENIED | no 2. is there an explicit ALLOW? --no--> DENIED (implicit) | yes 3. ALLOWED (unless an SCP / boundary restricts it) Default is DENY. You must be explicitly allowed. An explicit DENY always wins over any allow.
// IAM policy: allow read-only on one S3 bucket
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::my-bucket",
      "arn:aws:s3:::my-bucket/*"
    ]
  }]
}

Roles: the right way to grant access to workloads

Instead of putting access keys in code, give an EC2 instance, Lambda, or container an IAM role. The service automatically receives temporary, auto-rotated credentials.

WITHOUT (bad): app stores AWS access keys in config -> long-lived secret, big leak risk WITH a role (good): Lambda / EC2 / ECS task runs WITH an IAM role -> AWS hands it temporary credentials automatically -> no keys in code, auto-rotated Cross-account: a role in account B can be ASSUMED by a principal in account A (sts:AssumeRole) -> secure delegation without sharing credentials. For workloads outside AWS / in Kubernetes: use IAM Roles for Service Accounts (IRSA) or OIDC federation.
IAM golden rules
  • Never use the root account for daily work; lock it down with MFA and put it away.
  • Use roles, not access keys, for applications and services.
  • Apply least privilege — start minimal, add permissions as needed.
  • Require MFA for all human users.
  • Use IAM Identity Center (SSO) for human access at scale instead of IAM users.

EC2 (Elastic Compute Cloud)

Resizable virtual servers. You pick an AMI (machine image), an instance type, storage, and networking. Instance families target different workloads:

FamilyOptimized forExamples
T (burstable)General, bursty, low-costt3, t4g
M (general)Balanced CPU/RAMm6i, m7g
C (compute)High CPUc7g, c6i
R / X (memory)Large RAM (DBs, caches)r7g, x2

Graviton (the g suffix) are AWS's own ARM CPUs — better price/performance for many workloads.

Scaling & availability

  • Auto Scaling Groups (ASG) — maintain/scale a fleet of EC2 across AZs, replace unhealthy instances.
  • Elastic Load Balancing (ELB) — distribute traffic: ALB (L7/HTTP), NLB (L4/TCP), GWLB (appliances).
  • EBS — durable network block storage for instances; instance store is ephemeral local disk.

ECS vs EKS, and the Fargate dimension

Part 5 — Serverless (Lambda & friends) CORE

AWS pioneered modern serverless with Lambda. You run code without provisioning servers, paying only for compute time consumed.

AWS Lambda (FaaS)

EVENT SOURCE LAMBDA ------------ ------ API Gateway (HTTP) ----> [ your function ] S3 object created ----> (Python, Node, Java, DynamoDB stream ----> Go, Ruby, .NET, custom) SQS / SNS message ----> EventBridge event ----> scales automatically per event Step Functions step ----> pay per request + duration + memory Limits: up to 15 min runtime, configurable memory/CPU, ephemeral storage. Stateless by design.

The serverless application stack

ServiceRole
LambdaRun function code on events
API GatewayManaged REST/HTTP/WebSocket APIs in front of Lambda
Step FunctionsOrchestrate multi-step workflows (state machine)
EventBridgeEvent bus / routing & scheduling
AppSyncManaged GraphQL APIs
DynamoDBThe natural serverless database partner

Step Functions: orchestrating serverless

A visual state machine chains Lambdas & services: [validate] -> [charge] -> choice? --ok--> [ship] |--fail--> [refund] -> [notify] Handles retries, error catching, parallel branches, waits, and human-approval steps -- so your functions stay small and the workflow logic is declarative.
Lambda design constraints Functions are stateless, time-limited (15 min max), and can cold-start after idle (use provisioned concurrency for latency-sensitive APIs). Keep deployment packages small, reuse connections across invocations (initialize outside the handler), and make handlers idempotent — events like SQS/S3 can deliver more than once.

S3 — the foundational object store

S3 is one of AWS's oldest and most central services. It's effectively infinite, extremely durable (11 nines), and the backbone of data lakes, backups, static hosting, and ML data.

S3 storage classes (cost vs access pattern)

STANDARD frequent access, hot data INTELLIGENT-TIERING auto-moves objects between tiers based on access (set & forget) STANDARD-IA infrequent access (lower storage cost) ONE ZONE-IA infrequent, single AZ (cheaper, less HA) GLACIER INSTANT archive, millisecond retrieval GLACIER FLEXIBLE archive, minutes-to-hours retrieval GLACIER DEEP ARCHIVE cheapest, ~12 hr retrieval Lifecycle rules auto-transition/expire objects by age. Intelligent-Tiering is great when access is unpredictable.

Key S3 features

  • Versioning — keep multiple versions; protect against overwrites/deletes.
  • Strong read-after-write consistency — reads immediately reflect writes.
  • Presigned URLs — time-limited direct upload/download (don't proxy big files through your app).
  • Encryption — server-side by default (SSE-S3 or SSE-KMS).
  • Static website hosting + CloudFront for a cheap global static site.
  • Event notifications — trigger Lambda/SQS/SNS on object events.
Block public access by default Public S3 buckets are a classic data-breach source. "Block Public Access" is on by default — keep it on unless you intentionally host public content. Use bucket policies + IAM for access, presigned URLs for temporary sharing, and CloudFront (with OAC) to serve content without making the bucket public.

Part 8 — Networking (VPC) CORE

VPC — your isolated network

A Virtual Private Cloud is your private, logically isolated network in a region. You carve it into subnets across AZs, and control traffic with security groups and route tables. VPCs are regional (subnets are AZ-specific).

VPC 10.0.0.0/16 (in one region) +-- PUBLIC subnet us-east-1a 10.0.1.0/24 | -> route to Internet Gateway (has public IPs) | [ Load Balancer / bastion ] +-- PRIVATE subnet us-east-1a 10.0.2.0/24 | -> outbound via NAT Gateway; no inbound internet | [ app servers ] +-- PRIVATE subnet us-east-1b 10.0.3.0/24 [ databases ] (multi-AZ for HA) Security Group = stateful firewall on a resource (ENI) Network ACL = stateless firewall on a subnet

Core networking services

ServiceRole
Security GroupStateful instance-level firewall (allow rules)
Network ACLStateless subnet-level firewall (allow + deny)
Internet GatewayPublic internet access for a VPC
NAT GatewayOutbound internet for private subnets
Elastic Load BalancingALB (L7), NLB (L4), GWLB (appliances)
Route 53DNS + health checks + routing policies
CloudFrontCDN (edge caching) + WAF integration
VPC Endpoints / PrivateLinkReach AWS services privately (no internet)
Direct Connect / VPNConnect on-prem (dedicated line / encrypted tunnel)
Transit GatewayHub to connect many VPCs & on-prem networks

Security Group vs Network ACL

SECURITY GROUP (on the resource): stateful -> if you allow inbound, the response is automatically allowed out. Allow rules only. The everyday firewall you'll configure most. NETWORK ACL (on the subnet): stateless -> you must allow BOTH directions explicitly. Supports DENY rules. Coarse, subnet-wide guardrail.
Keep databases in private subnets Data and app tiers belong in private subnets with no inbound internet route. Put load balancers (and only those) in public subnets. Use NAT Gateways for outbound, VPC Endpoints/PrivateLink to reach AWS services (S3, DynamoDB) without traversing the internet, and tighten security groups to the minimum ports/sources.

SQS vs SNS vs EventBridge vs Kinesis

SQS (queue): producer -> [ queue ] -> one consumer buffer work; each message processed once. Standard (at-least-once) or FIFO (ordered, exactly-once). SNS (pub/sub): publisher -> TOPIC -+-> SQS queue +-> Lambda +-> email / HTTP fan a message out to many subscribers at once. EVENTBRIDGE (event bus): rich routing/filtering by event content; integrates SaaS + AWS events; scheduling. KINESIS (stream): ordered, replayable stream of records for real-time analytics; many consumers, retention. Common combo: SNS -> SQS "fan-out" (topic delivers to several queues, each feeding its own worker fleet).
The SNS + SQS fan-out pattern A classic AWS design: publish once to an SNS topic that delivers to multiple SQS queues, each consumed by a different service. This decouples producers from consumers and lets each consumer process at its own pace with its own retry/DLQ. Make consumers idempotent (at-least-once delivery).

Bedrock AgentCore — production agents

AgentCore is AWS's framework for building, deploying, and operating production AI agents. It's framework-agnostic (use LangGraph, CrewAI, Strands, or your own) and provides the managed runtime plus supporting services — think "managed infrastructure for agents".

AgentCore building blocks (mix & match): Runtime -> secure, serverless, scalable agent hosting Gateway -> turn APIs/Lambdas into agent tools (MCP) Memory -> short- & long-term agent memory Identity -> secure agent auth & access to resources Browser -> managed headless browser tool Code Interpreter -> sandboxed code execution Observability -> trace & monitor agent behavior Bring any framework/model; AgentCore runs & operates it.

A typical RAG architecture on AWS

docs in S3 -> Bedrock Knowledge Base (chunk + embed via Titan/Cohere -> store in OpenSearch / Aurora pgvector) user question -> Bedrock Knowledge Base "retrieve_and_generate" (embed -> vector search -> Claude generates grounded answer + citations) -> Bedrock Guardrails filter input/output Or wire it yourself: Lambda + Bedrock InvokeModel + a vector store (OpenSearch / Aurora pgvector / Pinecone).
Bedrock's edge: model choice + AWS integration Bedrock's value is one managed, serverless API across many top models (notably Anthropic's Claude), with data staying in your AWS account, IAM-based access, and tight integration with the rest of AWS (S3, Lambda, OpenSearch, Guardrails, AgentCore). For AWS-centric orgs building GenAI/agentic systems, it minimizes undifferentiated plumbing.

Observability: CloudWatch & X-Ray

CloudWatch (the core): +-- Metrics numeric time-series (CPU, latency, custom) +-- Logs centralized logs + Logs Insights (query) +-- Alarms thresholds -> SNS / auto-scaling / actions +-- Dashboards visualize +-- Synthetics canaries probe endpoints X-Ray: distributed tracing -> see a request flow across services, find latency/error hotspots. CloudTrail: records every API call (audit/forensics) — distinct from CloudWatch (operational metrics).
CloudWatch vs CloudTrail Easy to confuse: CloudWatch is for operational monitoring (metrics, logs, alarms — "is it healthy?"). CloudTrail is for auditing (who made which API call, when — "who did what?"). You want both: CloudWatch for performance, CloudTrail for security/compliance forensics.

Security mantras

  • Lock down root; use IAM Identity Center for humans, roles for workloads.
  • Least privilege everywhere; review with IAM Access Analyzer.
  • Secrets in Secrets Manager, keys in KMS — never in code.
  • Encrypt at rest (KMS) and in transit (TLS) — default on most services.
  • Block public S3; use private subnets + VPC endpoints for data.
  • Turn on GuardDuty + CloudTrail + Security Hub org-wide.

Cost management

  • Savings Plans / Reserved Instances for steady compute (up to ~72%).
  • Spot Instances for fault-tolerant/batch (up to ~90%).
  • Right-size with Compute Optimizer; delete idle resources.
  • S3 Intelligent-Tiering & lifecycle rules; clean up old snapshots.
  • Serverless (Lambda/Fargate/Aurora Serverless) to pay only for use.
  • Cost Explorer + Budgets + tags for visibility & alerts.
Shared responsibility model AWS is responsible for security of the cloud (hardware, global infrastructure, managed-service internals). You are responsible for security in the cloud — your IAM, data, encryption, network config, and (for EC2) OS patching. The boundary moves with the service: more on you for EC2, more on AWS for Lambda/managed services.

Final advice AWS wins on breadth and maturity — if a capability exists in the cloud, AWS almost certainly has it (often several ways). Lead with IAM (roles, least privilege), default to Multi-AZ and managed/serverless services, isolate workloads with multi-account + VPC, and codify with CDK/Terraform.
