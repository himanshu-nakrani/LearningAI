Part 0 — Mental model & global infrastructure ★ CORE

Azure is Microsoft's cloud platform: a global network of datacenters offering compute, storage, networking, databases, and higher-level managed services on demand. Its strength is deep enterprise and Microsoft-ecosystem integration (Windows, Active Directory, Office 365, .NET).

The geographic hierarchy

Understanding how Azure is physically organized explains availability, latency, and compliance choices.

GEOGRAPHY (e.g. "United States" — for data residency) +-- REGION (e.g. "East US" — a metro area of datacenters) | +-- AVAILABILITY ZONE 1 (independent DC: power, | | cooling, network) | +-- AVAILABILITY ZONE 2 | +-- AVAILABILITY ZONE 3 | +-- REGION PAIR (each region paired with another in the same geography for DR; e.g. East US <-> West US) Deploy across ZONES to survive a datacenter failure. Deploy across REGIONS to survive a regional disaster.
ConceptWhat it isProtects against
Availability ZonePhysically separate DC within a regionDC-level failure
RegionA set of DCs in one geography(deploy multi-region) regional outage
Region pairTwo regions linked for replication/DRDisaster, sequential updates

How you interact with Azure

  • Azure Portal — the web GUI (good for learning & exploration).
  • Azure CLI (az) — cross-platform command line.
  • Azure PowerShell — cmdlets for Windows-centric automation.
  • ARM / Bicep / Terraform — infrastructure as code.
  • SDKs — for .NET, Python, Java, JS, Go, etc.

The Azure resource model Everything you create is a resource (a VM, a database, an IP). Resources live in a resource group — a logical container for things that share a lifecycle. Resource groups live in a subscription (the billing + access boundary). This three-level grouping is fundamental to organizing and securing everything.

Part 1 — Accounts, subscriptions & governance ◆ CONCEPT

The management hierarchy

Microsoft Entra Tenant (your organization's identity) | Management Groups (group subscriptions, apply policy) | Subscriptions (billing + access boundary) | Resource Groups (lifecycle container) | Resources (VMs, DBs, storage, etc.) Policies and RBAC roles applied higher up are INHERITED downward -> govern many resources at once.
LevelPurpose
Management groupApply governance across many subscriptions
SubscriptionBilling unit + quota + access boundary
Resource groupGroup resources sharing a lifecycle/region
ResourceAn individual service instance

Governance tools

  • Azure Policy — enforce rules (e.g., "only allow these regions", "require tags", "no public IPs").
  • Blueprints / Landing Zones — repeatable, compliant environment setups.
  • Resource locks — prevent accidental deletion/modification.
  • Tags — key-value labels for cost allocation and organization.
  • Cost Management + Budgets — track and alert on spend.
Tag everything from day one Without consistent tags (owner, environment, cost-center, project) you can't attribute cost or clean up safely. Enforce required tags with Azure Policy. Retrofitting tags across hundreds of resources later is painful.

Part 2 — Identity: Microsoft Entra ID & RBAC ★ CORE

Identity is the foundation of cloud security. Microsoft Entra ID (formerly Azure Active Directory) is Azure's cloud identity and access management service — it controls who can sign in and what they can access.

Entra ID is not on-prem Active Directory Despite the old name, Entra ID is a cloud identity service for web/SaaS apps (OAuth, SAML, OIDC), not a drop-in replacement for on-prem AD (which uses LDAP/Kerberos for domain-joined machines). They're often synced together via Entra Connect in hybrid setups.

Authentication vs authorization

AUTHENTICATION (Entra ID): who are you? sign-in, MFA, conditional access, SSO AUTHORIZATION (Azure RBAC): what can you do? role assignments on resources identity --(authn)--> proven identity --(authz/RBAC)--> allowed actions

Azure RBAC: the three pieces

A role assignment = who (security principal) + what (role definition) + where (scope).

WHO WHAT (role) WHERE (scope) ------------ ----------------- ----------------- user Reader management group group Contributor subscription service Owner resource group principal custom role single resource managed identity assignment = principal + role + scope (inherited down)
Built-in roleCan do
OwnerFull access including granting access
ContributorManage resources, but not grant access
ReaderView only
User Access AdministratorManage access only

Managed identities (use these, not passwords)

A managed identity gives an Azure resource (like a VM or Function) its own Entra identity, so it can authenticate to other services without storing credentials in code. Azure rotates the secret automatically.

WITHOUT (bad): app holds a secret/key in config -> leaks, rotation pain WITH managed identity (good): VM/Function --(its identity)--> Key Vault / Storage no secret in code; Azure manages the credential System-assigned: tied to one resource's lifecycle User-assigned: standalone, shareable across resources
Principle of least privilege Grant the narrowest role at the narrowest scope that works. Avoid Owner/Contributor at subscription scope for day-to-day identities. Use Privileged Identity Management (PIM) for just-in-time elevation of admin roles, and require MFA + Conditional Access for all human sign-ins.

Part 3 — Compute ★ CORE

Azure offers a spectrum of compute, from raw VMs (you manage everything) to serverless (you manage nothing but code). The trade-off is control vs operational burden.

more control less ops burden <--------------------------------------------------> VMs VM Scale Sets App Service Functions (IaaS) (auto-scale Containers (serverless) VMs) (AKS/ACA) (FaaS) you patch Azure runs it the OS all for you

Virtual Machines (IaaS)

Full control over a virtual server — choose OS, size, disks. You manage patching, scaling, and availability. VM families are optimized for different workloads:

SeriesOptimized for

D / Dv5General purpose, balanced CPU/RAM
E / Ev5Memory-optimized (databases, caches)
FCompute-optimized (high CPU)
N (NC/ND/NV)GPU (AI training, rendering)
LStorage-optimized (high disk throughput)

Scaling: VM Scale Sets

A VMSS manages a group of identical VMs that scale automatically based on demand, behind a load balancer. This is how you run resilient, elastic workloads on IaaS.

Load Balancer / | \ VM VM VM <- VM Scale Set (auto add/remove based on CPU, schedule, or queue) scale OUT (more VMs) under load, scale IN when idle.

App Service (PaaS)

A managed platform for hosting web apps and APIs — push code (or a container) and Azure handles the OS, patching, load balancing, and autoscale. Ideal when you want to deploy an app without managing servers.

Part 5 — Serverless ★ CORE

Serverless means you deploy code or workflows and pay only for execution — no servers to provision or scale. Azure scales it automatically, including to zero when idle.

Azure Functions (FaaS)

Event-driven functions triggered by HTTP, timers, queues, blobs, and many other events. Bindings connect inputs/outputs declaratively without boilerplate SDK code.

TRIGGER (one) FUNCTION BINDINGS (in/out) ------------ -------- ---------------- HTTP request ----> [ your code ] ---> write to Cosmos DB timer schedule send to Queue new blob/queue msg return HTTP response Event Grid event Scales out automatically per event volume; pay per execution + execution time + memory.

Hosting plans

PlanBehavior
ConsumptionTrue serverless, scale to zero, pay per use (cold starts)
PremiumPre-warmed instances (no cold start), VNet, longer runs
Dedicated (App Service)Runs on your App Service plan, predictable cost

Logic Apps & Durable Functions

  • Logic Apps — low-code visual workflow orchestration across 1000+ connectors (great for integration).
  • Durable Functions — write stateful, long-running orchestrations in code (fan-out/fan-in, human approval, chaining).
Mind cold starts On the Consumption plan, an idle function "cold starts" — the first request after inactivity is slow while the runtime spins up. For latency-sensitive APIs use the Premium plan (pre-warmed) or keep functions warm. Design functions to be stateless and idempotent.

NoSQL: Azure Cosmos DB

A globally distributed, multi-model database with single-digit-millisecond latency and turnkey global replication. It supports multiple APIs so you can use familiar interfaces.

Cosmos DB APIs (pick one per account): - NoSQL (core, document/JSON) - MongoDB (wire-compatible) - Cassandra (wide-column) - Gremlin (graph) - Table (key-value) Global distribution: replicate to any region with a click; choose from 5 consistency levels: Strong -> Bounded Staleness -> Session -> Consistent Prefix -> Eventual (stronger = more latency/cost)

Caching & in-memory

  • Azure Cache for Redis — managed Redis for caching, sessions, leaderboards, pub/sub.
Cosmos DB's 5 consistency levels are a key differentiator Most databases offer "strong" or "eventual." Cosmos lets you tune the exact trade-off per workload. Session consistency (the default) is usually the sweet spot — read-your-own-writes guarantees with low latency. Reach for Strong only when correctness demands it, since it costs more and adds latency.

Part 8 — Networking ★ CORE

Virtual Network (VNet) — your private network

A VNet is your isolated network in Azure. You divide it into subnets, control traffic with security rules, and connect it to other networks or on-prem.

Virtual Network 10.0.0.0/16 +-- Subnet "web" 10.0.1.0/24 [ VMs / App ] | guarded by Network Security Group (NSG) +-- Subnet "app" 10.0.2.0/24 [ services ] +-- Subnet "data" 10.0.3.0/24 [ databases ] (private, no inbound from internet) NSG = firewall rules (allow/deny by IP, port, protocol) applied to subnets or NICs.

Core networking services

ServiceRole
Network Security Group (NSG)Allow/deny traffic rules (stateful firewall)
Azure Load BalancerL4 (TCP/UDP) load balancing
Application GatewayL7 (HTTP) LB + WAF + routing
Azure Front DoorGlobal L7 LB + CDN + WAF at the edge
Azure DNSManaged DNS hosting
VPN GatewayEncrypted tunnel to on-prem over internet
ExpressRoutePrivate dedicated link to Azure (no internet)
Private Link / EndpointReach PaaS services over private IP

Connecting to on-premises

VPN Gateway: on-prem ==(encrypted over internet)== Azure cheaper, variable latency ExpressRoute: on-prem ==(private dedicated circuit)== Azure expensive, predictable, higher bandwidth, bypasses the public internet
Keep data tiers private Databases and internal services should sit in subnets with no inbound internet access. Use Private Endpoints so traffic to PaaS services (SQL, Storage, Cosmos) stays on the Azure backbone, not the public internet. Expose only what must be public, behind a WAF (Application Gateway or Front Door).

Part 9 — Messaging & integration ◆ CONCEPT

Messaging decouples components so they can scale and fail independently. Azure has distinct services for different patterns — choosing the right one is a common design question.

ServicePatternUse for
Service BusEnterprise message broker (queues + topics)Ordered, transactional, pub/sub messaging
Event GridEvent routing (pub/sub, reactive)React to discrete events (blob created, etc.)
Event HubsHigh-throughput event streamingTelemetry, logs, IoT, big data pipelines (Kafka-like)
Queue StorageSimple, cheap queueBasic background job decoupling

Service Bus vs Event Grid vs Event Hubs

SERVICE BUS (messages, commands): "process this order" -> queue -> one worker handles it rich features: ordering (FIFO), sessions, dead-letter, transactions, topics+subscriptions (pub/sub) EVENT GRID (events, reactions): "a blob was created!" -> fan out to many subscribers lightweight, reactive, near-real-time event routing EVENT HUBS (event streams, telemetry): millions of events/sec -> [ stream ] -> consumers read at their own pace, replayable. Kafka-compatible. Rule: command/work -> Service Bus. Reaction to a fact -> Event Grid. Massive stream -> Event Hubs.
Design consumers to be idempotent Messaging delivers at-least-once, so a message may arrive twice. Processing it twice must be safe (dedupe on a message ID). Use dead-letter queues to isolate "poison" messages that repeatedly fail, so they don't block the pipeline.

Part 11 — AI & machine learning ★ CORE

Azure's AI portfolio spans pre-built APIs, the OpenAI partnership, and a full ML platform. This is a key strength given the Microsoft-OpenAI relationship.

A typical RAG architecture on Azure

docs -> Document Intelligence (extract) -> chunk -> Azure OpenAI (embeddings) -> Azure AI Search (vector index) user question -> embed (Azure OpenAI) -> Azure AI Search (hybrid retrieve + semantic rank) -> Azure OpenAI (GPT-4o) with retrieved context -> grounded answer + citations -> Content Safety checks in/out
Azure OpenAI vs OpenAI direct Azure OpenAI runs the same models inside your Azure tenant with enterprise features: VNet/Private Link, Entra ID auth, regional data residency, content filtering, and SLAs. Enterprises choose it for governance and compliance. The API is largely compatible with OpenAI's, so porting is straightforward.

The security mantras

  • Identity is the perimeter — secure with MFA, Conditional Access, least privilege.
  • Secrets in Key Vault, never in code; use managed identities to access them.
  • Encrypt in transit (TLS) and at rest (default on most services).
  • Defense in depth — layer network, identity, app, and data controls.
  • Defender + Sentinel for continuous monitoring and response.

Cost management

  • Right-size — match VM/DB SKUs to actual usage; downscale idle resources.
  • Commit — Reserved Instances / Savings Plans for steady workloads (up to ~70%).
  • Spot — for interruptible batch (up to ~90% off).
  • Auto-scale & scale-to-zero — Functions, Container Apps, serverless DB tiers.
  • Lifecycle policies — tier blobs to cool/archive automatically.
  • Budgets & alerts — Cost Management + tags for chargeback.
The shared responsibility model Azure secures the cloud (physical DCs, hypervisor, backbone). You secure what's in the cloud — your identities, data, network config, OS patching (for IaaS), and access policies. The line shifts: with SaaS/PaaS Azure handles more; with IaaS VMs you handle the OS and up. Know which side you own for each service.
