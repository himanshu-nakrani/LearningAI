Part 0 — Mental model & global infrastructure ★ CORE

Google Cloud Platform runs your workloads on the same global infrastructure that powers Google Search, Gmail, and YouTube. Its differentiators are a famously fast global network, data & analytics (BigQuery), Kubernetes (which Google created), and cutting-edge AI (Gemini, Vertex AI, TPUs).

The geographic hierarchy

MULTI-REGION (e.g. "US", "EU" — for geo-redundant data) +-- REGION (e.g. "us-central1" — independent geo area) | +-- ZONE us-central1-a (isolated DC failure domain) | +-- ZONE us-central1-b | +-- ZONE us-central1-c | +-- (regions interconnected by Google's private global fiber network — low latency between them) Deploy across ZONES to survive a DC failure. Deploy across REGIONS to survive a regional outage.
ConceptWhat it is
ZoneA single failure domain (≈ one datacenter) within a region
RegionA geographic area containing 3+ zones
Multi-regionData replicated across regions (e.g. for Cloud Storage, BigQuery)
GCP's global resources are a real differentiator Unlike many clouds where most things are regional, several GCP resources are global or multi-regional by design — the VPC network, HTTP(S) load balancer (one anycast IP worldwide), and Cloud Storage multi-region buckets. Google's private backbone makes cross-region traffic fast and predictable.

How you interact with GCP

  • Cloud Console — the web GUI.
  • gcloud CLI — the unified command-line tool (part of the Cloud SDK).
  • Cloud Shell — a browser-based terminal with tools pre-installed.
  • Terraform / Config Connector / Deployment Manager — IaC.
  • Client libraries — for Python, Go, Java, Node.js, etc.
# gcloud CLI basics
gcloud auth login
gcloud config set project my-project-id
gcloud compute instances create my-vm \
   --zone=us-central1-a --machine-type=e2-medium \
   --image-family=debian-12 --image-project=debian-cloud

Part 1 — Resource hierarchy & projects ◆ CONCEPT

The Project is the fundamental organizing unit in GCP — every resource belongs to exactly one project, which is the boundary for billing, APIs, permissions, and quotas.

ORGANIZATION (your company's root node, tied to a domain) | FOLDERS (optional: group by dept / team / env) | PROJECTS (the core unit: billing, APIs, IAM, quota) | RESOURCES (VMs, buckets, databases, etc.) IAM policies set higher up are INHERITED downward. Set a policy on a folder -> applies to all its projects.
LevelPurpose
OrganizationRoot of the hierarchy; org-wide policy
FolderGroup projects (by team, environment, dept)
ProjectBilling + API + IAM + quota boundary; holds resources
ResourceAn individual service instance
Use separate projects for separate environments A common pattern is one project per app per environment (e.g. myapp-dev, myapp-prod). Projects are free and give you clean isolation of billing, quotas, and access — far safer than mixing dev and prod in one project. Group them under folders for org-wide policy.

Enabling APIs

Unlike some clouds, in GCP you must explicitly enable each service's API in a project before using it. This is a frequent first stumbling block.

gcloud services enable compute.googleapis.com
gcloud services enable run.googleapis.com

Part 2 — Identity & access (IAM) ★ CORE

Google Cloud IAM answers: who can do what on which resource. The model is consistent across all of GCP.

WHO (member/principal) WHAT (role) ON (resource) ---------------------- -------------- ------------- Google account (user) a bundle of organization Google group permissions: folder service account roles/viewer project workload identity roles/editor specific resource allUsers (public) roles/owner custom roles IAM policy = binding of (member -> role) at a resource level, inherited down the hierarchy.

The three role types

TypeExampleNote
Basic (primitive)Owner, Editor, ViewerBroad; avoid in production
Predefinedroles/storage.objectAdminGranular, Google-curated — prefer these
Customyour own permission setWhen predefined don't fit exactly

Service accounts (the identity for workloads)

A service account is a special identity for a resource or application (not a human). Code running on a VM, in Cloud Run, or in GKE uses a service account to authenticate to other GCP services — without embedding keys.

WITHOUT (bad): app holds a service-account KEY FILE -> long-lived secret, leak risk WITH attached service account (good): Cloud Run / GKE / VM runs AS a service account -> gets short-lived tokens automatically, no key file For workloads OUTSIDE GCP (e.g. on AWS, GitHub Actions): use WORKLOAD IDENTITY FEDERATION -> exchange an external token for GCP access, still no key files.
Avoid service account key files Downloaded JSON key files are long-lived credentials that frequently leak (committed to git, left in images). Prefer attached service accounts (the resource assumes the identity) and Workload Identity Federation for external systems. If you must use keys, rotate them and store in Secret Manager. Apply least privilege — grant predefined roles at the narrowest scope.
Groups over individual grants Assign roles to Google Groups, then manage membership in the group, rather than binding individual users to resources. This keeps IAM policies small and makes onboarding/offboarding a single membership change.

Notable Compute Engine features

  • Custom machine types — pick exact vCPU/RAM instead of fixed sizes.
  • Live migration — VMs keep running during host maintenance (rare among clouds).
  • Managed Instance Groups (MIGs) — autoscaling, autohealing, rolling updates for identical VMs behind a load balancer.
  • Sustained-use discounts — automatic discounts the longer a VM runs in a month (no commitment needed).

Sustained-use discounts are automatic Unlike reserved instances elsewhere, GCP automatically discounts VMs that run for a large fraction of the month — no upfront commitment. Combine with committed-use discounts for steady baseline capacity and Spot for burst/batch.

Part 4 — Containers & Kubernetes (GKE) ★ CORE

Google created Kubernetes, and Google Kubernetes Engine (GKE) is widely regarded as the most mature managed Kubernetes. Containers are central to GCP's story.

ServiceWhat it is
Artifact RegistryStore container images & packages (successor to Container Registry)
Cloud RunServerless containers — scale to zero, pay per use
GKE AutopilotManaged K8s where Google runs the nodes for you
GKE StandardManaged K8s with full node control

GKE Autopilot vs Standard

STANDARD: you manage node pools, sizing, upgrades. full control, you optimize (and own) the nodes. AUTOPILOT: Google manages nodes entirely. You deploy pods; pay per pod resource request. Less ops, hardened defaults. -> recommended default. Both are real Kubernetes (kubectl, manifests, Helm).

Cloud Run — the GCP serverless container favorite

Deploy any container that listens on a port; Cloud Run handles scaling (including to zero), HTTPS, and revisions. It's the easiest path to production for stateless web services and APIs on GCP.

push container -> Cloud Run -> public HTTPS URL autoscale 0 -> N by traffic pay only while handling requests great for: APIs, web apps, event handlers, microservices without touching Kubernetes.
Default to Cloud Run, escalate to GKE For most stateless services, Cloud Run is simpler, cheaper at low/spiky traffic (scale to zero), and requires no cluster management. Choose GKE when you need full Kubernetes features: complex networking, stateful workloads, operators, fine-grained scheduling, or an existing K8s investment.

Cloud Run functions (FaaS)

TRIGGER FUNCTION ------- -------- HTTP request ----> [ your code ] Pub/Sub message ----> (Python, Node, Go, Cloud Storage event ----> Java, .NET, Ruby...) Cold starts & statelessness Scale-to-zero services cold-start on the first request after idle. Set a minimum number of instances for latency-sensitive APIs, keep containers lean for fast startup, and design every function to be stateless and idempotent (events may be delivered more than once).

Part 6 — Storage ★ CORE

ServiceModelUse for
Cloud Storage (GCS)Object storage (buckets → objects)Files, media, backups, data lake, static sites
Persistent Disk / HyperdiskBlock storage for VMsVM disks, databases
FilestoreManaged NFS file sharesShared filesystems, lift-and-shift

Cloud Storage classes (cost vs access frequency)

STANDARD frequent access, hot data, no retrieval fee NEARLINE accessed <1x/month (30-day min) -> backups COLDLINE accessed <1x/quarter (90-day min) -> archive ARCHIVE accessed <1x/year (365-day min) -> cheapest Object Lifecycle Management auto-transitions objects to colder classes (or deletes them) as they age. Buckets can be regional, dual-region, or multi-region (trade cost for geo-redundancy & availability).

Key Cloud Storage features

  • Single global namespace — bucket names are globally unique; one API regardless of location.
  • Strong consistency — reads after writes are immediately consistent.
  • Signed URLs — grant time-limited access for direct uploads/downloads (don't proxy big files through your app).
  • Uniform bucket-level access — manage permissions with IAM instead of per-object ACLs.
Use signed URLs for uploads Just like other clouds, don't stream large user uploads through your servers. Issue a signed URL so the client uploads directly to the bucket, then process via an event (Eventarc/Pub/Sub). This saves bandwidth and keeps app instances free.

Cloud Spanner — the standout

Spanner is Google's globally-distributed relational database that offers both horizontal scale (like NoSQL) and strong consistency with SQL and ACID transactions — historically a "pick one" trade-off. It powers Google's own critical systems.

Traditional SQL: strong consistency, but scales UP (one big machine + replicas) Traditional NoSQL: scales OUT, but eventual consistency SPANNER: scales OUT (many nodes, many regions) AND strong consistency + SQL + ACID (via TrueTime — synchronized atomic clocks) Use when you need global scale WITHOUT giving up transactions/consistency. Premium cost.

NoSQL & in-memory

ServiceModelUse for
FirestoreServerless document DB (real-time sync)Mobile/web apps, real-time data
BigtableWide-column, petabyte-scale, low latencyTime-series, IoT, analytics, high throughput
MemorystoreManaged Redis / MemcachedCaching, sessions
Picking a GCP database Relational + regional → Cloud SQL. Need Postgres but faster → AlloyDB. Global scale + strong consistency + SQL → Spanner. Document store with real-time sync → Firestore. Massive write throughput / time-series → Bigtable. Cache → Memorystore.

Part 8 — Networking ★ CORE

VPC — a global private network

A GCP Virtual Private Cloud is global: a single VPC can span all regions, with subnets that are regional. This simplifies multi-region architectures compared to clouds where VPCs are regional.

VPC "my-network" (GLOBAL — spans all regions) +-- Subnet us-central1 10.0.1.0/24 +-- Subnet europe-west1 10.0.2.0/24 +-- Subnet asia-east1 10.0.3.0/24 all in ONE VPC, connected over Google's backbone Firewall rules are defined at the VPC level (allow/deny by tag, service account, IP range, port).

Core networking services

ServiceRole
VPC firewall rulesAllow/deny traffic (by tag, SA, IP, port)
Cloud Load BalancingGlobal anycast LB (HTTP/S, TCP, UDP)
Cloud CDNEdge caching of content close to users
Cloud DNSManaged, global, low-latency DNS
Cloud NATOutbound internet for private instances
Cloud VPN / InterconnectConnect on-prem (VPN over internet / dedicated link)
Cloud ArmorWAF + DDoS protection at the edge
Private Service ConnectPrivate access to Google/3rd-party services

The global HTTP(S) load balancer

ONE anycast IP, worldwide: user (Tokyo) --+ user (Paris) --+--> single global IP --> nearest healthy user (NYC) --+ (Cloud LB + CDN) backend region Routes each user to the closest backend, integrates Cloud CDN and Cloud Armor (WAF). No per-region IPs to juggle. A signature GCP capability.
Keep backends private; expose via the LB Put application and data tiers on private subnets with no external IPs. Use Cloud NAT for outbound access, and front public traffic with the global load balancer + Cloud Armor. Use Private Service Connect / Private Google Access to reach Google APIs without traversing the internet.

Pub/Sub: the GCP messaging backbone

Pub/Sub is GLOBAL and serverless — one service covers both queue and streaming patterns: publisher -> TOPIC -> SUBSCRIPTION(s) -> subscriber(s) | +-------------+--------------+ v v v analytics data pipeline notifier (each subscription gets its own copy of messages) - at-least-once delivery (make consumers idempotent) - scales to millions of messages/sec automatically - dead-letter topics + retry policies built in - common ingestion front-end for Dataflow / BigQuery
Pub/Sub is the glue of GCP architectures It's the default way to decouple services and to ingest event/streaming data into the analytics stack (Pub/Sub → Dataflow → BigQuery is a canonical pipeline). Use push subscriptions to trigger Cloud Run, or pull subscriptions for worker fleets. Design idempotent consumers.

Part 10 — Data & analytics (BigQuery & friends) ★ CORE

Data analytics is arguably GCP's strongest domain, anchored by BigQuery.

INGEST STORE/QUERY PROCESS VISUALIZE ------ ----------- ------- --------- Pub/Sub -> BigQuery <- Dataflow -> Looker / Dataflow (serverless (Apache Beam) Looker Studio Data Transfer warehouse) Dataproc Storage Cloud Storage (managed Spark) (data lake)

BigQuery — the flagship

A serverless, petabyte-scale data warehouse. There are no servers to manage — you load data and run SQL; BigQuery handles all the infrastructure and scales compute automatically. Storage and compute are separated and billed independently.

load data -> BigQuery (columnar, distributed storage) -> run standard SQL across petabytes in seconds -> pay for bytes scanned (on-demand) OR reserved slots (flat-rate capacity) Built-in extras: - BigQuery ML: train ML models with SQL (CREATE MODEL) - BI Engine: in-memory acceleration for dashboards - federated queries: query GCS, Spanner, external data - Gemini in BigQuery: AI-assisted analytics
ServiceRole

Pub/SubStreaming ingestion
Cloud ComposerManaged Apache Airflow (orchestration)
DataplexData governance & catalog across the lake
Looker / Looker StudioBI & dashboards
Control BigQuery cost On-demand pricing charges by bytes scanned, so SELECT * on a huge table is expensive. Select only needed columns, partition tables by date, cluster on common filters, and preview with LIMIT cautiously (it still may scan). For steady heavy use, switch to capacity (slot) pricing.

A typical RAG architecture on GCP

docs -> Document AI (parse) -> chunk -> Vertex AI embeddings -> Vector Search index (or Vertex AI Search managed) user question -> embed (Vertex AI) -> Vector Search / Vertex AI Search (retrieve) -> Gemini (generate grounded answer + citations) -> safety filters in/out Or use Vertex AI Search as a managed end-to-end RAG engine (ingest + retrieve + ground) with less plumbing.
Gemini + BigQuery + TPUs = GCP's AI edge GCP's strengths: Gemini's strong multimodal/long-context models, native AI inside BigQuery (analyze data with SQL + LLMs), and TPUs for cost-effective large-scale training. If your workload is data-and-AI heavy, GCP's integration of analytics and ML is compelling.

Define SLOs in Cloud Monitoring Cloud Monitoring has first-class support for SLOs and error budgets. Define what "good" means (e.g., 99.9% of requests under 300ms) and alert on budget burn rather than raw thresholds — this reduces noisy alerts and focuses on user-facing impact.

Security mantras

  • Least privilege IAM — predefined roles at the narrowest scope; groups over individuals.
  • No service-account key files — use attached SAs & Workload Identity Federation.
  • Secrets in Secret Manager, keys in Cloud KMS.
  • VPC Service Controls to build a data exfiltration perimeter for sensitive projects.
  • Encryption at rest (default, Google-managed or CMEK) and in transit (default).
  • IAP for zero-trust app access instead of VPNs.

Cost management

  • Sustained- & committed-use discounts for steady compute.
  • Spot VMs for batch / fault-tolerant work (up to ~91% off).
  • Scale to zero with Cloud Run / Cloud Run functions.
  • BigQuery — partition/cluster tables, query only needed columns; consider slot reservations.
  • Storage lifecycle — auto-tier objects to Nearline/Coldline/Archive.
  • Budgets & alerts + labels for cost attribution; the Recommender suggests rightsizing.
Shared responsibility model Google secures the underlying infrastructure (hardware, network, hypervisor). You secure your data, IAM configuration, network rules, and (for IaaS) OS patching. With serverless/managed services Google handles more of the stack; with Compute Engine VMs you own the OS upward. Know the boundary per service.
