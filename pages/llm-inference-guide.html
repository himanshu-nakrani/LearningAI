Part 0 — Why inference is hard & what we optimize ◆ CONCEPT

Training gets the headlines, but in production inference is where the money goes — a deployed model serves predictions millions of times. LLM inference is uniquely hard because models are huge (billions of parameters), generation is sequential (one token at a time), and GPUs are expensive and memory-constrained. The whole field is about squeezing more tokens per second per dollar out of fixed hardware.

The three things we trade off

LATENCY (fast per request) /\ / \ / \ You can't max all three at once. / \ Optimizations move you along these / \ axes; the "right" point depends on /__________\ your product (chatbot vs batch job). THROUGHPUT COST (many req ($ per per second) million tokens)

A real-time chatbot prioritizes latency. A nightly document-processing job prioritizes throughput and cost and doesn't care about per-request latency. Almost every technique in this guide is "improve one axis, possibly hurt another" — knowing which knob does what is the senior skill.

The optimization landscape (the map)

LayerTechniquesMainly improves
ModelQuantization, distillation, pruning, smaller modelMemory, cost, latency
Attention/kernelFlashAttention, GQA/MQA, fused kernelsLatency, memory
DecodingSpeculative decoding, Medusa, lookaheadLatency
MemoryPagedAttention, prefix caching, KV quantizationThroughput (bigger batches)
SchedulingContinuous batching, chunked prefillThroughput, latency
SystemParallelism, disaggregation, multi-GPUScale, latency
ServingAutoscaling, routing, caching responsesCost, latency
The one-sentence mental model LLM decode is memory-bandwidth bound: for each token you must read all the model's weights from GPU memory, but you only do a little math with them. So the game is (1) read fewer/smaller weights (quantization, smaller models), (2) reuse the read across many requests (batching), and (3) avoid redundant work (KV cache, prefix caching). Almost everything follows from this.

Part 1 — The two phases: prefill vs decode ★ CORE

Every LLM request has two fundamentally different phases with opposite performance characteristics. Understanding this split is the foundation of everything else.

PROMPT: "Translate to French: Hello world" PHASE 1 — PREFILL (process the whole prompt at once) all prompt tokens processed in PARALLEL in one pass -> builds the initial KV cache -> produces the FIRST output token -> COMPUTE-bound (lots of matrix math, GPU saturated) -> determines TTFT (time to first token) PHASE 2 — DECODE (generate output one token at a time) token N depends on token N-1 -> strictly SEQUENTIAL each step: read ALL weights, compute ONE token -> MEMORY-BANDWIDTH-bound (GPU underutilized) -> determines TPOT (time per output token) prefill: [t1 t2 t3 t4 t5] --one pass--> first token decode: -> t6 -> t7 -> t8 -> ... (one at a time)

Why they behave so differently

PrefillDecode
Tokens processedAll prompt tokens at onceOne at a time
ParallelismHigh (parallel over sequence)None (sequential dependency)
BottleneckCompute (FLOPs)Memory bandwidth
GPU utilizationHighLow (without batching)
Metric it drivesTTFTTPOT / tokens-per-sec

The implication for a single request

A 500-token prompt -> 200-token answer: prefill 500 tokens: fast, one big parallel pass (e.g. 50ms) decode 200 tokens: 200 sequential steps (e.g. 200 x 20ms = 4000ms) <- dominates total latency! Long OUTPUTS are expensive (sequential decode). Long INPUTS are cheaper per token (parallel prefill) but cost memory (bigger KV cache) and compute.
Why a single request wastes the GPU During decode you read billions of weight parameters from HBM to generate just one token's worth of math. The GPU's compute units sit mostly idle waiting on memory. This is the central inefficiency — and the reason batching many requests together (Part 5) is the single biggest throughput lever: you read the weights once and amortize that read across many sequences.

Part 2 — The KV cache (the heart of it all) ★ CORE

The KV cache is the most important concept in LLM serving. It's an optimization that makes decode tractable — and it's also the main thing competing for GPU memory.

The problem it solves

In attention, each new token must attend to all previous tokens via their Key (K) and Value (V) vectors. Without caching, generating token N would recompute the K and V for all N-1 previous tokens every single step — O(N²) wasted work. The KV cache stores those K and V vectors so each new token only computes its own.

WITHOUT KV cache (naive): step for token 4: recompute K,V for tokens 1,2,3,4 step for token 5: recompute K,V for tokens 1,2,3,4,5 -> redundant recomputation every step (O(N^2) total) WITH KV cache: keep K,V for all past tokens in GPU memory. step for token 5: compute ONLY token 5's K,V, attend against cached 1..4. -> each step is O(N) attention, no recompute. cache grows by one token's K,V each decode step: [K1 K2 K3] + K4 -> [K1 K2 K3 K4] [V1 V2 V3] + V4 -> [V1 V2 V3 V4]

The KV cache size formula (memorize this)

KV cache bytes = 2 x num_layers x (num_kv_heads x head_dim) x seq_len x batch_size x bytes_per_value 2 -> one for K, one for V num_layers -> cache exists at every transformer layer kv_heads x head_dim -> the hidden size used for K/V seq_len -> grows with every generated token batch_size -> one cache per sequence in the batch bytes -> 2 for FP16, 1 for INT8/FP8

A worked example (why memory runs out fast)

Llama-3-style 70B model, FP16 KV cache:
  layers = 80, kv_heads = 8, head_dim = 128  (GQA)
  per-token KV = 2 * 80 * (8 * 128) * 2 bytes
              = 2 * 80 * 1024 * 2  = ~327 KB per token

  One request with 8K context:
     8192 tokens * 327 KB  = ~2.6 GB  (for ONE sequence!)

  Batch of 32 at 8K context:
     32 * 2.6 GB = ~84 GB  of KV cache alone
  ... on top of 140 GB of FP16 weights. This is why
  KV cache memory, not compute, caps your batch size.
Why GQA/MQA exist Notice the KV size scales with num_kv_heads. Multi-Query Attention (MQA, 1 KV head) and Grouped-Query Attention (GQA, a few KV heads shared across many query heads) slash KV cache size — often 8x smaller — letting you fit far bigger batches/contexts with minimal quality loss. This is why nearly every modern model uses GQA. (More in Part 8.)
The KV cache is the bottleneck, not the weights Weights are a fixed cost loaded once. The KV cache is dynamic — it grows with every token and every concurrent request, and it competes with weights for the same HBM. Most "out of memory" and "why is my batch size so small" problems trace back to KV cache. Managing it well (Parts 6, 7, 11) is the core of high-throughput serving.

Part 3 — Memory math: what fits on a GPU ★ CORE

Senior interviews love "will this model fit?" and "how many GPUs do I need?" Know the back-of-envelope math cold.

Weight memory (the dominant fixed cost)

weight memory ~= num_params x bytes_per_param bytes_per_param: FP32=4 FP16/BF16=2 INT8/FP8=1 INT4=0.5 Quick rule (FP16): GB needed ~= 2 x billions of params 7B model -> ~14 GB 13B model -> ~26 GB 70B model -> ~140 GB 405B model -> ~810 GB INT8: roughly 1 x params (GB) ; INT4: ~0.5 x params

The total memory budget

GPU HBM must hold ALL of: +------------------------------------------+ | model weights (fixed, the biggest) | | KV cache (grows w/ batch+len) | | activations (transient, working) | | framework overhead (CUDA ctx, buffers) | +------------------------------------------+ usable for KV cache = HBM - weights - overhead -> this leftover determines your max batch x context.

Common GPU memory sizes

GPUHBMComfortably serves (FP16)
A10G / L424 GB~7B (or quantized 13B)
A100 40GB40 GB~13B; 70B needs quant or multi-GPU
A100 / H100 80GB80 GB~70B quantized, or 1 of several for 70B FP16
H200141 GB70B FP16 single-GPU with room for KV
8x H100640 GB405B (with tensor parallelism)
The "how many GPUs" answer Step 1: weights = ~2 × params GB (FP16). Step 2: add KV cache budget for your target batch × context. Step 3: divide by per-GPU HBM and round up — then pick a parallelism degree that divides the model cleanly (2, 4, 8). Always leave ~10-20% headroom for activations and fragmentation. Quantizing to INT8/FP8 roughly halves weight memory and can drop your GPU count.

Part 4 — Roofline: compute-bound vs memory-bound ◆ CONCEPT

The roofline model explains why batching helps and where the ceilings are. It's the theoretical backbone of inference optimization.

Arithmetic intensity

Arithmetic intensity = FLOPs of compute ÷ bytes moved from memory. If you do lots of math per byte read, you're compute-bound (limited by the GPU's TFLOPs). If you do little math per byte, you're memory-bound (limited by HBM bandwidth).

performance (tokens/s) ^ | ___________ compute ceiling (TFLOPs) | / | / <- compute-bound region | / (prefill, large batches) | / | / <- memory-bound region | / (single-request decode) | / +---/------------------------> arithmetic intensity Decode of ONE request sits far left (memory-bound): GPU compute idle, waiting on weight reads. Batching raises arithmetic intensity -> moves you RIGHT toward the compute ceiling -> better GPU use.

Why batching is the master lever

Decode reads the FULL weight matrix once per step. batch = 1: read weights, compute 1 token -> 1 token/read batch = 32: read weights ONCE, compute 32 tokens (one per sequence) -> 32 tokens/read Same memory traffic, 32x the useful work, until you hit the compute ceiling. This is why throughput scales nearly for free with batch size in the memory-bound regime.
Batching has a ceiling and a cost As batch size grows you eventually become compute-bound (the free lunch ends) or run out of KV cache memory (the more common limit). And bigger batches raise per-request latency (each request waits for the whole batch step). Throughput vs latency, again. The art is the largest batch that still meets your latency SLO.

Part 5 — Batching: static, dynamic, continuous ★ CORE

Batching is the highest-impact throughput technique. How you batch matters enormously — continuous batching is the breakthrough that modern engines are built around.

Static batching (naive)

Collect N requests, run them together, wait for ALL to finish before starting the next batch. req A: [====done at step 5]........(idle)......... req B: [==================done at step 20] req C: [========done at step 9]....(idle)......... ^ batch can't refill until B finishes ^ Problem: short requests finish early and their GPU slot sits IDLE until the longest request in the batch ends. Terrible utilization when output lengths vary (they do).

Continuous batching (a.k.a. in-flight / iteration-level batching)

Instead of batching at the request level, batch at the iteration (per-token) level. After every decode step, finished sequences leave and waiting requests join immediately. The batch is continuously refilled.

After EACH token step, evict finished, admit new: step 5: A finishes -> slot freed -> D admitted instantly req A: [====done] req D: [new====starts here====...] req B: [=========================...] req C: [========done] -> E admitted req E: [new===...] GPU slots stay full -> 2-4x+ higher throughput than static batching on real, variable-length workloads. This is THE key innovation behind vLLM / TGI / TRT-LLM.

Chunked prefill (mixing prefill and decode)

A long prompt's prefill can monopolize the GPU and stall ongoing decodes (raising everyone's latency). Chunked prefill splits a big prefill into chunks and interleaves them with decode steps, smoothing latency.

Without: [-------- huge prefill --------] then decodes ongoing requests stall (TTFT/TPOT spike) With chunked prefill: [prefill chunk][decode][prefill chunk][decode]... -> prefill progresses WITHOUT starving active decodes. Balances TTFT vs TPOT.
BatchingThroughputNotes
None (1 req)WorstGPU mostly idle in decode
StaticOKWastes slots on length variance
ContinuousBestStandard in modern engines
+ Chunked prefillBest + smootherBalances TTFT and TPOT
The interview soundbite "Static batching wastes GPU because the batch is held hostage by its longest sequence. Continuous batching schedules at the token level — finished requests leave and new ones join every iteration — keeping the GPU saturated. It's the single biggest reason vLLM and TGI massively outperform naive serving." Knowing this distinction signals real serving experience.

Part 6 — PagedAttention & KV cache management ★ CORE

PagedAttention (introduced by vLLM) solved the KV cache memory fragmentation problem and is the reason vLLM became the default serving engine. It's the most-asked optimization in serving interviews.

The problem: KV cache fragmentation

Traditional serving pre-allocates a contiguous chunk of memory for each request's KV cache, sized to the maximum possible length. This wastes huge amounts of memory: most requests don't reach max length (internal fragmentation), and freed blocks of different sizes leave unusable gaps (external fragmentation).

NAIVE: reserve max_len contiguous slab per request req A (max 2048): [used 100][======= wasted 1948 =======] req B (max 2048): [used 1500][==== wasted 548 ====] -> you reserved for the worst case, but most tokens never arrive. Often 60-80% of KV memory is wasted, so your effective batch size collapses.

The solution: page the KV cache like virtual memory

PagedAttention borrows the OS idea of paging. KV cache is split into small fixed-size blocks (pages). A request's tokens map to blocks via a block table; blocks need not be contiguous and are allocated on demand as the sequence grows.

Logical view (per request) Physical GPU blocks (shared pool) req A tokens -> block table +--------+--------+--------+ [0..15] -> phys block 7 | blk 0 | blk 1 | blk 2 | [16..31] -> phys block 3 +--------+--------+--------+ [32..] -> phys block 9 | blk 3 A| blk 4 | blk 5 | +--------+--------+--------+ req B tokens -> block table | blk 6 | blk 7 A| blk 8 | [0..15] -> phys block 1 +--------+--------+--------+ [16..] -> phys block 4 | blk 9 A| ... | +--------+ Allocate a block only when needed -> near-zero waste (<4% vs 60-80%). Frees blocks the instant a request ends.

Bonus: copy-on-write sharing

Because tokens are blocks, multiple sequences can share identical blocks — e.g., a shared system prompt or parallel samples from one prompt. They share the underlying physical blocks until one diverges (copy-on-write), saving memory and prefill compute.

Shared system prompt across 3 requests: req1 ┐ req2 ├── all point to the SAME physical blocks for req3 ┘ the shared prefix; only their unique continuations get private blocks. -> the basis of "prefix caching" (Part 11).
The interview soundbite "PagedAttention treats KV cache like OS virtual memory: fixed-size blocks, non-contiguous, allocated on demand via a block table. It cuts KV waste from ~60-80% to under 4%, so you fit far bigger batches — directly boosting throughput. It also enables copy-on-write sharing of common prefixes." This one answer demonstrates you understand the actual bottleneck in serving.

Part 7 — Quantization ★ CORE

Quantization stores weights (and sometimes activations and the KV cache) in lower precision — fewer bits per number. It shrinks memory, lets bigger models fit on fewer GPUs, and speeds up the memory-bound decode phase (less data to move).

The precision ladder

FormatBitsMemory vs FP16Typical use
FP32322xRare for inference
FP16 / BF16161x (baseline)Default full precision
FP880.5xModern GPUs (H100+), great quality/speed
INT880.5xWidely supported, small quality hit
INT440.25xMax compression, noticeable but often acceptable loss

Why lower precision speeds up decode

Decode is memory-bound: time ~ bytes of weights read. FP16 70B: read ~140 GB per token step INT8 70B: read ~70 GB -> ~2x faster decode INT4 70B: read ~35 GB -> ~4x less memory traffic Less data to move from HBM = faster tokens AND smaller footprint = bigger batches. A double win in the memory-bound regime.

PTQ vs QAT

The norm for LLM inferenceFor squeezing out the last accuracy

Weight-only vs weight+activation

W4A16: 4-bit weights, 16-bit activations (GPTQ/AWQ) great memory savings; compute still in FP16. Best for memory-bound DECODE (the common case). W8A8: 8-bit weights AND activations (SmoothQuant, FP8) uses faster INT8/FP8 compute units too. Helps compute-bound PREFILL and large batches.
Quantization is not free — measure it Lower precision can degrade quality, and the impact is task-dependent: it may be invisible on chat but hurt code generation, math, or long-context reasoning. Always run your own evals after quantizing. FP8 and good 4-bit methods (AWQ) are often nearly lossless; aggressive INT4 on a small model can fall off a cliff. Rule of thumb: a larger model quantized often beats a smaller model at full precision for the same memory.

Part 8 — Attention optimizations (FlashAttention, GQA, MQA) ★ CORE

FlashAttention — fix the memory bottleneck in attention

Naive attention computes the full N×N attention score matrix and writes it to HBM — slow and memory-hungry (O(N²) memory). FlashAttention computes attention in tiles that fit in fast on-chip SRAM, never materializing the full matrix in HBM. It's mathematically identical, just IO-aware.

NAIVE attention: Q x K^T -> [N x N] scores -> write to HBM -> softmax -> read back -> x V. O(N^2) HBM traffic. Slow. FLASHATTENTION (tiled, fused, online softmax): process Q,K,V in blocks that fit in SRAM (fast), accumulate the result incrementally, never store the full N x N matrix in HBM. -> O(N) HBM traffic, big speedup, less memory. -> enables long context that would otherwise OOM.

MHA vs MQA vs GQA — shrinking the KV cache

Standard Multi-Head Attention (MHA) gives every query head its own K and V heads — large KV cache. MQA shares a single K/V head across all query heads (tiny cache, some quality loss). GQA is the sweet spot: a few K/V heads shared among groups of query heads.

MHA (e.g. 32 Q heads, 32 KV heads): Q1 Q2 Q3 ... Q32 K1 K2 K3 ... K32 <- full KV cache (biggest) MQA (32 Q heads, 1 KV head): Q1 Q2 Q3 ... Q32 K1 (shared by all) <- 32x smaller KV, some quality loss GQA (32 Q heads, 8 KV heads) -- the modern default: [Q1-Q4]->K1 [Q5-Q8]->K2 ... 8 groups -> ~4x smaller KV than MHA, near-MHA quality. Used by Llama-3, Mistral, most current models.
SchemeKV cache sizeQuality
MHALargest (1 KV per Q head)Best
GQAMedium (shared in groups)Near-MHA
MQASmallest (1 KV total)Slight drop
Why this matters for serving Smaller KV cache (GQA/MQA) means more memory for batching and longer contexts — directly more throughput. FlashAttention makes long context feasible at all. When someone asks "how would you support 128K context efficiently?", the answer combines GQA (small KV), FlashAttention (no N² blowup), KV quantization, and PagedAttention (no fragmentation).

Part 9 — Speculative decoding & parallel decoding ★ CORE

Decode is sequential and memory-bound, so the GPU is underused. Speculative decoding exploits that idle compute: use a cheap method to guess several future tokens, then verify them all in one parallel pass of the big model. Accepted guesses are free tokens.

How it works

1. DRAFT: a small fast model proposes the next K tokens draft: "the cat sat on the" (guesses 5 tokens) 2. VERIFY: the big target model checks all K guesses in ONE parallel forward pass (same cost as 1 decode step, because decode is memory-bound — verifying 5 is ~free) 3. ACCEPT the longest correct prefix; reject the rest. target agrees with "the cat sat on" (4 of 5) -> emit 4 tokens, resume drafting from there Net: multiple tokens per big-model pass instead of one. Quality is IDENTICAL to the target model (verification guarantees only target-approved tokens are emitted).

Why it's a free speedup

The key insight: verifying K tokens costs almost the same as generating 1, because decode is memory-bandwidth-bound — you're reading the weights anyway, so processing K positions barely adds time. If the draft is right most of the time, you get 2-3x fewer big-model steps.

Variants

MethodHow it drafts
Draft modelA small separate model (e.g. 1B drafts for 70B)
Self-speculativeThe model drafts with some of its own layers
MedusaExtra prediction heads guess multiple next tokens
Lookahead decodingGenerates n-grams in parallel, no draft model
EAGLEFeature-level autoregression; high acceptance rates
Prompt lookupDraft by copying n-grams from the prompt (great for RAG/code)
Speculative decoding helps latency, not throughput It's a latency optimization for low-batch / interactive serving where the GPU has spare compute. Under heavy batching the GPU is already compute-saturated, so spending compute on speculation has little headroom and can even hurt. The speedup also depends on the acceptance rate — a poorly matched draft model wastes work. Use it for chatbots at modest concurrency; reconsider for max-throughput batch jobs.
Interview nuance worth stating "Speculative decoding trades spare compute for fewer sequential steps, so it shines at low batch sizes where decode is memory-bound and the GPU is idle. As batch size grows and you become compute-bound, its benefit shrinks. Output quality is unchanged because the target model verifies every token." That last point — lossless quality — is the part people forget.

Part 10 — Parallelism: tensor, pipeline, expert, data ★ CORE

When a model is too big for one GPU, or you need more throughput, you split work across GPUs. The four parallelism strategies solve different problems and are often combined.

Data parallelism (more throughput)

Replicate the WHOLE model on each GPU; split REQUESTS. GPU0: [full model] <- handles requests 1-100 GPU1: [full model] <- handles requests 101-200 Scales throughput linearly. Requires the model to fit on ONE GPU. No inter-GPU comms during inference. This is just "run N replicas behind a load balancer."

Tensor parallelism (split a model that's too big, low latency)

Split each LAYER's weight matrices ACROSS GPUs; every GPU does part of every layer, then they combine (all-reduce). layer's big matrix: [ ==== W ==== ] GPU0 holds [ W_left ] | GPU1 holds [ W_right ] each computes its half -> all-reduce to merge + reduces latency (GPUs work in parallel on each token) - heavy communication EVERY layer -> needs fast links (NVLink). Best WITHIN a single node (e.g. 8 GPUs).

Pipeline parallelism (split by layers across nodes)

Assign different LAYERS to different GPUs; tokens flow through the pipeline stage by stage. GPU0: layers 1-20 ┐ GPU1: layers 21-40 ├ a request passes 0 -> 1 -> 2 -> 3 GPU2: layers 41-60 │ GPU3: layers 61-80 ┘ + low communication (only at stage boundaries) -> works ACROSS nodes - "pipeline bubbles" (idle stages) unless you keep many micro-batches in flight. Adds latency.

Expert parallelism (for Mixture-of-Experts models)

MoE models have many "expert" FFNs; each token is routed to a few. Distribute experts across GPUs. token -> router -> expert 3 (GPU1) + expert 7 (GPU3) Only a FRACTION of params activate per token -> huge models with lower per-token compute. Requires routing comms (all-to-all). Used by Mixtral, DeepSeek, etc.
TypeSplitsUse whenComms cost
DataRequests (full model replicated)Model fits on 1 GPU; want throughputNone
TensorWithin each layerModel too big; want low latencyHigh (per layer) — needs NVLink
PipelineAcross layersModel spans nodesLow (stage boundaries)

How they combine in practice A 405B model on 8×H100 might use tensor parallelism within the node (fast NVLink). To scale across nodes you add pipeline parallelism, and to add throughput you replicate the whole setup (data parallelism). Rule: tensor parallel inside a node, pipeline parallel across nodes, data parallel for replicas. Set TP degree to a divisor of the head count and node GPU count.

Part 11 — Prefix caching, disaggregation & advanced tricks ▲ PROD

Prefix caching (automatic prefix sharing)

Many requests share a common prefix — a long system prompt, a few-shot template, or a RAG document reused across questions. Prefix caching stores the KV cache of that shared prefix and reuses it, skipping redundant prefill.

10,000 requests, all with the same 2,000-token system prompt: WITHOUT prefix caching: prefill the 2,000 tokens 10,000x WITH prefix caching: prefill ONCE, reuse the cached KV blocks for all 10,000 -> massive prefill savings, lower TTFT for every request after the first. Enabled by PagedAttention's block sharing (copy-on-write). Huge win for: chatbots (fixed system prompt), RAG (reused context), agents (repeated tool/instructions preamble).

Prefill/decode disaggregation

Prefill (compute-bound) and decode (memory-bound) have opposite needs and interfere with each other on the same GPU. Disaggregation runs them on separate GPU pools, each tuned for its phase, transferring the KV cache between them.

prompt -> [ PREFILL pool ] -- KV cache transfer --> (compute-optimized) [ DECODE pool ] big parallel pass (bandwidth-optimized) streams out tokens + each phase scales independently, no interference + better TTFT (prefill not blocked by decodes) AND better TPOT (decode not stalled by big prefills) - adds complexity + KV transfer cost. Used at large scale (e.g. DeepSeek, modern vLLM/Dynamo deployments).

Other production tricks

  • Response caching — cache full responses for identical (or semantically similar) requests; the cheapest token is the one you never generate.
  • Structured/constrained decoding — mask invalid tokens to force JSON/grammar; guarantees parseable output and can speed sampling.
  • CUDA graphs — capture the decode step as a graph to remove per-step kernel-launch overhead (big for small batches).
  • Multi-LoRA serving — host one base model + many small LoRA adapters, swapping adapters per request (S-LoRA) instead of one model per fine-tune.
  • Continuous KV offloading — spill cold KV blocks to CPU/NVMe to extend effective capacity.
Multi-LoRA is an underrated cost win If you serve many fine-tuned variants, don't run a separate replica per variant. Serve one base model and load lightweight LoRA adapters per request. Engines like vLLM (S-LoRA) batch requests across different adapters on the same base weights — dramatically cutting GPU count when you have many fine-tunes (common in multi-tenant SaaS).

Part 13 — Metrics, SLOs & benchmarking ★ CORE

You can't optimize what you don't measure. These are the metrics every serving discussion uses — know them precisely.

The core latency metrics

Goodput — the metric that matters

Raw throughput is misleading: you can push huge batches that maximize tokens/sec but blow your latency SLO, making most of that throughput useless to users. Goodput = requests/sec that meet your latency targets. Optimize for goodput, not raw throughput.

Always report percentiles

p50 (median): typical experience p95 / p99: the tail — what your unlucky users feel p999: worst case, matters at scale Averages hide the tail. A p50 of 200ms with a p99 of 5s means 1 in 100 requests is painful. SLOs are set on p95/p99.
Benchmark with realistic load, not toy prompts Numbers from a single request or fixed-length prompts are meaningless. Benchmark with: realistic input/output length distributions, your actual concurrency, and a sustained load (warm cache, steady state). Report TTFT and TPOT percentiles at a given throughput. Tools: vLLM's benchmark scripts, LLMPerf, or your own load generator replaying production traces.

Part 14 — Cost optimization & capacity planning ▲ PROD

The cost equation

$ per million tokens = (GPU $/hour) / (tokens/sec throughput x 3600 / 1e6) -> driven almost entirely by THROUGHPUT per GPU. Everything that raises tokens/sec/GPU (batching, quantization, paged KV) directly lowers $/token. Self-host break-even vs API: high, steady volume -> self-host wins (amortize GPU) low, spiky volume -> API wins (pay per token, no idle GPU cost)

Model routing / cascade

request | [ cheap small model attempts it ] | | confident? not confident / hard? | | return answer [ escalate to big model ] Most queries are easy -> served cheaply. Only the hard ~20% hit the expensive model. Big cost cut at similar quality. Pairs well with a small classifier/router.
The cheapest token is the one you never generate Before optimizing the serving stack, question the workload: do you need an LLM for this at all? Can a cached answer, a smaller model, a shorter prompt, or a deterministic rule handle it? Right-sizing the model to the task usually beats every low-level kernel optimization. Then layer on batching, quantization, and caching.

Part 15 — Autoscaling, routing & production patterns ▲ PROD

The serving architecture

clients | [ API gateway ] auth, rate limit, quota | [ router / LB ] model routing, least-load, | session affinity for prefix cache +--------+--------+--------+ | replica | replica | replica | each = engine (vLLM) |(GPU pool)|(GPU pool)|(GPU pool)| + continuous batching +--------+--------+--------+ | [ KV cache / prefix cache, model registry ] | [ metrics: TTFT/TPOT/throughput/queue depth -> autoscaler ]

Autoscaling LLMs is different

Problems unique to LLM autoscaling: - cold start is SLOW: loading a 70B model = minutes (download + load to HBM) -> can't scale instantly - GPUs are scarce & expensive -> scale-to-zero is risky - the right signal isn't CPU; use QUEUE DEPTH, batch fullness, TTFT, or tokens/sec per replica Mitigations: - keep a warm pool / min replicas to absorb spikes - pre-load models; snapshot/fast-load weights - scale on queue depth or pending tokens, not CPU - separate pools per model size

Routing strategies

  • Least-load / least-queued — send to the replica with the shortest queue (avoid head-of-line blocking).
  • Prefix-aware routing — route requests sharing a prefix (same system prompt/session) to the same replica to hit its prefix cache.
  • Model-based routing — route by required model/size; cheap vs expensive pools.
  • Priority queues — interactive traffic preempts batch traffic.

Reliability patterns (same as any service, plus LLM specifics)

  • Timeouts + retries with backoff; cap max output tokens to bound worst-case latency.
  • Fallback to a smaller model or cached response under overload (graceful degradation).
  • Load shedding / admission control when queues exceed SLO — reject early rather than melt down.
  • Circuit breakers around model backends; health checks that actually run a tiny inference.
The cold-start trap Unlike stateless web apps, you cannot autoscale LLM replicas in seconds — loading tens of GBs of weights into GPU memory takes minutes. If you scale reactively on a traffic spike, the new replicas arrive too late. Provision a warm baseline, scale on leading indicators (queue depth, pending tokens), and use load shedding to protect SLOs while new capacity spins up.

Part 16 — Interview cheat sheet & numbers to know

The 60-second framework for "optimize this LLM service"

  1. Clarify the goal — latency-sensitive (chat) or throughput/cost (batch)? What's the SLO (TTFT/TPOT)? Scale (QPS, context length)?
  2. Right-size the model — smallest model/quantization that meets quality. Consider routing/cascade.
  3. Fix the memory — PagedAttention, GQA, KV/weight quantization → bigger batches.
  4. Maximize the batch — continuous batching + chunked prefill for goodput.
  5. Cut redundant work — prefix caching, response caching.
  6. Latency tricks — speculative decoding (low batch), FlashAttention, CUDA graphs, streaming.
  7. Scale out — TP within node, PP across nodes, DP for replicas; disaggregate prefill/decode at scale.
  8. Operate it — autoscale on queue depth, warm pools, load shedding, percentile SLOs.

The soundbites that signal seniority

  • "Decode is memory-bandwidth-bound, so batching amortizes the weight read across requests — that's why throughput scales nearly for free until you hit the compute ceiling or run out of KV cache."
  • "PagedAttention is OS-style paging for the KV cache; it kills fragmentation and enables prefix sharing."
  • "Continuous batching schedules at the token level, not the request level, so the GPU never waits on the longest sequence."
  • "Speculative decoding spends idle compute to cut sequential steps — great at low batch, lossless, diminishing returns when compute-bound."
  • "Optimize for goodput, not raw throughput — tokens/sec that miss the SLO don't count."
  • "Prefill and decode have opposite resource profiles; disaggregating them lets each scale independently."
Final advice The whole field reduces to one chain of reasoning: decode is memory-bound → so read fewer bytes (quantize, smaller model, GQA) and reuse each read (batch, cache). Memory is the constraint → so manage the KV cache ruthlessly (PagedAttention, prefix caching, KV quant). Then scale out with the right parallelism and operate for percentile SLOs and goodput. If you can derive each optimization from "decode is memory-bandwidth-bound," you'll handle any inference question they throw at you.
End of LLM inference & serving guide. The engines and exact numbers evolve fast — but the underlying physics (memory bandwidth, the KV cache, the prefill/decode split) is stable. Master the reasoning, not just the tool names.
