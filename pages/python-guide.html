Part 0 — Setup, running code, the mental model BASIC

Python is an interpreted, dynamically typed, garbage-collected language. You write .py files and run them with the interpreter. Everything in Python is an object — numbers, functions, classes, even modules.

Running Python

python script.py          # run a file
python -m module_name     # run a module
python                    # interactive REPL
python -c "print(2+2)"    # one-liner

Virtual environments (always use one per project)

python -m venv .venv          # create
source .venv/bin/activate     # activate (macOS/Linux)
pip install requests          # install into the venv
pip freeze > requirements.txt # snapshot deps
deactivate                    # leave the venv
Why virtual environments matter They isolate each project's dependencies so version conflicts can't happen across projects. Never pip install into the system Python. Modern alternatives like uv and poetry manage this for you and are worth adopting.

The mental model: names point to objects

A variable in Python is a name bound to an object, not a box holding a value. Assignment binds a name; it never copies. This explains most "surprising" behavior later (mutable defaults, aliasing).

x = [1, 2, 3] y = x # y points to the SAME list y.append(4) print(x) # [1, 2, 3, 4] -- both names see it x ──┐ ├──> [1, 2, 3, 4] y ──┘

Mutable vs immutable — the dividing line

This single distinction underlies a huge share of Python bugs. Immutable objects (int, float, str, tuple, frozenset) can never change after creation — "modifying" one actually makes a new object. Mutable objects (list, dict, set, most class instances) can change in place, and every name pointing at them sees the change.

IMMUTABLE (int): MUTABLE (list): a = 5 a = [1, 2] b = a a──>5 b──>5 b = a a──┐ b = b + 1 ├──>[1, 2] b now ──>6, a still ──>5 b.append(3) b──┘ (a brand-new int object) a is now [1,2,3] too! (same object mutated)
ImmutableMutable
int, float, bool, complexlist
str, bytesdict
tuple, frozensetset
Nonemost custom class instances
Why this matters everywhere Only immutable objects can be dict keys or set members (they need a stable hash). Passing a mutable object to a function lets the function change your original. And the infamous mutable-default-argument bug (Part 5) is a direct consequence of this model.

Part 2 — Strings BASIC

Strings are immutable sequences of Unicode characters. Any operation that "changes" a string returns a new one.

f-strings (the modern way to format)

name, score = "Ada", 97.5
f"{name} scored {score:.1f}%"      # 'Ada scored 97.5%'
f"{score:>10}"                     # right-align in 10 cols
f"{1000000:,}"                     # '1,000,000'
f"{x=}"                            # 'x=42'  debug form (3.8+)

Essential string methods

s.strip()             # trim whitespace (lstrip/rstrip variants)
s.lower() / s.upper()
s.split(",")          # -> list of parts
",".join(parts)       # list -> string
s.replace("a", "b")
s.startswith("http")  # also endswith
s.find("x")           # index or -1
"x" in s              # membership
s.zfill(5)            # pad with zeros
s.encode("utf-8")     # str -> bytes

Slicing (works on any sequence)

s = "abcdef"
s[1:4]      # 'bcd'   [start:stop)
s[:3]       # 'abc'
s[3:]       # 'def'
s[::-1]     # 'fedcba'  reverse
s[::2]      # 'ace'    every other char
Build strings with join, not += Repeated s += piece in a loop is O(n²) because each step copies the whole string. Collect pieces in a list and "".join(pieces) at the end — O(n).

Part 3 — Collections: list, tuple, set, dict BASIC

The four core containers

TypeOrderedMutableUse for
listYesYesOrdered sequence, may change
tupleYesNoFixed record, dict key
setNoYesUniqueness, fast membership
dictYes*YesKey → value mapping

*Dicts preserve insertion order since Python 3.7.

Which container should I use?

Do you map keys to values? | +-- YES ----------------------------> dict {k: v} | +-- NO: do you need only unique items | with fast "is it in here?" tests? | | | +-- YES -----------------> set {a, b, c} | +-- NO: will the contents change after creation? | +-- YES (add/remove/sort) -> list [a, b, c] | +-- NO (fixed, hashable) --> tuple (a, b, c)

The mutability and ordering columns drive the choice. Need O(1) "have I seen this?" → set. Need a key the dict can hash → tuple, never list. Need order plus the ability to grow → list.

Flexible arguments

Return values & multiple returns

The mutable default argument trap Never write def f(items=[]):. The default list is created once and shared across all calls. Use the sentinel pattern instead: 
def f(items=None):
    if items is None:
        items = []

Lambdas (small anonymous functions)

sorted(words, key=lambda w: len(w))
nums.sort(key=lambda x: (x % 2, x))   # even-odd then value

Use lambdas only for tiny one-liners passed as arguments. For anything longer, define a named function.

Scope: how Python resolves a name (LEGB)

When you reference a name, Python searches four scopes in order — Local, Enclosing, Global, Built-in — and stops at the first match. Understanding this order explains why functions can read outer variables but need global/nonlocal to rebind them.

+-----------------------------------+ | Built-in (print, len, range) | | +-----------------------------+ | | | Global (module-level) | | | | +-----------------------+ | | | | | Enclosing (outer fn) | | | | | | +-----------------+ | | | | | | | Local (this fn) | | | | | | | +-----------------+ | | | | | +-----------------------+ | | | +-----------------------------+ | +-----------------------------------+ Lookup searches inside-out: L -> E -> G -> B. First match wins. Assignment creates a LOCAL name unless you declare 'global x' or 'nonlocal x'.
count = 0                 # global

def outer():
    n = 10                # enclosing (relative to inner)
    def inner():
        nonlocal n        # rebind the enclosing n
        n += 1
    inner()
    return n              # 11

Part 6 — Comprehensions & generators INTERMEDIATE

Comprehensions build collections concisely and are faster than equivalent loops.

How to read a comprehension

A comprehension packs a loop, an optional filter, and a transformation into one expression. Read it as "give me expression for each item in iterable where condition." It maps directly onto the equivalent for loop:

[ x*x for x in range(10) if x % 2 == 0 ] \_/ \______________/ \__________/ transform what to loop filter (output) over (keep when true) equivalent loop: result = [] for x in range(10): # the "for" part if x % 2 == 0: # the "if" part result.append(x*x) # the transform/output
# List comprehension
squares = [x*x for x in range(10)]

# With a filter
evens = [x for x in range(20) if x % 2 == 0]

# Nested
pairs = [(i, j) for i in range(3) for j in range(3)]

# Dict comprehension
sq_map = {x: x*x for x in range(5)}

# Set comprehension
unique_lengths = {len(w) for w in words}

Generator expressions (lazy, memory-efficient)

# Parentheses instead of brackets -> a generator
gen = (x*x for x in range(1_000_000))   # nothing computed yet
total = sum(x*x for x in range(1_000_000))  # streamed, low memory
List vs generator Use a list comprehension when you need the whole collection (indexing, reuse, length). Use a generator when you iterate once and want to avoid building a big list in memory — ideal for large or infinite streams and pipelines.

Generator functions with yield

A generator function looks like a normal function but uses yield. Calling it doesn't run the body — it returns a generator object that runs lazily, pausing at each yield and resuming where it left off on the next request. State is preserved between resumes automatically.

def countdown(n): while n > 0: yield n <-- execution PAUSES here, hands out n n -= 1 resumes here on next iteration for x in countdown(3): print(x) next() -> run until yield -> 3 (paused, n=3) next() -> resume, n=2, yield -> 2 (paused) next() -> resume, n=1, yield -> 1 (paused) next() -> resume, n=0, loop ends -> StopIteration Only one value exists in memory at a time, not the whole sequence -- this is why generators scale to huge or infinite streams.
def countdown(n):
    while n > 0:
        yield n            # pauses here, resumes on next()
        n -= 1

for x in countdown(3):     # 3, 2, 1
    print(x)

The __main__ guard

def main():
    ...

if __name__ == "__main__":
    main()      # runs only when executed directly,

Why the guard matters When a module is imported, all top-level code runs. The if __name__ == "__main__" block lets a file double as both an importable module and a runnable script without side effects on import.

Part 8 — Errors & exceptions INTERMEDIATE

An exception interrupts normal flow and "propagates up" the call stack until something catches it. If nothing does, the program crashes with a traceback. The try/except block lets you intercept and handle specific failures.

flow through try/except/else/finally: try: risky() ----+------ no error -----+ | | error raised v | else: v (runs only if except ValueError: no exception) (matching handler runs) | | | +----------+-----------+ | v finally: (ALWAYS runs -- cleanup, close files, release locks)
try:
    result = risky()
except ValueError as e:
    print(f"bad value: {e}")
except (KeyError, IndexError):
    handle_lookup_error()
else:
    print("no exception occurred")
finally:
    cleanup()        # always runs

The exception hierarchy

Exceptions form a class tree. Catching a parent type also catches its children, which is why catching Exception is so broad and bare except: (which catches even SystemExit) is dangerous.

BaseException ├── SystemExit, KeyboardInterrupt (don't usually catch these) └── Exception (catch THIS or narrower) ├── ArithmeticError │ └── ZeroDivisionError ├── LookupError │ ├── KeyError │ └── IndexError ├── ValueError ├── TypeError └── OSError (FileNotFoundError, ...) Catching ValueError also catches its subclasses. Catch the most specific type you can handle.

Raising and custom exceptions

raise ValueError("amount must be positive")

class InsufficientFundsError(Exception):
    """Raised when an account lacks funds."""
    pass

raise InsufficientFundsError("balance too low")

Exception chaining and groups

try:
    parse()
except ValueError as e:
    raise RuntimeError("parse failed") from e   # preserves cause
Catch narrowly, fail loudly Avoid bare except: — it swallows KeyboardInterrupt and hides bugs. Catch the specific exceptions you can handle. "Ask forgiveness, not permission" (EAFP) is Pythonic: try the operation and handle the exception rather than checking preconditions everywhere.

Part 9 — Files, context managers & I/O INTERMEDIATE

Reading and writing

The with statement is the right way to handle files (and any resource that must be released). It guarantees the file is closed even if an exception fires inside the block — no leaked file handles.

with open("data.txt") as f: data = f.read() ... what happens under the hood: f = open(...) # __enter__: acquire the resource try: data = f.read() # your block runs ... finally: f.close() # __exit__: ALWAYS release, # even if the block raised Resource is guaranteed closed. No "forgot to close" bugs.
# Always use 'with' -- it auto-closes the file
with open("data.txt", "r", encoding="utf-8") as f:
    content = f.read()          # whole file
    # or iterate lines lazily:
with open("data.txt") as f:
    for line in f:              # memory-friendly
        process(line.rstrip())

with open("out.txt", "w", encoding="utf-8") as f:
    f.write("hello\n")

Modern path handling with pathlib

from pathlib import Path
p = Path("data") / "file.txt"   # OS-agnostic join
p.exists()
p.read_text(encoding="utf-8")
p.write_text("hi")
for f in Path(".").glob("*.py"):
    print(f.name)

Structured formats

text = json.dumps(data, indent=2)

Writing your own context manager

from contextlib import contextmanager

@contextmanager
def timer():
    import time
    start = time.perf_counter()
    yield                         # body runs here
    print(f"took {time.perf_counter() - start:.3f}s")

with timer():
    do_work()

Part 10 — Object-oriented programming INTERMEDIATE

A class is a blueprint; an instance is a concrete object built from it. Class attributes are shared by all instances; instance attributes belong to one object. Methods are functions that take the instance (self) as their first argument.

class Account <- the blueprint +-------------------+ | bank = "ACME" | <- class attribute (shared) | __init__() | | deposit() | <- methods +-------------------+ | instances (each has its own data): +------------------+ +------------------+ | a1 | | a2 | | owner = "Ada" | | owner = "Lin" | | balance = 100 | | balance = 50 | | bank -> "ACME" --+---+-> shared via class| +------------------+ +------------------+
class Account:
    bank = "ACME"                 # class attribute (shared)

    def __init__(self, owner, balance=0):
        self.owner = owner        # instance attribute
        self.balance = balance

    def deposit(self, amount):    # instance method
        self.balance += amount
        return self.balance

    def __repr__(self):           # developer-friendly string
        return f"Account({self.owner!r}, {self.balance})"

Inheritance & super()

A subclass inherits everything from its parent and can add or override behavior. super() calls the parent's version of a method — essential in __init__ so the parent can set up its part of the object before you add yours.

Account (base / parent) | owner, balance, deposit() | | inherits everything v SavingsAccount (subclass / child) | + rate | + add_interest() | reuses deposit() from Account isinstance(savings, Account) -> True a "SavingsAccount" IS-A "Account"
class SavingsAccount(Account):
    def __init__(self, owner, balance=0, rate=0.02):
        super().__init__(owner, balance)
        self.rate = rate

    def add_interest(self):
        self.deposit(self.balance * self.rate)

Method types

class C:
    @staticmethod
    def helper(x):            # no self/cls, just namespaced
        return x * 2

    @classmethod
    def from_string(cls, s):  # alternative constructor
        return cls(*s.split(","))

    @property
    def computed(self):       # access like an attribute
        return self._x * 2

Dataclasses (less boilerplate)

from dataclasses import dataclass, field

@dataclass
class Point:
    x: float
    y: float = 0.0
    tags: list = field(default_factory=list)

p = Point(3, 4)        # auto __init__, __repr__, __eq__
Dunder methods make objects feel native Implement __len__, __getitem__, __eq__, __lt__, __iter__ and your objects work with len(), indexing, comparisons, sorting, and for loops. This is "duck typing" via the data model.

Part 11 — Iterators, generators & the data model ADVANCED

The for loop is sugar over the iterator protocol. Understanding it unlocks lazy pipelines and custom iterable objects.

Iterable vs iterator

  • An iterable has __iter__() that returns an iterator (lists, strings, dicts).
  • An iterator has __next__() that yields the next item or raises StopIteration.

A for loop is just sugar over this protocol. It calls iter() once to get an iterator, then calls next() repeatedly until StopIteration signals the end:

for x in [10, 20, 30]: print(x) is really: it = iter([10, 20, 30]) # __iter__() -> iterator while True: try: x = next(it) # __next__() -> 10, 20, 30 except StopIteration: # raised when exhausted break print(x) iterable --iter()--> iterator --next()--> values... (can ask (knows its until for a fresh current StopIteration iterator) position)
it = iter([1, 2, 3])
next(it)        # 1
next(it)        # 2

class Countdown:
    def __init__(self, n): self.n = n
    def __iter__(self): return self
    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1

Generators are iterators you get for free

# Infinite generator -- only computes what's consumed
def naturals():
    n = 1
    while True:
        yield n
        n += 1

import itertools
first_five = list(itertools.islice(naturals(), 5))  # [1,2,3,4,5]

itertools — the lazy toolkit

itertools.chain(a, b)          # concatenate iterables
itertools.count(10, 2)         # 10, 12, 14, ...
itertools.cycle("AB")          # A B A B ...
itertools.groupby(sorted_data, key)
itertools.combinations(x, 2)
itertools.product(a, b)        # cartesian product
itertools.accumulate(nums)     # running totals

Part 12 — Decorators & closures ADVANCED

A closure is a function that captures variables from its enclosing scope. A decorator is a function that takes a function and returns a modified function — used to add behavior without changing the original.

What @decorator really does

The @ syntax is pure sugar. @log_calls above a function definition simply reassigns the name to the decorated version. The decorator wraps the original in an outer function that runs extra code before and after calling it.

@log_calls def add(a, b): return a + b is exactly: add = log_calls(add) The wrapper "surrounds" the original: call add(2, 3) | v +--------------------------------+ | wrapper | | print("calling add") <-- before | result = add(2, 3) ---> runs original -> 5 | print("-> 5") <-- after | return result | +--------------------------------+ | v you get 5, plus the logging side effects

Closure

def make_multiplier(factor):
    def multiply(x):
        return x * factor     # captures 'factor'
    return multiply

triple = make_multiplier(3)
triple(10)                    # 30

A basic decorator

import functools

def log_calls(func):
    @functools.wraps(func)        # preserves name/docstring
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__}")
        result = func(*args, **kwargs)
        print(f"  -> {result}")
        return result
    return wrapper

@log_calls
def add(a, b):
    return a + b

add(2, 3)     # logs the call, returns 5

Decorators with arguments

def retry(times):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except Exception:
                    if attempt == times - 1:
                        raise
        return wrapper
    return decorator

@retry(times=3)
def flaky():
    ...

Decorators you'll see often

  • @functools.lru_cache — memoize results
  • @functools.cached_property — compute once, store
  • @property / @staticmethod / @classmethod
  • @dataclass
  • @app.route(...) in web frameworks
Always use @functools.wraps Without it, the wrapped function loses its name, docstring, and signature, which breaks introspection, debugging, and documentation tools.

Part 14 — Type hints & static typing ADVANCED

Type hints don't affect runtime behavior, but they document intent and let tools like mypy or pyright catch bugs before you run the code.

def greet(name: str, times: int = 1) -> str:
    return (f"Hi {name}! " * times).strip()

# Modern syntax (3.10+)
def parse(data: str | None) -> list[int]:
    ...

from typing import Optional, Union, Any, Callable

scores: dict[str, list[float]] = {}
handler: Callable[[int, str], bool]
maybe: Optional[int] = None          # same as int | None

Useful typing constructs

from typing import TypedDict, Protocol, Literal, TypeVar, Generic

class User(TypedDict):
    name: str
    age: int

Mode = Literal["r", "w", "a"]        # restrict to these values

T = TypeVar("T")
def first(items: list[T]) -> T:
    return items[0]

class Comparable(Protocol):          # structural typing
    def __lt__(self, other) -> bool: ...
Adopt typing incrementally You don't need to annotate everything. Start with function signatures at module boundaries and public APIs. Run mypy --strict on new code. Hints pay off most in large codebases and team settings.

Part 15 — Concurrency: threads, processes, asyncio ADVANCED

Choosing the right concurrency model is about whether your work is I/O-bound (waiting on network/disk) or CPU-bound (crunching numbers).

I/O-bound vs CPU-bound — the deciding question

If your program spends most of its time waiting (network calls, disk reads, database queries), it's I/O-bound — concurrency helps because you can wait on many things at once. If it spends its time computing (math, parsing, image processing), it's CPU-bound — you need real parallelism across CPU cores.

I/O-BOUND (waiting dominates): task A: |--wait for network--| task B: |--wait for disk--| overlap the WAITS task C: |--wait for db--| -> threads / asyncio Total time shrinks: waits happen concurrently. CPU-BOUND (computing dominates): task A: |####compute####| task B: |####compute####| GIL serializes threads DON'T help -- only one runs Python at a time. Use multiple PROCESSES to use multiple cores: core1: |####A####| core2: |####B####| truly parallel -> faster

The GIL in one paragraph

CPython has a Global Interpreter Lock: only one thread executes Python bytecode at a time. So threads give no speedup for CPU-bound work, but they're great for I/O-bound work because the GIL is released while waiting. For CPU parallelism, use multiple processes. (Free-threaded builds removing the GIL are emerging in 3.13+, but the GIL is still the default model to reason about.)

WorkloadUse
I/O-bound, many tasksasyncio or threads
CPU-boundmultiprocessing / ProcessPoolExecutor
Mixed / simple parallel callsconcurrent.futures

Threads & processes via the same API

from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

with ThreadPoolExecutor(max_workers=8) as ex:   # I/O-bound
    results = list(ex.map(fetch_url, urls))

with ProcessPoolExecutor() as ex:               # CPU-bound
    results = list(ex.map(heavy_compute, chunks))

asyncio — single-threaded cooperative concurrency

import asyncio

async def fetch(session, url):
    async with session.get(url) as resp:
        return await resp.text()

async def main(urls):
    async with aiohttp.ClientSession() as session:
        tasks = [fetch(session, u) for u in urls]
        return await asyncio.gather(*tasks)   # concurrent

asyncio.run(main(urls))
Don't block the event loop In async code, a synchronous CPU-heavy call or a blocking time.sleep() freezes all tasks. Use await asyncio.sleep() and offload CPU work to a process pool with loop.run_in_executor.

Practical speed wins

  • Use built-ins (sum, map, sorted) — they run in C.
  • Prefer comprehensions/generators over manual loops.
  • Use set/dict for membership instead of list.
  • Hoist invariant work out of loops; cache attribute lookups locally.
  • For numeric work, use numpy — vectorized, C-backed.
  • Memoize pure functions with functools.lru_cache.

Memory tools

import sys
sys.getsizeof(obj)            # shallow size in bytes

# __slots__ removes per-instance __dict__, saving memory
class Point:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y
Optimize the right thing Profile first — intuition about bottlenecks is usually wrong. Most slowdowns come from a small fraction of the code (or from O(n²) algorithms, not constant factors). Improving the algorithm beats micro-optimizing nearly every time.
