Part 0 — The interview framework ★ CORE

A system design interview is open-ended on purpose. The interviewer wants to see how you think, not a memorized answer. The biggest mistake is jumping straight to boxes and arrows. Drive the conversation with a repeatable framework so you never freeze.

The RESHADED-style flow (use this every time)

  1. Requirements — clarify functional & non-functional needs. Never skip this.
  2. Estimate — back-of-envelope scale: users, QPS, storage, bandwidth.
  3. API design — define the key endpoints / contracts.
  4. Data model — what entities, what storage.
  5. High-level design — the box-and-arrow diagram.
  6. Deep dive — pick the 1–2 hardest components and detail them.
  7. Bottlenecks & scale — find the weak points, fix with caching/sharding/replication.
  8. Wrap up — trade-offs, what you'd monitor, what you'd do with more time.
TIME BUDGET for a 45-min interview: Requirements |####| ~5 min Estimation |##| ~3 min API + data |###| ~5 min High-level |######| ~10 min Deep dive |#########| ~15 min Scale/wrap |####| ~7 min +-----------------------------------> Don't spend 20 minutes on requirements, and don't start drawing before you know what you're building.

Step 1: nail the requirements

Spend the first few minutes asking questions. This shows seniority and stops you building the wrong thing.

  • Functional: What must it do? (e.g., "post a tweet, follow users, view a feed")
  • Non-functional: How well? (availability, latency, consistency, scale)
  • Scope: What's explicitly out of scope? Lock it down so you don't sprawl.
  • Scale: How many users? Read-heavy or write-heavy? Global or regional?
The read/write ratio drives everything Ask early: is this read-heavy or write-heavy? A read-heavy system (Twitter feed, ~100:1) leans on caching and read replicas. A write-heavy system (logging, metrics) leans on partitioning, write buffers, and append-only stores. State your assumption out loud and design accordingly.

Functional vs non-functional requirements

Functional (what)Non-functional (how well)
Upload a video99.9% availability
Search for a user< 200 ms p99 latency
Send a messageHandle 10k messages/sec
Process a paymentStrong consistency, no double-charge

A worked estimation: Twitter-like service

Assume:
  300M monthly active users
  50% use it daily            -> 150M daily active users (DAU)
  Each user posts 2 tweets/day

Write QPS (tweets per second):
  150M DAU * 2 tweets = 300M tweets/day
  300M / 86,400 sec   ~= 3,500 tweets/sec  (average)
  Peak ~= 2x average  ~= 7,000 tweets/sec

Read QPS (timeline views):
  Each user reads timeline ~20x/day
  150M * 20 = 3B reads/day
  3B / 86,400 ~= 35,000 reads/sec  -> READ-HEAVY (~10:1)

Storage (5 years of tweets):
  Tweet ~= 300 bytes (text + metadata)
  300M tweets/day * 365 * 5 ~= 550B tweets
  550B * 300 bytes ~= 165 TB (text only)
  Media dominates -> petabytes with images/video
Estimation shortcuts Seconds in a day ≈ 86,400 ≈ 100,000 (round up for easy math). 1 million writes/day ≈ ~12/sec. Always compute average QPS first, then multiply by 2–3× for peak. State storage in GB/TB/PB so the interviewer can sanity-check your data tier.

Part 2 — Core concepts: latency, throughput, availability ◆ CONCEPT

Latency vs throughput

They're different and often in tension. Latency is how long one request takes. Throughput is how many requests you handle per second. A highway analogy: latency is how long your car takes to travel the road; throughput is how many cars pass per minute. Adding lanes (parallelism) raises throughput without lowering any single car's travel time.

LATENCY (per request) THROUGHPUT (system-wide) request --[ 200ms ]--> resp ====> 10,000 req/sec ====> Low latency, low throughput: fast but serves few High latency, high throughput: slow each, serves many Goal: low latency AND high throughput (hard, costs money)

Measure tail latency, not averages

Averages lie. If 1% of requests take 5 seconds, the average may still look fine, but those users are furious. Use percentiles: p50 (median), p95, p99, p999. The "tail" (p99+) is what users remember and what cascades into outages.

latency distribution: count |#### |###### |######## |######### p50 = 80ms (typical) |####### ## p95 = 250ms |##### # # p99 = 600ms <- the tail |### # # # p999 = 2s <- worst 0.1% +----------------------------> latency A few slow requests don't move the average much but ruin the experience for many users at scale.

Availability: the nines

AvailabilityDowntime / yearDowntime / day
99% (two nines)3.65 days14.4 min
99.9% (three nines)8.77 hours1.44 min
99.99% (four nines)52.6 min8.6 sec
99.999% (five nines)5.26 min0.86 sec

Each additional nine costs roughly an order of magnitude more in engineering effort. Components in series multiply: two 99.9% services in a chain give 99.9% × 99.9% ≈ 99.8%. Redundancy in parallel improves availability.

SLA vs SLO vs SLI An SLI (indicator) is the measured metric (e.g., % of requests under 300ms). An SLO (objective) is your internal target (99.9%). An SLA (agreement) is the contractual promise to customers, usually looser than the SLO, with penalties if breached.

Part 3 — The CAP theorem & consistency models ◆ CONCEPT

The CAP theorem says a distributed system can guarantee only two of these three during a network partition:

  • Consistency — every read sees the most recent write (or an error).
  • Availability — every request gets a (non-error) response.
  • Partition tolerance — the system keeps working despite dropped network messages.

In the real world networks do partition, so P is non-negotiable. The real choice is C vs A when a partition happens.

Network partition splits the cluster: Node A X---X Node B (can't talk) | | client1 client2 CP choice (consistency): refuse writes on the minority side so data never diverges. -> some requests fail. Examples: traditional RDBMS, HBase, MongoDB(default), ZooKeeper, etcd. AP choice (availability): accept writes on both sides, reconcile later. -> always answers, may serve stale. Examples: Cassandra, DynamoDB, Riak, CouchDB.

The consistency spectrum

"Consistency" isn't binary. From strongest to weakest:

ModelGuaranteeUse case
Strong / linearizableReads always see latest writeBank balance, locks
Read-your-writesYou see your own updatesProfile edits
Monotonic readsNever go backwards in timeTimelines
EventualConverges if writes stopDNS, likes count, feeds
PACELC: the fuller picture CAP only describes behavior during a partition. PACELC adds: else (when running normally), you still trade Latency vs Consistency. Strong consistency requires coordination (more latency); eventual consistency is faster but stale. Most systems tune this per-operation.

Part 4 — Networking, DNS, load balancing ★ CORE

What happens when you type a URL

browser | 1. DNS lookup: example.com -> 93.184.x.x v DNS resolver --------------------> returns IP | 2. TCP handshake (SYN/SYN-ACK/ACK) + TLS v Load Balancer (the public IP) | 3. picks a healthy backend v +----------+ +----------+ +----------+ | server 1 | | server 2 | | server 3 | +----------+ +----------+ +----------+ | 4. app queries cache/DB, builds response v response travels back -> browser renders

Load balancing

A load balancer spreads traffic across servers so no single machine is overwhelmed, and routes around failed ones. It's the front door to a scalable system.

Layer 4 vs Layer 7

L4 (transport)L7 (application)
Routes by IP + portRoutes by URL, headers, cookies
Fast, protocol-agnosticSmarter, content-aware
Can't read request bodyCan do path-based routing, SSL termination

Balancing algorithms

  • Round robin — rotate through servers in order. Simple.
  • Least connections — send to the server with fewest active requests. Good for uneven workloads.
  • Weighted — bigger servers get more traffic.
  • IP hash / consistent hash — same client always hits the same server (sticky sessions).
The load balancer is a single point of failure If you have one LB, its death takes everything down. Run them in pairs (active-passive or active-active) with a floating IP and health checks. In the cloud, managed LBs (ALB/NLB, Cloud Load Balancing) handle this redundancy for you.

Stateless vs stateful servers

Prefer stateless application servers: they store no session data locally, so any server can handle any request and you can add/remove them freely. Push state to a shared store (Redis, database). Stateful servers force sticky routing and complicate scaling.

STATELESS (good): STATEFUL (avoid if possible): any server, any request session pinned to server 2 session in Redis/DB if server 2 dies -> logged out add servers freely scaling = data migration pain client client / | \ | srv1 srv2 srv3 srv2 (only) \ | / | shared session store local memory

Part 5 — Caching SCALE

A cache stores copies of data closer to where it's needed so you avoid slow recomputation or database hits. Caching is the single highest-leverage scaling technique for read-heavy systems. The principle: most systems access a small "hot" subset of data far more often than the rest (the 80/20 rule).

Where caches live (closest to farthest from the user)

browser cache (user's device, fastest) | CDN edge cache (geographically near user) | load balancer / reverse proxy cache | application in-memory cache (local to server) | distributed cache (Redis / Memcached cluster) | database (the source of truth, slowest) Each layer absorbs reads so fewer requests reach the DB.

Cache reading strategies

PatternHow it worksTrade-off
Cache-aside (lazy)App checks cache; on miss, reads DB and populates cacheMost common; first request is slow, possible staleness
Read-throughCache itself loads from DB on missSimpler app code; needs cache library support
Write-throughWrite to cache and DB together, synchronouslyCache always fresh; slower writes
Write-backWrite to cache, flush to DB later (async)Fast writes; risk of data loss on crash

Cache-aside, step by step (the default you should describe)

READ: 1. app asks cache for key 2. HIT -> return cached value (fast path) MISS -> read from DB -> write value into cache (with TTL) -> return value WRITE: 1. write to DB 2. invalidate (delete) the cache key (next read repopulates it) client --> [cache] --hit--> done |miss v [database] --> backfill cache

Eviction policies

A cache has limited memory, so when full it must evict something:

  • LRU (least recently used) — evict what hasn't been touched longest. Most common default.
  • LFU (least frequently used) — evict the least-accessed item.
  • FIFO — evict oldest inserted. Simple but ignores access patterns.
  • TTL — every entry expires after a fixed time, independent of the above.
The three cache failure modes
  • Cache penetration — queries for keys that don't exist bypass the cache and hammer the DB. Fix: cache "null" results or use a bloom filter.
  • Cache avalanche — many keys expire at once, flooding the DB. Fix: jitter the TTLs.
  • Cache stampede — a hot key expires and thousands of requests rebuild it simultaneously. Fix: locking / single-flight so only one request recomputes.
Cache invalidation is hard "There are only two hard things in computer science: cache invalidation and naming things." Stale data is the cost of caching. Decide your tolerance: a likes counter can be seconds stale; a bank balance cannot. Use TTLs for bounded staleness and explicit invalidation on writes for correctness.

Part 6 — Databases: SQL vs NoSQL ★ CORE

Choosing the right datastore is often the most consequential design decision. There's no universally "better" option — it depends on your access patterns, consistency needs, and scale.

SQL (relational)

Data in tables with fixed schemas and relationships. Strong consistency, powerful queries via joins, and ACID transactions. Scales up (bigger machine) more easily than out. Examples: PostgreSQL, MySQL.

NoSQL (non-relational)

Flexible schema, designed to scale out horizontally. Trades joins and strong consistency for throughput and availability. Four main families:

TypeModelExamplesGood for
Key-valuekey → blobRedis, DynamoDBCaching, sessions
DocumentJSON documentsMongoDB, CouchbaseFlexible records, catalogs
Wide-columnrows with dynamic columnsCassandra, HBaseTime-series, huge write volume
Graphnodes + edgesNeo4j, NeptuneSocial graphs, recommendations

ACID vs BASE

ACID (SQL) BASE (NoSQL) ------------------- ---------------------- Atomicity Basically Available Consistency Soft state Isolation Eventual consistency Durability "All-or-nothing, always "Stay up and fast, correct" -> safety converge later" -> scale

How to choose (say this in the interview)

Choose SQL when…Choose NoSQL when…
Complex queries & joinsSimple key-based access at scale
Strong consistency / transactions (payments)Massive write throughput
Well-defined, stable schemaFlexible / evolving schema
Moderate scale fits one big box (+ replicas)Need horizontal scale across many nodes
"It depends" — but justify it Don't just say SQL or NoSQL. Tie it to access patterns: "Reads are key-lookups by user_id at very high QPS with flexible fields, so a key-value/document store fits. But the payments piece needs ACID, so I'll keep that in Postgres." Polyglot persistence — different stores for different needs — is a strong senior answer.

Indexes: the read/write trade-off

An index is a sorted lookup structure (usually a B-tree) that turns an O(n) table scan into an O(log n) lookup. The cost: every write must also update the index, and indexes consume storage. Index the columns you filter/sort on; don't index everything.

Without index: WHERE email = 'x' -> scan all N rows O(N) With B-tree index on email: -> tree descent O(log N) [m] / \ [d] [t] find 'email' by descending / \ / \ the sorted tree, not scanning ... leaves point to rows ...

Part 7 — Replication & partitioning (sharding) SCALE

Two distinct techniques, often confused. Replication = copies of the same data for redundancy and read scaling. Partitioning (sharding) = splitting different data across machines for write scaling and capacity.

Replication

PRIMARY-REPLICA (a.k.a. master-slave): writes | v +---------+ replicate +---------+ +---------+ | PRIMARY | -------------> | REPLICA | | REPLICA | +---------+ +---------+ +---------+ ^ ^ ^ writes reads reads Writes go to primary; reads fan out to replicas. Great for READ-HEAVY systems. Replicas can lag slightly (replication lag) -> reads may be momentarily stale.
ModeBehaviorTrade-off
SynchronousPrimary waits for replica to confirmNo data loss, higher write latency
AsynchronousPrimary replies before replicas catch upFast writes, risk of losing recent writes on failover

Multi-primary / leaderless setups (e.g., Cassandra, Dynamo) accept writes anywhere and reconcile conflicts (last-write-wins, vector clocks, or quorum reads/writes: R + W > N).

Partitioning (sharding)

When data or write volume exceeds one machine, split it. Each shard holds a subset and runs independently.

All users (too big for one DB): +------------------------------------------+ | user 1 ... user 100,000,000 | +------------------------------------------+ | shard by user_id +-----------+-----------+ v v v +--------+ +--------+ +--------+ | shard0 | | shard1 | | shard2 | | users | | users | | users | | 0-33M | | 33-66M | | 66-100M| +--------+ +--------+ +--------+

Sharding strategies

StrategyHowRisk
Range-basedSplit by key ranges (A–M, N–Z)Hot spots if data skews to one range
Hash-basedhash(key) % N picks shardEven spread, but resharding moves most data
Consistent hashingKeys + nodes on a hash ringAdding a node moves only ~1/N of keys
Directory-basedLookup table maps key → shardFlexible, but the directory is a bottleneck/SPOF

Consistent hashing (the interview favorite)

Naive hash(key) % N breaks when N changes — almost every key moves to a new shard. Consistent hashing places both keys and nodes on a circular hash ring; each key belongs to the next node clockwise. Adding or removing a node only relocates the keys between it and its neighbor.

0 / 360 o Node A N_C o o key1 -> goes to Node A (next clockwise) / \ o o Node B key3 o o key2 -> goes to Node B \ / Node C o----o key... Add Node D between B and C? Only keys in that arc move. Used by: Cassandra, DynamoDB, memcached clients, CDNs.
Sharding costs you things Cross-shard joins and transactions become hard or impossible. Queries that don't include the shard key must fan out to all shards (scatter-gather). Choose a shard key that matches your most common access pattern and spreads load evenly. Avoid keys that create hot spots (e.g., sharding by timestamp for append-heavy data).

Part 8 — Messaging, queues & event streaming SCALE

Message queues decouple producers from consumers. Instead of calling a service directly and waiting, you drop a message and move on; consumers process at their own pace. This absorbs spikes, enables async work, and isolates failures.

Synchronous vs asynchronous

SYNCHRONOUS (tight coupling): client --> service A --> service B --> service C client waits for the whole chain. If C is slow, everyone waits. If C is down, the request fails. ASYNCHRONOUS (via queue): client --> service A --> [ QUEUE ] --> worker A replies immediately ("accepted"). Worker processes later. Spikes buffer in the queue. C down? messages wait safely until it recovers.

Queue vs pub/sub

Message queue (point-to-point)Pub/sub (publish-subscribe)
Each message consumed by ONE workerEach message delivered to ALL subscribers
Work distribution, task processingEvent broadcast, fan-out
e.g., SQS, RabbitMQ (work queue)e.g., SNS, Kafka topics, Redis pub/sub
QUEUE (one consumer gets each job): producer -> [ A B C D ] -> worker1 (gets A, C) -> worker2 (gets B, D) PUB/SUB (every subscriber gets every event): +-> subscriber 1 (email) publisher -> topic +-> subscriber 2 (analytics) +-> subscriber 3 (audit log)

Event streaming (Kafka model)

A log-based stream like Kafka keeps an ordered, durable, replayable record of events. Unlike a traditional queue that deletes a message once consumed, the log retains events so multiple consumers can read independently and replay history.

Kafka topic = an append-only log, split into partitions: partition 0: [e0][e1][e2][e3][e4]... (ordered) ^ ^ consumer-group-A producer appends here reads at offset 2 - Order guaranteed WITHIN a partition (not across). - Consumers track their own offset -> replay anytime. - Partitions enable parallel consumption + scale.

Delivery guarantees

  • At-most-once — may lose messages, never duplicates. (fire and forget)
  • At-least-once — never lost, but may duplicate. Most common; requires idempotent consumers.
  • Exactly-once — no loss, no dupes. Hardest and most expensive; often approximated with dedup + idempotency keys.
Design consumers to be idempotent Since at-least-once delivery can replay a message, processing it twice must be safe. Use an idempotency key (e.g., dedup on message_id) so "charge card for order 123" runs once even if delivered three times. This single habit prevents a huge class of distributed-systems bugs.
Dead letter queues A message that repeatedly fails processing shouldn't block the queue forever. After N retries, route it to a Dead Letter Queue (DLQ) for inspection. This isolates "poison" messages and keeps the main pipeline flowing.

Part 9 — Microservices, APIs & communication ◆ CONCEPT

Monolith vs microservices

A monolith is one deployable unit — simple to build and debug, but every change redeploys everything and one bug can crash the whole app. Microservices split the system into independently deployable services owned by small teams, at the cost of operational and network complexity.

MONOLITH MICROSERVICES +------------------+ +------+ +------+ +------+ | auth | orders | | auth | |orders| | pay | | pay | inventory | +------+ +------+ +------+ +------------------+ | each: own DB, one codebase, one DB | own deploy, own team one deploy +------+ simple but coupled |invtry| network calls between +------+ them -> complexity
Monolith winsMicroservices win
Small team, early stageLarge org, many teams
Simple deploymentIndependent scaling & deploys
Easy local debuggingFault isolation, tech diversity
No network overheadScale only the hot services
Start with a monolith Most successful systems begin as a well-structured monolith and extract services only when team size or scaling pain demands it. Premature microservices add distributed-systems complexity (network failures, eventual consistency, distributed tracing) before you can afford it.

API styles

StyleStrengthBest for
RESTSimple, cacheable, ubiquitousPublic CRUD APIs
GraphQLClient picks exactly the fields it needsComplex, nested data; mobile
gRPCFast binary (protobuf), streamingInternal service-to-service
WebSocketBidirectional, persistentChat, live updates, gaming

The API Gateway

A single entry point in front of many microservices. It handles cross-cutting concerns so each service doesn't have to: authentication, rate limiting, routing, request aggregation, SSL termination, and logging.

+-------------+ clients ---> | API GATEWAY | auth, rate-limit, route +-------------+ | | | +-------+ | +-------+ v v v +------+ +------+ +------+ | auth | |orders| | pay | +------+ +------+ +------+ Clients talk to ONE endpoint; the gateway fans out.

Resilience patterns for service calls

  • Timeout — never wait forever on a downstream call.
  • Retry with backoff — retry transient failures, with exponential delay + jitter (don't retry instantly in a tight loop).
  • Circuit breaker — after repeated failures, "trip" and fail fast for a while instead of hammering a dying service, then probe to recover.
  • Bulkhead — isolate resource pools so one failing dependency can't exhaust all threads.
CIRCUIT BREAKER states: CLOSED --(too many failures)--> OPEN (calls requests pass (fail fast, flow) don't even try) ^ | | | after cooldown +---(probe succeeds)-- HALF-OPEN <--+ (let a few test calls through)

Part 10 — Storage, CDN & blob systems SCALE

Storage types

TypeModelExamplesUse for
Block storageRaw volumes, like a diskEBS, attached SSDDatabases, low-level I/O
File storageHierarchical files/dirsNFS, EFSShared filesystems
Object storageFlat key → blob + metadataS3, GCS, Azure BlobMedia, backups, static assets

Object storage is the workhorse for large unstructured data (images, video, logs). It's cheap, virtually infinite, and durable (S3 advertises 11 nines of durability). You store the blob in object storage and keep only a URL/reference in your database — never store large blobs in the DB.

Content Delivery Network (CDN)

A CDN caches static content (images, CSS, JS, video) on edge servers physically close to users worldwide. Instead of every request crossing the globe to your origin, users hit a nearby edge — cutting latency dramatically and offloading your servers.

WITHOUT CDN: WITH CDN: user (Tokyo) user (Tokyo) | 150ms | 10ms v v origin (US) edge (Tokyo) -- cache hit! | (only on miss) v origin (US) Edge caches absorb most reads; origin handles misses and dynamic content. Push (preload) or pull (on-demand).
Static vs dynamic content Serve static assets from a CDN and object storage. Keep dynamic, personalized content (your feed, your cart) on application servers, but cache the static shell. Many designs win latency just by correctly separating these two.

Designing a blob upload flow (pre-signed URLs)

Don't proxy large uploads through your app servers — it wastes bandwidth and ties up workers. Instead, issue a pre-signed URL so the client uploads directly to object storage.

1. client asks app: "I want to upload photo.jpg" 2. app returns a pre-signed S3 URL (short-lived token) 3. client uploads the file DIRECTLY to S3 4. S3 notifies app (event) -> app saves the object key client ---(1 request)---> app ---(presign)---> client client ---------------(big upload)------------> S3 app's bandwidth is never touched by the file itself.

Part 11 — Consistency patterns & distributed transactions ◆ CONCEPT

When a single business operation spans multiple services or databases, you can't use one ACID transaction. You need patterns that keep data consistent across boundaries.

The dual-write problem

If you write to a database and then publish an event (or write to a second service), a crash between the two leaves the system inconsistent. The fixes below address this.

Two-phase commit (2PC)

A coordinator asks all participants to "prepare," then "commit" only if all agreed. Strong consistency, but blocking and fragile — if the coordinator dies mid-commit, participants are stuck holding locks. Rarely used at scale.

Phase 1 (prepare): coordinator -> "can you commit?" A: yes B: yes C: yes Phase 2 (commit): coordinator -> "commit!" all commit together. If ANY says no -> everyone aborts. Problem: coordinator crash = participants block. SPOF.

The Saga pattern (preferred for microservices)

Break a distributed transaction into a sequence of local transactions, each with a compensating action to undo it. If a step fails, run the compensations in reverse to roll back.

Book a trip (3 services): forward: reserve flight -> reserve hotel -> charge card OK OK FAILS! compensate: <- cancel flight <- cancel hotel <-+ Each step commits locally and emits an event that triggers the next. On failure, compensating transactions undo the prior steps. Eventually consistent.
Orchestration sagaChoreography saga
Central coordinator directs each stepServices react to each other's events
Easier to monitor & debugMore decoupled, no central point
Coordinator is a focal pointHard to track the overall flow

Outbox pattern (solving dual-write)

Write the business change and an "event to publish" into the same database transaction (the outbox table). A separate process reads the outbox and publishes to the message broker. Now the DB write and the intent-to-publish are atomic.

ONE local transaction: +-- update orders table +-- insert row into OUTBOX table (atomic together) Separate relay process: poll OUTBOX -> publish to Kafka -> mark row sent No lost events: if the order committed, the event row did too, and the relay will eventually publish it.
CQRS & event sourcing (advanced) CQRS separates the write model from the read model — you write to one optimized store and serve reads from another (often denormalized) view. Event sourcing stores the full sequence of state-changing events as the source of truth, rebuilding current state by replaying them. Powerful for audit trails and complex domains, but adds significant complexity — mention them, don't reach for them by default.

Part 12 — Reliability, observability & failure handling ★ CORE

At scale, failure is constant — disks die, networks blip, deploys go bad. Reliable systems are designed to expect failure and degrade gracefully rather than collapse.

Eliminate single points of failure (SPOF)

SPOF (one of everything): REDUNDANT (no SPOF): client client | / \ 1 LB <- dies = outage LB1 LB2 (failover) | \ / 1 server server pool (N+1) | | 1 DB <- dies = outage primary + replicas (auto-failover) Rule: for every critical component, ask "what happens when this one instance dies?"

Redundancy & failover

  • Active-passive — standby takes over when primary fails (failover delay, simpler).
  • Active-active — all instances serve traffic; failure just removes capacity (no failover gap, more complex).
  • N+1 / N+2 — provision enough spare capacity to survive 1 (or 2) node losses.

Graceful degradation

When a dependency fails, serve a reduced experience instead of an error. If the recommendation service is down, show generic popular items. If the avatar service is down, show a default avatar. The core function keeps working.

Observability: the three pillars

+-----------+ +-----------+ +-----------+ | METRICS | | LOGS | | TRACES | +-----------+ +-----------+ +-----------+ numbers over timestamped follow ONE time: QPS, events: errors, request across latency, CPU debug detail all services "IS something "WHY did it "WHERE did the wrong?" happen?" time/error go?" Together they answer: is it broken, why, and where.
PillarAnswersTools

Health checks & heartbeats Load balancers and orchestrators (Kubernetes) poll each instance's health endpoint. A liveness check asks "are you alive?" (restart if not); a readiness check asks "can you take traffic?" (route around if not). Distinguishing them prevents sending requests to a booting or overloaded instance.
Design for failure explicitly In the interview, proactively name failure modes: "If this cache cluster dies, reads fall through to the DB — so I'll size the DB to survive a cache outage, or accept degraded latency." Naming and handling failure is a senior signal.

Part 13 — Security & rate limiting ★ CORE

Authentication vs authorization

  • Authentication (authn) — who are you? (login, tokens, sessions)
  • Authorization (authz) — what are you allowed to do? (roles, permissions)

Tokens & sessions

Session-basedToken-based (JWT)
Server stores session; client holds session IDSelf-contained signed token; server stores nothing
Easy to revoke (delete session)Hard to revoke before expiry
Needs shared session store to scaleStateless, scales horizontally

Security essentials to mention

  • Encrypt in transit (TLS everywhere) and at rest (disk/DB encryption).
  • Hash passwords with a slow salted hash (bcrypt, Argon2) — never store plaintext or fast hashes.
  • Validate & sanitize input — prevent SQL injection (parameterized queries), XSS, etc.
  • Principle of least privilege — every service/user gets only the access it needs.
  • Secrets management — keep keys in a vault (AWS Secrets Manager, HashiCorp Vault), not in code.

Rate limiting algorithms

Rate limiting protects against abuse, runaway clients, and cascading overload. Four common algorithms:

AlgorithmIdeaNote
Token bucketTokens refill at a rate; each request spends oneAllows bursts up to bucket size. Most popular.
Leaky bucketRequests queue and drain at a fixed rateSmooths bursts into a steady flow
Fixed windowCount per time window (e.g., 100/min)Simple but allows 2x burst at window edges
Sliding windowRolling count over the last intervalSmoother, more accurate, more state
TOKEN BUCKET: bucket holds up to 10 tokens, refills 1/sec [* * * * * * * * * *] full -> burst of 10 allowed request -> take a token (* -> _) [* * * * * * * * * _] empty bucket -> requests rejected (429) until refill Allows short bursts while capping the long-run rate.
Where to rate limit Apply limits at the API gateway / edge so abusive traffic is rejected before consuming backend resources. In a distributed setup, store counters in a shared fast store (Redis) so the limit is enforced globally, not per-server. Return HTTP 429 with a Retry-After header.

The standard scaling journey

Most systems evolve along the same path as load grows. Knowing this lets you say "we'd start simple and add X when we hit Y."

STAGE 1: single server (app + DB on one box) client -> [ server + DB ] STAGE 2: split tiers, add a load balancer client -> LB -> [app][app] -> [ DB ] STAGE 3: add caching + read replicas client -> LB -> [app][app] -> cache -> primary DB -> replicas STAGE 4: CDN, queues, shard the DB, microservices client -> CDN -> LB -> gateway -> services -> queue -> workers -> sharded DBs + caches

Trade-off vocabulary (sprinkle these in)

  • Consistency vs availability (CAP) and latency (PACELC)
  • Read performance vs write performance (indexes, denormalization)
  • Latency vs throughput
  • Strong vs eventual consistency
  • Normalization (less duplication) vs denormalization (faster reads)
  • Push (precompute) vs pull (compute on read)
  • Cost vs performance vs complexity
Push vs pull — a recurring decision Should you precompute and store a result (push, fast reads, heavy writes/storage) or compute it on demand (pull, cheap writes, slower reads)? The news-feed "fan-out" question below is the classic example. The right answer often depends on the read/write ratio and on outliers (celebrities).

Part 15 — Worked design: URL shortener (TinyURL) ★ CORE

A great warm-up problem that touches encoding, storage, caching, and read-heavy scale.

1. Requirements

  • Functional: shorten a long URL; redirect a short URL to the original; optional custom alias and expiry.
  • Non-functional: highly available, low-latency redirects, short codes, massively read-heavy.

2. Estimation

100M new URLs/day -> ~1,200 writes/sec
Read:write ~= 100:1 -> ~120,000 redirects/sec  (READ-HEAVY)
Store 5 years: 100M * 365 * 5 ~= 180B URLs
Each record ~500 bytes -> ~90 TB

3. The core question: how to generate the short code?

A short code is just the long URL's ID encoded in base62 (a-z A-Z 0-9). Base62 packs more values into fewer characters than base10.

62^6 = ~56 billion 6 chars 62^7 = ~3.5 trillion 7 chars -> plenty of space Approach A: auto-increment ID -> base62 encode it id 125 -> "cb" (sequential, predictable) Approach B: hash(URL) -> take first 7 chars risk of collisions -> check & retry Approach C: pre-generate keys with a Key Generation Service (KGS) and hand them out -> no collisions, no encoding at write time. (often preferred)

4. API & data model

POST /shorten   { long_url, custom_alias?, expiry? }  -> { short_url }
GET  /{code}    -> 301/302 redirect to long_url

Table urls:
  short_code (PK)  | long_url | created_at | expiry | user_id

5. High-level design

CREATE: client -> LB -> app -> get key from KGS -> store {code -> long_url} in DB -> return short URL REDIRECT (the hot path, 100x more traffic): client -> LB -> app -> check CACHE for code hit -> 302 redirect (fast!) miss-> read DB, cache it, redirect +--------+ +-----+ +-------+ +-------------+ | client |-->| LB |-->| app |-->| Redis cache | +--------+ +-----+ +-------+ +-------------+ | miss | v v +----------------------+ | DB (key-value store) | +----------------------+

6. Scale & trade-offs

  • Redirects are read-heavy → aggressive caching (Redis) + CDN; cache hit serves in single-digit ms.
  • Data is simple key→value at huge scale → a NoSQL key-value store (DynamoDB/Cassandra) shards naturally by code.
  • 301 (permanent) caches in the browser and skips your server on repeat visits, but kills click analytics; 302 (temporary) keeps every redirect coming to you. Pick based on whether you need analytics.
  • Custom aliases need a uniqueness check; expiry needs a background cleanup job.

Part 16 — Worked design: news feed (Twitter/Facebook) SCALE

The canonical "fan-out" problem. The whole interview hinges on one decision: compute the feed on write or on read?

1. Requirements

  • Functional: post content; follow users; view a home feed of followees' posts, newest first.
  • Non-functional: feed loads fast (< 200ms), read-heavy, eventual consistency is fine (a post can appear a few seconds late).

2. The central decision: fan-out on write vs read

FAN-OUT ON WRITE (push): when Alice posts, immediately insert that post into the precomputed feed cache of EVERY follower. Alice posts -> [push to follower1 feed] -> [push to follower2 feed] -> [push to followerN feed] + Reads are instant (feed already built) - Writes are expensive; a user with 50M followers triggers 50M writes ("celebrity problem") FAN-OUT ON READ (pull): build the feed when the user opens the app, by fetching recent posts from everyone they follow. Bob opens app -> fetch posts from all followees -> merge + sort by time -> show + Writes are cheap (just store the post once) - Reads are expensive & slow (query many users live)

3. The hybrid answer (what to actually say)

Use fan-out on write for most users (fast reads), but fan-out on read for celebrities (avoid millions of writes per post). At read time, merge a user's precomputed feed with the latest posts from the few celebrities they follow.

normal followee posts -> pushed into your feed cache celebrity posts -> NOT pushed (too many followers) when you open the app: your precomputed feed (from normal users) + live-fetch recent celebrity posts you follow = merge, sort, return Best of both: cheap celebrity writes, fast normal reads.

4. High-level design

WRITE PATH: post -> post service -> store in DB -> enqueue fan-out job fan-out worker -> push post id into followers' feed cache (Redis list per user) READ PATH: GET feed -> feed service -> read user's feed cache -> merge celebrity posts -> hydrate post details (cache/DB) -> return page [post svc]->[queue]->[fan-out workers]->[feed cache] ^ client -> [feed svc] ----------------------- + -> DB

5. Scale & trade-offs

  • Feed cache (Redis) stores post IDs only; hydrate full content separately so cache stays small.
  • Fan-out is async via a queue so posting feels instant and spikes are absorbed.
  • Eventual consistency is acceptable — a slight delay before a post appears is fine.
  • Store media in object storage + CDN; the feed holds references, not blobs.
  • Paginate with cursors (not offsets) for stable, efficient infinite scroll.

Part 17 — Worked design: chat / messaging (WhatsApp) SCALE

Tests real-time delivery, connection management, and presence — a different flavor from request/response systems.

1. Requirements

  • Functional: 1:1 messaging, group chat, delivery/read receipts, online presence, message history.
  • Non-functional: real-time (low latency), reliable delivery (no lost messages), ordered within a conversation.

2. The key insight: persistent connections

HTTP request/response can't push a message to a user the instant it arrives. Chat needs a persistent bidirectional connection — typically WebSocket — so the server can push to the client at any time.

POLLING (bad): client repeatedly asks "anything new?" wasteful, laggy. WEBSOCKET (good): one long-lived connection, both sides push anytime. client A <==== persistent WS ====> chat server ^ client B <==== persistent WS ==========+ Server holds millions of open connections, mapping user_id -> which server holds their connection.

3. How a message flows

1. A sends msg over its WebSocket to chat-server-1 2. server persists msg (so it's not lost) + assigns ID 3. look up: which server holds B's connection? (a session registry: user_id -> server, in Redis) 4. route msg to chat-server-2 (B's server) 5. server-2 pushes msg down B's WebSocket 6. B's client ACKs -> sender sees "delivered" If B is OFFLINE: store in B's inbox/queue; deliver when B reconnects (and send a push notification).

4. Core components

  • Connection/gateway servers — hold the WebSocket connections (stateful; one user pinned to one server).
  • Session registry — maps user_id → connection server (Redis), so servers can route to each other.
  • Message store — persists messages; a wide-column store (Cassandra) suits the huge write volume and "fetch recent messages by conversation" access pattern.
  • Presence service — tracks online/offline via heartbeats; last-seen timestamps.
  • Push notification service — for offline users (APNs/FCM).

5. Scale & trade-offs

  • Connection servers are stateful — use a load balancer that supports sticky WebSocket connections, and a registry so any server can reach any user.
  • Ordering: assign a per-conversation sequence number; clients sort by it. A single partition per conversation preserves order.
  • Group chat is fan-out: deliver to each online member's connection; store once per recipient inbox or once per conversation depending on read pattern.
  • Delivery guarantee: persist before ACK, dedup on message ID, retry on reconnect → at-least-once with idempotent clients.
  • End-to-end encryption (if required) means the server only routes ciphertext.

Part 18 — More worked designs (rate limiter, typeahead, notifications) ◆ CONCEPT

Distributed rate limiter

Limit each user to N requests per window across a fleet of servers. The challenge: the count must be shared, or each server enforces its own limit and the global rate is N × servers.

Per-server counters (WRONG): user gets N * serverCount Shared counter in Redis (RIGHT): every server INCR a Redis key per user+window reject when the count exceeds N srv1 --INCR user:123--+ srv2 --INCR user:123--+--> [ Redis ] -> count, enforce srv3 --INCR user:123--+ Token bucket implemented with Redis atomic ops (or a Lua script) keeps it correct under concurrency.

Put the limiter at the API gateway, fail fast with HTTP 429, and use a sliding window or token bucket for smoothness. Accept tiny inaccuracy for performance.

Typeahead / autocomplete

Suggest completions as the user types, in < 100ms. The data structure is a trie (prefix tree); precompute the top-K suggestions at each node so a lookup is a quick descent, not a search.

trie for "ca", "cat", "car", "card": (root) |c (c) |a (a) top-K here: [cat, car, card...] / \ (t) (r) |d (d) type "ca" -> jump to that node -> return its cached top-K list. Build offline from search-frequency logs; refresh periodically. Cache hot prefixes in Redis.

Notification system

Send email / SMS / push to millions of users. Decouple producers from senders with queues, and isolate each channel so one slow provider doesn't block the others.

event -> notification service -> [ queue per channel ] | | | email sms push worker worker worker | | | SendGrid Twilio APNs/FCM - rate-limit per provider, retry with backoff + DLQ - dedup so users aren't spammed (idempotency keys) - respect user preferences / opt-outs - template service for content
Notice the recurring building blocks Every design above reuses the same parts: a load balancer, a cache, a queue for async work, a sharded datastore, and idempotent processing. System design is largely about combining a small set of well-understood components to fit the specific read/write pattern and consistency needs.

Part 19 — Final checklist & numbers to memorize

The interview checklist

  1. Clarify functional + non-functional requirements; state scope.
  2. Estimate scale (QPS, storage, bandwidth); identify read vs write heavy.
  3. Sketch the API and data model.
  4. Draw the high-level architecture (client → LB → app → cache → DB).
  5. Deep-dive the 1–2 hardest components.
  6. Find bottlenecks; apply caching, replication, sharding, queues.
  7. Address reliability (SPOF, failover) and observability.
  8. State trade-offs out loud; mention what you'd do with more time.

The mantras

  • Clarify before you design. Wrong assumptions waste the whole interview.
  • Read-heavy? Cache and replicate. Write-heavy? Partition and queue.
  • Everything is a trade-off. There's no "best" — only "best for these requirements."
  • Design for failure. Assume every component will die; plan the response.
  • Start simple, scale when needed. Don't over-engineer for scale you don't have.
  • Keep app servers stateless. Push state to shared stores so you can scale horizontally.
  • Make operations idempotent. Retries and at-least-once delivery demand it.
Final advice There's no single correct answer in system design — interviewers want to see structured thinking, sensible trade-offs, and the ability to go deep when probed. Drive the conversation with the framework, justify every choice with requirements and numbers, and proactively name the weaknesses of your own design. That self-awareness is what separates senior candidates.
