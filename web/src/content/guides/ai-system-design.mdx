<h2 id="part-0">Part 0 — How to answer an AI system design interview <Tag kind="core">★ CORE</Tag></h2>

<p>AI system design interviews are usually not asking for low-level distributed-systems detail first. They want to see whether you can structure an ambiguous product into a sensible <strong>data flow</strong>, <strong>model flow</strong>, <strong>serving architecture</strong>, and <strong>operations plan</strong>. The best answers are simple, layered, and explicit about trade-offs.</p>

<h3 id="a-simple-interview-flow">A simple interview flow</h3>
<ol>
  <li><strong>Clarify the use case</strong> — who uses it, what task, what success means.</li>
  <li><strong>Define inputs and outputs</strong> — text, image, audio, structured records, actions.</li>
  <li><strong>Choose the AI pattern</strong> — classification, ranking, retrieval, generation, agent, forecasting.</li>
  <li><strong>Draw the high-level architecture</strong> — clients, APIs, model layer, data stores, async workers.</li>
  <li><strong>Discuss model lifecycle</strong> — data collection, training/fine-tuning, deployment, evaluation.</li>
  <li><strong>Discuss production concerns</strong> — latency, cost, safety, monitoring, fallback paths.</li>
  <li><strong>Close with trade-offs</strong> — why this design over simpler or more advanced options.</li>
</ol>

<Callout variant="tip" title="Lead with the product goal, not the model">
  In AI interviews, many candidates jump directly to "use an LLM" or "train a transformer." Strong candidates start with the user problem and the success metric. The model is one component of the system, not the whole answer.
</Callout>

<h3 id="what-to-clarify-early">What to clarify early</h3>
<ul>
  <li><strong>Users:</strong> internal employees, consumers, analysts, support agents, doctors, drivers?</li>
  <li><strong>Mode:</strong> batch, near-real-time, real-time, interactive?</li>
  <li><strong>Output quality bar:</strong> helpful suggestion, top-1 prediction, autonomous action, or human-reviewed draft?</li>
  <li><strong>Risk level:</strong> low-risk summarization vs high-risk finance/healthcare decisioning.</li>
  <li><strong>Scale:</strong> daily batch jobs, hundreds of QPS, or millions?</li>
</ul>

<h3 id="a-good-one-line-structure">A good one-line structure</h3>

<Ascii>{`  User request / event
        -> data retrieval + context assembly
        -> model inference / decision engine
        -> post-processing + guardrails
        -> response / action
        -> logging + feedback + evaluation`}</Ascii>

<h3 id="time-budget">A 45-minute AI system design time budget</h3>
<table>
  <tr><th scope="col">Phase</th><th scope="col">Time</th><th scope="col">What to say</th></tr>
  <tr><td>Clarify</td><td>5 min</td><td>Use case, users, risk, latency, scale, success metric</td></tr>
  <tr><td>Choose pattern</td><td>3 min</td><td>Predictive ML, RAG, agent, recommendation, multimodal, or hybrid</td></tr>
  <tr><td>High-level design</td><td>10 min</td><td>Online path, offline path, stores, model serving, safety layer</td></tr>
  <tr><td>Deep dive</td><td>15 min</td><td>Retrieval, ranking, feature freshness, agent tools, evals, or latency</td></tr>
  <tr><td>Operations</td><td>7 min</td><td>Monitoring, drift, cost, fallback, rollout, incident handling</td></tr>
  <tr><td>Wrap</td><td>5 min</td><td>Trade-offs, what you would build first, what you would defer</td></tr>
</table>

<Callout variant="tip" title="The strongest answer shape">
  Separate the <strong>online serving path</strong> from the <strong>offline improvement path</strong>. The online path answers users; the offline path improves the model, index, features, prompts, and evals. This single separation makes most AI designs sound production-ready.
</Callout>

<h3 id="requirements-that-matter-for-ai">Requirements that matter specifically for AI</h3>
<table>
  <tr><th scope="col">Requirement</th><th scope="col">Why it matters</th><th scope="col">Design implication</th></tr>
  <tr><td>Quality target</td><td>AI output is probabilistic</td><td>Define eval metric, not just feature list</td></tr>
  <tr><td>Latency target</td><td>LLMs, rerankers, speech, and tools add delay</td><td>Use streaming, caching, smaller models, async jobs</td></tr>
  <tr><td>Risk level</td><td>Wrong actions can harm users or business</td><td>Add approval gates, audit logs, policy checks</td></tr>
  <tr><td>Freshness</td><td>Knowledge, features, and fraud patterns change</td><td>Use event-driven indexing, streaming features, retraining cadence</td></tr>
  <tr><td>Personalization</td><td>Context improves utility but increases privacy complexity</td><td>Use scoped profiles, consent, feature TTLs, access checks</td></tr>
  <tr><td>Explainability</td><td>Analysts and regulators need reasons</td><td>Store evidence, citations, feature attributions, decision reasons</td></tr>
</table>

  <tr><td>Feature / context layer</td><td>Prepares model inputs</td><td>Feature store, retrieval service, prompt builder</td></tr>
  <tr><td>Model serving layer</td><td>Runs inference</td><td>LLM endpoint, classifier, ranker, speech model</td></tr>

  <tr><td>Evaluation / feedback</td><td>Measures quality and drift</td><td>Offline evals, human review, A/B testing</td></tr>
  <tr><td>Safety / governance</td><td>Controls bad behavior and compliance</td><td>Filters, policy engine, audit logs</td></tr>

<h3 id="common-ai-system-types">Common AI system types</h3>
<ul>
  <li><strong>Predictive ML:</strong> classify, score, forecast, rank.</li>
  <li><strong>Search + retrieval:</strong> semantic search, hybrid search, enterprise knowledge lookup.</li>
  <li><strong>Generative AI:</strong> chat, summarization, drafting, code generation.</li>
  <li><strong>Agentic systems:</strong> plan, use tools, fetch data, take actions across systems.</li>
  <li><strong>Decisioning systems:</strong> fraud, abuse, recommendations, bidding, dynamic pricing.</li>
  <li><strong>Multimodal systems:</strong> image understanding, OCR, speech, voice assistants.</li>
</ul>

      |          |           |            |          |           |
      |          |           |            |          |           v

<h2 id="part-1-5">Part 1.5 — AI-specific estimation <Tag kind="core">★ CORE</Tag></h2>

<p>AI system estimation includes normal system-design numbers plus model-specific numbers: tokens, retrieval fan-out, model calls, GPU/API cost, and feedback volume.</p>

<h3 id="what-to-estimate">What to estimate</h3>
<ul>
  <li><strong>Traffic:</strong> QPS, daily active users, peak multiplier.</li>
  <li><strong>Input size:</strong> tokens per prompt, audio seconds, image size, number of documents.</li>
  <li><strong>Model calls:</strong> one model call vs router + retriever + reranker + generator + judge.</li>
  <li><strong>Retrieval fan-out:</strong> top-k chunks, reranked candidates, metadata filters.</li>
  <li><strong>Latency budget:</strong> retrieval, model first token, tool calls, post-processing.</li>
  <li><strong>Storage growth:</strong> logs, embeddings, traces, raw data, labels.</li>
  <li><strong>Cost:</strong> token/API cost, GPU cost, vector DB cost, human review cost.</li>
</ul>

<h3 id="rag-cost-example">Worked estimate: internal RAG assistant</h3>
<Ascii>{`  Assumptions:
    20,000 employees
    30% use assistant daily        -> 6,000 DAU
    8 questions / active user / day -> 48,000 queries/day
    Peak ~= 3x average

  Average QPS:
    48,000 / 86,400 ~= 0.56 QPS
    Peak ~= 1.7 QPS  (small traffic, quality matters more than scale)

  Per query:
    input prompt      ~= 1,500 tokens
    retrieved context ~= 4 chunks * 500 tokens = 2,000 tokens
    output            ~= 400 tokens
    total             ~= 3,900 tokens/query

  Daily token volume:
    48,000 * 3,900 ~= 187M tokens/day

  Design implication:
    The main problem is not QPS. It is grounding quality,
    permissions, token cost, evals, and trace/debug storage.`}</Ascii>

<h3 id="embedding-storage-estimate">Embedding storage estimate</h3>
<Ascii>{`  1M document chunks
  embedding dimension: 1,536
  float32 size: 4 bytes

  raw vectors = 1M * 1,536 * 4 bytes ~= 6.1 GB
  plus metadata + ANN index overhead ~= 2-4x
  practical storage estimate ~= 12-25 GB

  If using float16 or quantized vectors, storage drops,
  but recall may change. Mention this as a tuning lever.`}</Ascii>

<Callout variant="tip" title="Estimation signal">
  In AI interviews, a good estimate often shows that the hard part is not always traffic. Sometimes the hard part is token cost, eval quality, stale context, labeling throughput, or permission-safe retrieval.
</Callout>

<h2 id="part-1-7">Part 1.7 — LLM inference internals every interviewer expects <Tag kind="core">★ CORE</Tag></h2>

<p>For senior AI system design rounds, interviewers expect you to talk about LLM serving with the same fluency you would talk about database indexes. You do not need to derive attention from scratch, but you do need to explain the runtime cost shape, how serving frameworks exploit it, and how those properties show up in your design.</p>

<h3 id="prefill-vs-decode">Prefill vs decode: the two phases that drive everything</h3>

<p>An LLM forward pass during generation has two distinct phases with different cost shapes. Almost every serving optimization is about exploiting this asymmetry.</p>

<Ascii>{`  PREFILL (process the prompt)              DECODE (generate tokens, one at a time)
  -------------------------------            -----------------------------------------
  parallel over all input tokens             sequential, one token per step
  compute-bound (matmul heavy)               memory-bandwidth-bound (load KV cache)
  good GPU utilization                       low GPU utilization unless batched
  cost ~ O(N_in)                             cost ~ O(N_out) per request
  affects: time-to-first-token (TTFT)        affects: tokens-per-second (TPS / TPOT)`}</Ascii>

<table>
  <tr><th scope="col">Metric</th><th scope="col">What it measures</th><th scope="col">User-visible effect</th></tr>
  <tr><td>TTFT (time to first token)</td><td>Prefill time + queueing + first decode step</td><td>How "snappy" the response feels</td></tr>
  <tr><td>TPOT (time per output token)</td><td>Inverse of decode throughput per request</td><td>How fast the answer streams</td></tr>
  <tr><td>End-to-end latency</td><td>TTFT + N_out * TPOT</td><td>Total wait for a complete answer</td></tr>
  <tr><td>Throughput (tokens/sec/GPU)</td><td>Aggregate across all concurrent requests</td><td>Cost per million tokens</td></tr>
</table>

<h3 id="kv-cache">KV cache: why it dominates memory</h3>

<p>During autoregressive decoding, attention needs the keys and values of every prior token. Recomputing them each step would be quadratic, so they are cached. The KV cache is the largest dynamic memory consumer on the GPU during inference, and it scales with <em>tokens in flight</em>, not parameter count.</p>

<Ascii>{`  KV cache size per request:
    2 * n_layers * n_heads * head_dim * seq_len * dtype_bytes

  Concrete example (Llama-like, 70B class):
    n_layers = 80, n_kv_heads = 8, head_dim = 128, dtype = fp16 (2 bytes)
    per token:  2 * 80 * 8 * 128 * 2 = ~320 KB / token
    8k context: ~2.5 GB per request just for KV cache

  Why it matters in design:
    batch size at serving time is gated by KV memory, not FLOPs.
    longer contexts -> fewer concurrent users per GPU -> higher cost/token.`}</Ascii>

<h3 id="batching-strategies">Batching strategies</h3>

<table>
  <tr><th scope="col">Strategy</th><th scope="col">How it works</th><th scope="col">Trade-off</th></tr>
  <tr><td>Static batching</td><td>Wait for N requests, run them together to completion</td><td>Easy, but slow requests block fast ones (head-of-line blocking)</td></tr>
  <tr><td>Dynamic batching</td><td>Bucket by length, flush on timer or size</td><td>Better utilization, still suffers from variable output length</td></tr>
  <tr><td>Continuous batching (in-flight)</td><td>New requests join the batch every decode step; finished requests leave</td><td>Standard for vLLM, TensorRT-LLM, TGI; 2–10x throughput gain</td></tr>
  <tr><td>Chunked prefill</td><td>Split long prompts into chunks interleaved with decode steps of other requests</td><td>Keeps decode latency low while serving long-context prefills</td></tr>
</table>

<h3 id="paged-attention">Paged attention and memory fragmentation</h3>

<p>Naive KV cache allocates one contiguous block per request sized to <code>max_seq_len</code>, wasting most of it. Paged attention (vLLM) treats KV cache like virtual memory: small fixed-size blocks, allocated on demand, addressed by a per-request block table. Result: 2–4x more concurrent requests on the same GPU.</p>

<Ascii>{`  Without paging:                       With paged attention:
  [Req A: 8192 reserved | used 200 ]    blocks: [A0][B0][A1][C0][B1][A2]...
  [Req B: 8192 reserved | used 100 ]    A's table: [0, 2, 5, ...]
  [Req C: 8192 reserved | used 50  ]    B's table: [1, 4, ...]
                                        C's table: [3, ...]

  internal fragmentation high           internal fragmentation ~ 1 block / req
  rejects requests early                packs many short requests densely`}</Ascii>

<h3 id="speculative-decoding">Speculative decoding</h3>

<p>A small "draft" model proposes K tokens; the large "verifier" model checks them in one forward pass and accepts the longest matching prefix. Net effect: decode throughput goes up because the expensive model does fewer sequential steps. Acceptance rate determines the speedup (typical 2–3x for similar-distribution drafters).</p>

<Ascii>{`  draft model (small) -> proposes: "the cat sat on the"
  target model (big)  -> verifies all 5 in parallel
                         accepts "the cat sat on" (4), rejects "the", resamples 5th

  Variants:
    - Medusa heads (extra heads on the same model predict multiple tokens)
    - EAGLE (uses target model's hidden state to draft)
    - Lookahead decoding (no draft model, uses Jacobi iteration)`}</Ascii>

<h3 id="quantization-table">Quantization choices</h3>

<table>
  <tr><th scope="col">Format</th><th scope="col">Bits</th><th scope="col">When to use</th><th scope="col">Caveat</th></tr>
  <tr><td>FP16 / BF16</td><td>16</td><td>Default for training and high-quality inference</td><td>BF16 has wider range, better for training stability</td></tr>
  <tr><td>FP8 (E4M3 / E5M2)</td><td>8</td><td>H100/H200 inference for new training runs</td><td>Requires recent hardware and calibration</td></tr>
  <tr><td>INT8 (SmoothQuant, W8A8)</td><td>8</td><td>2x throughput on most GPUs, small quality drop</td><td>Outlier channels need handling</td></tr>
  <tr><td>INT4 (GPTQ, AWQ)</td><td>4 weight / 16 act</td><td>Fits 70B on a single 80GB GPU; on-device deploys</td><td>Weight-only; activations stay fp16</td></tr>
  <tr><td>KV cache quant (FP8 / INT4)</td><td>varies</td><td>Doubles concurrent requests at long context</td><td>Long-context tasks regress more</td></tr>
</table>

<h3 id="parallelism">Distributed inference parallelism</h3>

<ul>
  <li><strong>Tensor parallel (TP):</strong> shard each layer's matmuls across GPUs in a node. Low latency, high bandwidth required (NVLink). Used for models that don't fit on one GPU.</li>
  <li><strong>Pipeline parallel (PP):</strong> split layers across nodes. Higher latency but cheaper interconnect; usually combined with TP, not used alone for serving.</li>
  <li><strong>Expert parallel (EP):</strong> for MoE models, route each expert to a different GPU. Activates only top-k experts per token; saves compute, increases routing/comm complexity.</li>
  <li><strong>Sequence/context parallel:</strong> shard the sequence dimension; useful for very long context (&gt;100k tokens).</li>
  <li><strong>Replication:</strong> for throughput scaling, just replicate the whole model across GPUs and load-balance.</li>
</ul>

<h3 id="prefix-caching">Prefix caching</h3>

<p>If many requests share a prefix (system prompt, few-shot examples, long document), reuse the KV cache for the shared portion across requests. Cuts TTFT dramatically for chat apps and RAG with stable system prompts. Most modern serving stacks (vLLM, TensorRT-LLM, SGLang) support this.</p>

<Callout variant="tip" title="Interview shortcut">
  When asked about LLM latency, lead with: "There are two phases — prefill (compute-bound, sets TTFT) and decode (memory-bound, sets TPOT). I'd optimize TTFT with prefix caching and chunked prefill, optimize TPOT with continuous batching and speculative decoding, and reduce KV memory with paged attention plus KV quantization to raise concurrency." That single sentence signals seniority.
</Callout>

<h3 id="serving-stack-choices">Serving stack choices</h3>

<table>
  <tr><th scope="col">Option</th><th scope="col">Best for</th><th scope="col">Note</th></tr>
  <tr><td>vLLM</td><td>Open-source default; paged attention + continuous batching</td><td>Strong throughput, broad model support</td></tr>
  <tr><td>TensorRT-LLM</td><td>Maximum throughput on NVIDIA GPUs</td><td>Per-model engine build; less flexible</td></tr>
  <tr><td>TGI (HuggingFace)</td><td>Easy ops, broad model support</td><td>Good for medium-scale production</td></tr>
  <tr><td>SGLang</td><td>Programs/agents with shared prefixes, structured output</td><td>RadixAttention for prefix sharing</td></tr>
  <tr><td>Hosted API (Anthropic / OpenAI / Bedrock)</td><td>You don't want to run GPUs at all</td><td>Pay per token; opaque latency variance</td></tr>
</table>

<h2 id="part-2">Part 2 — Core trade-offs interviewers expect <Tag kind="concept">◆ CONCEPT</Tag></h2>

<h3 id="accuracy-vs-latency-vs-cost">Accuracy vs latency vs cost</h3>
<p>This is the central AI production triangle. Larger models often improve quality, but also raise latency and cost. Good answers explain how to tier the system: cheap model first, expensive model only when needed.</p>

<Ascii>{`  Better quality  -> usually larger model / more retrieval / more compute
  Lower latency   -> smaller model / caching / precomputation
  Lower cost      -> batching / routing / fallback / async processing

  In interviews: say which side you optimize first for this product.`}</Ascii>

<h3 id="online-vs-offline">Online vs offline</h3>
<ul>
  <li><strong>Offline:</strong> training, indexing, batch enrichment, feature computation, evaluation.</li>
  <li><strong>Online:</strong> request-time retrieval, ranking, inference, safety checks, response formatting.</li>
</ul>
<p>A common mistake is placing too much work in the online path. High-level designs should move expensive work offline whenever possible.</p>

<h3 id="personalization-vs-simplicity">Personalization vs simplicity</h3>
<p>Personalization improves utility, but adds feature pipelines, privacy concerns, online feature freshness requirements, and harder debugging. Mention this explicitly for recommendations, assistants, and ranking systems.</p>

<h3 id="automation-vs-human-in-the-loop">Automation vs human-in-the-loop</h3>
<p>For low-risk tasks, fully automated AI may be acceptable. For high-risk workflows, a better architecture is AI draft → human review → audited final action. This is often the correct enterprise answer.</p>

<h3 id="retrieval-vs-fine-tuning-vs-prompting">Prompting vs RAG vs fine-tuning vs agents</h3>
<table>
  <tr><th scope="col">Approach</th><th scope="col">Use when</th><th scope="col">Avoid when</th></tr>
  <tr><td>Prompting</td><td>The task is simple and the model already knows enough</td><td>You need private/fresh knowledge or consistent behavior at scale</td></tr>
  <tr><td>RAG</td><td>You need grounded answers over changing knowledge</td><td>The problem is style/format/skill rather than factual lookup</td></tr>
  <tr><td>Fine-tuning</td><td>You need consistent format, domain style, or narrow repeated behavior</td><td>You mainly need up-to-date facts or citations</td></tr>
  <tr><td>Agent/tools</td><td>The task requires multi-step actions, APIs, or decisions based on intermediate results</td><td>A fixed workflow or simple retrieval answer is enough</td></tr>
  <tr><td>Classical ML</td><td>You need low-latency scoring, ranking, forecasting, or classification</td><td>The task requires open-ended reasoning or generation</td></tr>
</table>

<h3 id="consistency-for-ai-systems">Consistency in AI systems</h3>
<p>AI systems have normal data consistency issues plus model/version consistency issues. Say which version of the prompt, model, retriever, feature set, and policy produced a result. Without that, debugging and rollback become guesswork.</p>

<Ascii>{`  User saw bad answer at 10:03
          |
          v
  Need to reconstruct:
    model version       = gpt-x / llama-y / ranker-v12
    prompt version      = support_prompt_2026_06_10
    retrieval index     = docs_index_184
    feature snapshot    = online_features_10:03
    policy version      = pii_policy_v7
    tool outputs        = account_api response IDs
    final output        = exact text/action returned`}</Ascii>

<h2 id="part-2-5">Part 2.5 — Retrieval, embeddings, and reranking choices <Tag kind="core">★ CORE</Tag></h2>

<p>Retrieval is where most production RAG systems succeed or fail. Interviewers want you to name specific algorithms and explain the trade-offs, not just say "use a vector DB."</p>

<h3 id="ann-index-types">ANN index choices</h3>

<table>
  <tr><th scope="col">Index</th><th scope="col">How it works</th><th scope="col">When to pick</th><th scope="col">Caveats</th></tr>
  <tr><td>Flat / brute force</td><td>Exact cosine/L2 over all vectors</td><td>&lt; 100k vectors, or eval ground truth</td><td>O(N) per query; doesn't scale</td></tr>
  <tr><td>HNSW (graph)</td><td>Layered proximity graph, greedy descent</td><td>General default; high recall at low latency</td><td>Memory hungry; rebuilds slow; updates degrade graph</td></tr>
  <tr><td>IVF + PQ</td><td>Coarse cluster (IVF) then product-quantized codes</td><td>Very large corpora (100M+) where memory matters</td><td>Recall drops with aggressive quantization</td></tr>
  <tr><td>ScaNN</td><td>Anisotropic quantization + tree search</td><td>Billion-scale, Google ecosystem</td><td>Less common outside Google stack</td></tr>
  <tr><td>DiskANN / Vamana</td><td>Graph index on SSD</td><td>Vectors don't fit in RAM</td><td>Higher tail latency than in-memory</td></tr>
</table>

<h3 id="vector-db-products">Vector database options</h3>

<ul>
  <li><strong>Postgres + pgvector:</strong> small to medium corpora, transactional consistency with your app data. Easiest if you already run Postgres.</li>
  <li><strong>Elastic / OpenSearch:</strong> hybrid keyword + vector in one index, mature ACL/aggregation story.</li>
  <li><strong>Pinecone / Weaviate / Qdrant / Milvus:</strong> dedicated vector stores with managed sharding and replication; pick when scale outgrows pgvector or you need namespaces/multi-tenancy.</li>
  <li><strong>FAISS:</strong> library, not a service. Wrap it in your own server when you need full control.</li>
  <li><strong>LanceDB / Chroma:</strong> embedded; good for local agents and notebooks.</li>
</ul>

<h3 id="chunking-strategies">Chunking strategies</h3>

<table>
  <tr><th scope="col">Strategy</th><th scope="col">Good for</th><th scope="col">Risk</th></tr>
  <tr><td>Fixed-size with overlap (e.g. 800 tok / 100 overlap)</td><td>Generic prose, default starting point</td><td>Cuts mid-sentence; loses structure</td></tr>
  <tr><td>Recursive structural (by heading then paragraph)</td><td>Wiki, docs, contracts</td><td>Needs a good parser per format</td></tr>
  <tr><td>Sentence-window</td><td>QA on dense text</td><td>Many small chunks; reranker becomes critical</td></tr>
  <tr><td>Semantic chunking (cluster sentences by embedding distance)</td><td>Long-form articles, transcripts</td><td>Slower to ingest; non-deterministic</td></tr>
  <tr><td>Page or row level</td><td>PDFs, tables, spreadsheets</td><td>One chunk may be much larger than others</td></tr>
  <tr><td>Parent-child (small for retrieval, large for context)</td><td>When retrieval precision and context fullness conflict</td><td>Doubles storage</td></tr>
</table>

<h3 id="bi-encoder-vs-cross-encoder">Bi-encoder vs cross-encoder</h3>

<Ascii>{`  BI-ENCODER (used for retrieval)              CROSS-ENCODER (used for reranking)
  embed(query) and embed(doc) separately       feed [query; doc] together into model
  similarity = cosine(q_vec, d_vec)            output a relevance score directly
  fast: precompute doc vectors, ANN lookup     slow: must run per (q, d) pair
  use to fetch top-100 candidates              use to rerank top-100 -> top-5
  example: sentence-transformers, OpenAI       example: cohere-rerank, BGE-reranker,
           text-embedding-3, e5, bge                    monoT5, ColBERT (late-interact)`}</Ascii>

<h3 id="hybrid-retrieval">Hybrid retrieval (almost always wins)</h3>

<p>BM25 (sparse, keyword) and dense embeddings (semantic) have complementary failure modes. Combining them beats either alone on most enterprise corpora because acronyms, IDs, product codes, and rare names don't embed well.</p>

<Ascii>{`  query
    |
    +---> BM25 / keyword search  -> top-50 (sparse)
    +---> dense vector search    -> top-50 (semantic)
            |
            v
       fusion: RRF (reciprocal rank fusion) or weighted score
            |
            v
       reranker (cross-encoder) on top-50
            |
            v
       top-5 passed to LLM with citations`}</Ascii>

<h3 id="advanced-rag-patterns">Advanced RAG patterns worth naming</h3>

<ul>
  <li><strong>Query rewriting / decomposition:</strong> turn "compare our PTO policy to Acme's" into two sub-queries.</li>
  <li><strong>HyDE (hypothetical document embedding):</strong> ask the LLM to draft a hypothetical answer, embed that, use it as the retrieval query. Helps short queries with sparse vocabulary overlap.</li>
  <li><strong>Multi-vector / ColBERT-style:</strong> store one vector per token (late interaction). Higher recall, much more storage.</li>
  <li><strong>Self-querying:</strong> LLM emits a structured filter (date range, owner, doc type) alongside the semantic query, executed as metadata filter + vector search.</li>
  <li><strong>GraphRAG:</strong> build an entity/relationship graph from the corpus offline; retrieve subgraphs for queries that need multi-hop reasoning ("who reports to the person who owns project X").</li>
  <li><strong>Contextual retrieval (prefix each chunk with a short LLM-generated summary of its surroundings):</strong> cheap quality lift, popularized by Anthropic.</li>
</ul>

<h3 id="adaptation-menu">Model adaptation menu (what's actually being tuned)</h3>

<table>
  <tr><th scope="col">Technique</th><th scope="col">What it changes</th><th scope="col">When to use</th><th scope="col">Trade-off</th></tr>
  <tr><td>Prompting / few-shot</td><td>Nothing (inference only)</td><td>Fastest iteration; small behavior tweaks</td><td>Token cost grows with examples</td></tr>
  <tr><td>RAG</td><td>Context, not weights</td><td>Knowledge changes frequently</td><td>Retrieval quality is the new bottleneck</td></tr>
  <tr><td>Supervised fine-tuning (SFT)</td><td>All weights, full precision</td><td>Domain-specific style or skill</td><td>Expensive, needs labeled data</td></tr>
  <tr><td>LoRA / QLoRA (PEFT)</td><td>Small adapter matrices; base frozen</td><td>Many narrow variants on one base model</td><td>Quality usually within a few % of full SFT</td></tr>
  <tr><td>DPO / KTO / ORPO</td><td>Aligns to preference pairs</td><td>Tone, refusal behavior, safety nudges</td><td>Needs preference data, not just labels</td></tr>
  <tr><td>RLHF / RLAIF</td><td>Optimizes against a reward model</td><td>Complex behaviors hard to describe by examples</td><td>Highest complexity; reward hacking risk</td></tr>
  <tr><td>Distillation</td><td>Train smaller model on larger model's outputs</td><td>Cut serving cost after quality is solved</td><td>Caps at teacher quality on covered cases</td></tr>
  <tr><td>Continued pretraining</td><td>Base weights, on raw domain text</td><td>Truly new vocabulary or modality</td><td>Most expensive option</td></tr>
</table>

<Callout variant="tip" title="The ladder">
  In interviews, walk up this ladder: "Start with prompting + RAG. If style/format is the problem, do LoRA SFT. If tone/safety is the problem, layer DPO. Only do full fine-tuning or continued pretraining if those fail." This sequencing is what staff-level candidates say.
</Callout>

<h2 id="part-3">Part 3 — Generic AI architecture template <Tag kind="core">★ CORE</Tag></h2>

<p>This template works for many interview questions. Adapt it rather than inventing a brand-new structure each time.</p>

<Ascii>{`  [User / App / Event]
          |
          v
    [API Gateway / Backend]
          |
          +--> [Auth / Rate limiting / Policy checks]
          |
          +--> [Context builder]
          |         |
          |         +--> [Operational DB]
          |         +--> [Object store / docs]
          |         +--> [Vector DB / search index]
          |         +--> [Feature store / profile store]
          |
          +--> [Model router / orchestrator]
                    |
                    +--> [Classifier / ranker / LLM / speech model]
                    +--> [Fallback model]
                    +--> [Tool calls / external APIs]
                    |
                    v
              [Post-processing + guardrails]
                    |
                    v

                    |

<h3 id="how-to-explain-it">How to explain it</h3>
<ul>
  <li><strong>Ingress:</strong> request enters through app/API layer with auth and rate limits.</li>
  <li><strong>Context assembly:</strong> gather the minimum context needed for good inference.</li>
  <li><strong>Inference/orchestration:</strong> call one or more models or tools.</li>
  <li><strong>Guardrails:</strong> validate response, redact sensitive data, check policy.</li>
  <li><strong>Feedback loop:</strong> store interactions for analytics, evals, and future improvement.</li>
</ul>

<Callout variant="tip" title="Say where training lives">
  Even in a high-level interview, mention that training and re-indexing live off the critical request path: scheduled pipelines in batch/stream processing, model registry, offline evaluation, then controlled deployment to serving.
</Callout>

<h3 id="model-router-pattern">Model router pattern</h3>
<p>A production AI system rarely sends every request to the largest model. A router can classify difficulty, risk, or domain and choose the cheapest reliable path.</p>

<Ascii>{`  request
    |
    v
  [intent + risk classifier]
    |             |              |
    | easy        | hard         | unsafe / restricted
    v             v              v
  small model   large model    refuse / human review
    |             |
    +-------> common response validator
                  |
                  v
              response`}</Ascii>

<h3 id="fallback-patterns">Fallback patterns</h3>
<table>
  <tr><th scope="col">Failure</th><th scope="col">Fallback</th><th scope="col">Example</th></tr>
  <tr><td>LLM timeout</td><td>Smaller model or cached answer</td><td>Return concise answer with sources already retrieved</td></tr>
  <tr><td>Retriever empty</td><td>Keyword search, broader query, or ask clarifying question</td><td>"I could not find a policy doc for that exact term"</td></tr>
  <tr><td>Tool/API failure</td><td>Retry if idempotent, otherwise degrade to draft</td><td>Support copilot drafts but does not submit action</td></tr>
  <tr><td>Safety uncertainty</td><td>Human review</td><td>Payment reversal, account closure, medical guidance</td></tr>
  <tr><td>High cost pressure</td><td>Queue async job or summarize shorter</td><td>Long document analysis becomes background task</td></tr>
</table>

<h2 id="part-3-5">Part 3.5 — Data, model, and deployment lifecycle <Tag kind="core">★ CORE</Tag></h2>

<p>High-level AI design is not complete unless you describe how the system improves after launch. The lifecycle is the difference between a demo and a product.</p>

<h3 id="lifecycle-diagram">Lifecycle diagram</h3>
<Ascii>{`  production traffic
        |
        v
  logs + traces + feedback + labels
        |
        +--> data quality checks
        +--> eval set construction
        +--> error taxonomy
        |
        v
  improve one layer:
    - prompt
    - retrieval/chunking
    - features
    - model/fine-tune
    - policy/guardrails
        |
        v
  offline evals -> canary -> A/B test -> full rollout
        |
        v
  monitor drift, cost, quality, incidents`}</Ascii>

<h3 id="training-vs-serving-skew">Training-serving skew</h3>
<p>Training-serving skew happens when the model is trained on features or data transformations that differ from what online serving uses. This is common in recommendation, fraud, ranking, and personalization systems.</p>

<table>
  <tr><th scope="col">Skew source</th><th scope="col">Example</th><th scope="col">Mitigation</th></tr>
  <tr><td>Feature calculation</td><td>Offline uses 30-day purchase count; online uses stale cache</td><td>Shared feature definitions, feature store, freshness SLAs</td></tr>
  <tr><td>Label leakage</td><td>Training uses future data accidentally</td><td>Point-in-time joins, backtesting discipline</td></tr>
  <tr><td>Different distributions</td><td>Training on historical users, serving new user cohort</td><td>Drift monitoring, shadow evaluation, fresh labels</td></tr>
  <tr><td>Prompt/retrieval mismatch</td><td>Offline eval uses curated docs; production retrieval returns noisy chunks</td><td>End-to-end evals with real retriever</td></tr>
</table>

<h3 id="deployment-strategies">Deployment strategies</h3>
<ul>
  <li><strong>Shadow mode:</strong> run new model beside production, do not affect users.</li>
  <li><strong>Canary:</strong> send a small percentage of traffic to new version.</li>
  <li><strong>A/B test:</strong> compare product metrics and quality metrics.</li>
  <li><strong>Human-reviewed rollout:</strong> new AI output is visible only to reviewers first.</li>
  <li><strong>Rollback:</strong> keep model, prompt, retriever, and policy versions separately rollbackable.</li>
</ul>

<h3 id="model-registry-and-governance">Model registry and governance</h3>
<Ascii>{`  training job / prompt change / retriever change
        |
        v
  artifact + config + eval report + owner
        |
        v
  model/prompt/index registry
        |
        +--> staging endpoint
        +--> canary endpoint
        +--> production endpoint
        |
        v
  rollback pointer: prod -> previous known-good version`}</Ascii>

<Callout variant="warn" title="Do not ignore prompts and indexes">
  In LLM/RAG systems, the deployed artifact is not just the model. The prompt template, retrieval index, chunking strategy, reranker, tool schemas, and guardrail policy are all part of the deployable system.
</Callout>

<h2 id="part-3-7">Part 3.7 — AI gateway, model routing, and multi-tenancy <Tag kind="core">★ CORE</Tag></h2>

<p>Any non-trivial AI product ends up putting a gateway between application code and model providers. Interviewers asking "how would you scale this across the company?" expect you to describe this layer.</p>

<h3 id="ai-gateway-responsibilities">Gateway responsibilities</h3>

<table>
  <tr><th scope="col">Responsibility</th><th scope="col">Why it lives here</th></tr>
  <tr><td>Provider abstraction</td><td>Swap Anthropic/OpenAI/Bedrock/in-house without changing app code</td></tr>
  <tr><td>Auth and key vaulting</td><td>App services hold app credentials; provider keys never leak past the gateway</td></tr>
  <tr><td>Per-tenant quotas and rate limits</td><td>Stops one team or customer from exhausting org-level rate limits</td></tr>
  <tr><td>Cost attribution</td><td>Token usage tagged by team, feature, environment for chargeback</td></tr>
  <tr><td>Caching</td><td>Exact-match and semantic cache for popular prompts</td></tr>
  <tr><td>Prompt and policy enforcement</td><td>Inject system prompts, redact PII, enforce content policies centrally</td></tr>
  <tr><td>Observability</td><td>Trace IDs, token counts, latencies, retries, fallbacks in one place</td></tr>
  <tr><td>Failover and circuit breaking</td><td>If primary provider degrades, route to secondary; trip circuit on error rate</td></tr>
</table>

<h3 id="gateway-diagram">Gateway architecture</h3>

<Ascii>{`  application services
        |
        v
  AI GATEWAY
    auth + tenant resolution
    request shaping (prompt template, redaction)
    cache lookup
        |  miss
        v
    model router
      +--- by intent (cheap classifier on prompt)
      +--- by cost budget for this tenant
      +--- by latency SLO (small model if user is waiting)
      +--- by capability (only some models do tool use, vision, JSON mode)
        |
        v
    provider client(s)        --->  OpenAI / Anthropic / Bedrock / vLLM cluster
        |
        v
    response normalization (unified schema, token usage, finish reasons)
        |
        v
    output guardrails
        |
        v
    cache write + audit log + metrics
        |
        v
    application

  side outputs:
    - usage events -> billing/metering
    - traces -> observability backend
    - flagged outputs -> review queue`}</Ascii>

<h3 id="caching-tiers">Caching tiers</h3>

<ul>
  <li><strong>Exact-match cache:</strong> hash of (model, prompt, params). High hit rate on repeated tool prompts and system messages.</li>
  <li><strong>Semantic cache:</strong> embed the query, look up nearest cached queries above a similarity threshold. Risky for personalized or stateful answers; great for FAQ-like traffic.</li>
  <li><strong>Provider-side prompt cache:</strong> Anthropic/OpenAI/Bedrock all expose a cache-breakpoint mechanism that reuses KV for stable prefixes; often the biggest single cost win for chat apps and agents.</li>
  <li><strong>Retrieval cache:</strong> memoize embedding + retrieval results for identical queries within a TTL.</li>
</ul>

<Callout variant="tip" title="Cache layering rule">
  When asked to cut LLM cost, name the layers in order: exact-match → provider prompt cache → retrieval cache → semantic cache → distillation to a smaller model. Each layer is cheaper to build than the next and usually buys 20–60% on its own.
</Callout>

<h3 id="multi-tenancy">Multi-tenancy patterns</h3>

<table>
  <tr><th scope="col">Concern</th><th scope="col">Design choice</th></tr>
  <tr><td>Data isolation</td><td>Per-tenant index/namespace in vector DB; row-level security in feature/profile stores; per-tenant encryption keys for regulated data</td></tr>
  <tr><td>Compute isolation</td><td>Shared model pool for most; dedicated endpoints for noisy/regulated tenants; separate clusters for "BYOC" deployments</td></tr>
  <tr><td>Quota fairness</td><td>Token-bucket per tenant with burst allowance; global circuit breaker for provider-level limits</td></tr>
  <tr><td>Prompt isolation</td><td>Never concatenate tenant-supplied text into another tenant's system prompt; treat user text as data, not instructions</td></tr>
  <tr><td>Model selection</td><td>Allowlist of models per tenant (some can't use frontier models for data-residency reasons)</td></tr>
  <tr><td>Audit and retention</td><td>Per-tenant retention policy; signed audit logs for regulated industries</td></tr>
</table>

<h3 id="rate-limiting-tokens">Rate limiting in token-shaped traffic</h3>

<p>Standard request-per-second limits don't fit LLMs because a single request can consume 100x more tokens than another. Use <strong>token-per-minute</strong> (TPM) and <strong>requests-per-minute</strong> (RPM) buckets together, mirroring how provider APIs charge.</p>

<Ascii>{`  on request:
    estimate input_tokens (count locally) + max_output_tokens (param)
    check: tenant TPM bucket has capacity?
    check: tenant RPM bucket has capacity?
    check: global provider TPM has capacity?
        any miss -> 429 with retry-after, or fall through to smaller/cheaper model

  on response:
    refund unused output tokens (we reserved max, used less)
    record actual usage for billing`}</Ascii>

<h2 id="part-4">Part 4 — Example: design a RAG assistant <Tag kind="neutral">EXAMPLE</Tag></h2>

<h3 id="goal-rag">Goal</h3>
<p>Build an internal enterprise assistant that answers employee questions using company documents with citations.</p>

<h3 id="requirements-rag">Requirements</h3>
<ul>
  <li>Answers should be grounded in internal knowledge.</li>
  <li>Return citations and document links.</li>
  <li>Support permissions: users should only see docs they can access.</li>
  <li>Latency target around 2–5 seconds for interactive chat.</li>
</ul>

<h3 id="api-rag">API sketch</h3>

```json
POST /chat
{
  "conversation_id": "c_123",
  "message": "What is our parental leave policy?"
}

Response:
{
  "answer": "...",
  "citations": [
    {"doc_id": "hr_policy_2026", "title": "Leave Policy", "chunk_id": "..."}
  ],
  "confidence": "medium",
  "trace_id": "tr_abc"
}
```

<h3 id="high-level-design-rag">High-level design</h3>
<Ascii>{`  Document sources -> ingestion pipeline -> chunking -> embeddings -> vector index
          |                                                    |
          |                                                    v
          +---------------------- metadata / ACLs --------> retriever

  User query -> API -> auth -> query rewrite (optional) -> retrieve top-k docs
             -> rerank (optional) -> prompt builder -> LLM -> answer + citations
             -> logs / feedback / eval`}</Ascii>

<h3 id="key-components-rag">Key components</h3>
<ul>
  <li><strong>Ingestion pipeline:</strong> pulls docs from Drive, Confluence, PDFs, tickets, wiki.</li>
  <li><strong>Parsing/chunking:</strong> split documents into useful chunks with metadata.</li>
  <li><strong>Embedding/indexing:</strong> create embeddings and store them in vector DB.</li>
  <li><strong>Metadata filters:</strong> enforce team, role, or document ACLs at retrieval time.</li>
  <li><strong>Retriever + reranker:</strong> retrieve top-k chunks, optionally rerank for relevance.</li>
  <li><strong>Prompt builder:</strong> inject user question + selected context + style rules.</li>
  <li><strong>LLM response:</strong> generate grounded answer with citations.</li>
</ul>

<h3 id="rag-ingestion-details">Ingestion details</h3>
<Ascii>{`  connectors
    |  (Drive, Confluence, SharePoint, S3, Git, tickets)
    v
  parse / OCR / clean
    |
    v
  chunk by structure
    |  title, heading path, owner, ACL, timestamp
    v
  embed chunks
    |
    +--> vector index
    +--> keyword index
    +--> metadata store
    +--> dead-letter queue for parse failures`}</Ascii>

<h3 id="rag-retrieval-stack">Retrieval stack</h3>
<table>
  <tr><th scope="col">Layer</th><th scope="col">Purpose</th><th scope="col">Notes</th></tr>
  <tr><td>Query rewrite</td><td>Turn follow-up into standalone query</td><td>Use conversation summary, not entire chat history</td></tr>
  <tr><td>Hybrid retrieval</td><td>Combine semantic and keyword search</td><td>Handles acronyms, names, exact policy terms</td></tr>
  <tr><td>ACL filtering</td><td>Prevent unauthorized chunks</td><td>Filter during retrieval, not after answer generation</td></tr>
  <tr><td>Reranking</td><td>Improve top-k precision</td><td>Useful when corpus is large/noisy; adds latency</td></tr>
  <tr><td>Context packing</td><td>Fit best evidence into token budget</td><td>Dedupe, order by relevance, preserve headings</td></tr>
</table>

<h3 id="tradeoffs-rag">Trade-offs to mention</h3>
<ul>
  <li><strong>Pure fine-tuning vs RAG:</strong> RAG is better when knowledge changes frequently.</li>
  <li><strong>Latency vs quality:</strong> reranking improves relevance but adds delay.</li>
  <li><strong>Chunk size:</strong> too small loses context; too large hurts retrieval precision.</li>
  <li><strong>Freshness:</strong> need incremental indexing or event-driven reindexing.</li>
</ul>

<h3 id="rag-evals">RAG evaluation</h3>
<table>
  <tr><th scope="col">Metric</th><th scope="col">Question it answers</th></tr>
  <tr><td>Retrieval recall@k</td><td>Did we retrieve the document that contains the answer?</td></tr>
  <tr><td>Context precision</td><td>Are the retrieved chunks actually relevant?</td></tr>
  <tr><td>Faithfulness / groundedness</td><td>Is the answer supported by retrieved context?</td></tr>
  <tr><td>Answer relevance</td><td>Did the answer address the user's question?</td></tr>
  <tr><td>Citation accuracy</td><td>Do links point to the evidence actually used?</td></tr>
  <tr><td>Permission leakage rate</td><td>Did unauthorized content appear?</td></tr>
</table>

<h3 id="rag-failure-modes">RAG failure modes</h3>
<ul>
  <li><strong>Missing document:</strong> connector or index freshness problem.</li>
  <li><strong>Bad chunking:</strong> answer spans chunks or tables were parsed poorly.</li>
  <li><strong>Wrong retrieval:</strong> embedding misses exact keyword or acronym.</li>
  <li><strong>Lost context:</strong> relevant chunk retrieved but dropped during context packing.</li>
  <li><strong>Hallucinated synthesis:</strong> model answers beyond supplied context.</li>
  <li><strong>ACL bug:</strong> retrieval sees data the user cannot access.</li>
</ul>

<div>
  <div>Good interview line:</div>
  <div>I would keep ingestion and indexing offline, and keep the online path limited to auth, retrieval, prompt construction, generation, and response validation. That keeps latency predictable while allowing the knowledge base to evolve independently.</div>
</div>

<h2 id="part-5">Part 5 — Example: design an agentic workflow system <Tag kind="neutral">EXAMPLE</Tag></h2>

<h3 id="goal-agent">Goal</h3>
<p>Design an AI system that can analyze a support ticket, fetch account data, query internal tools, propose a resolution, and optionally take approved actions.</p>

<h3 id="high-level-design-agent">High-level design</h3>
<Ascii>{`  Ticket / user request
        -> orchestrator
            -> planner / policy layer
            -> tool registry
            -> identity / permissions
            -> memory / state store
            -> LLM reasoning loop
            -> action executor
        -> human approval (for sensitive actions)
        -> final response + audit log`}</Ascii>

<h3 id="agent-state-machine">Agent state-machine view</h3>
<Ascii>{`  START
    |
    v
  understand goal
    |
    v
  plan steps ---- invalid/unsafe ----> refuse or ask human
    |
    v
  execute next tool
    |
    +--> tool failed? -> retry / alternate / escalate
    |
    +--> needs approval? -> pause -> human approves/denies
    |
    v
  update task state
    |
    +--> done? no -> execute next tool
    |
    v
  final answer + audit log`}</Ascii>

<h3 id="what-the-interviewer-wants-agent">What the interviewer wants to hear</h3>
<ul>
  <li><strong>Tool use is constrained:</strong> the model should not have unrestricted access.</li>
  <li><strong>State is explicit:</strong> task state, tool outputs, retries, and memory are stored outside the model.</li>
  <li><strong>Approval gates exist:</strong> high-risk actions need human confirmation.</li>
  <li><strong>Observability matters:</strong> trace every tool call, prompt, result, and failure.</li>
</ul>

<h3 id="key-design-choices-agent">Key design choices</h3>
<table>
  <tr><th scope="col">Choice</th><th scope="col">Recommended answer</th></tr>
  <tr><td>Planning</td><td>Use structured plans or state-machine/graph workflow, not free-form endless loops</td></tr>
  <tr><td>Tool access</td><td>Allowlisted tools with schemas, auth, and timeout budgets</td></tr>
  <tr><td>Memory</td><td>Session memory for current task, long-term memory only if it adds clear value</td></tr>
  <tr><td>Action safety</td><td>Human-in-the-loop for money movement, deletions, account changes</td></tr>
  <tr><td>Retries</td><td>Idempotent actions, bounded retries, circuit breakers</td></tr>
</table>

<h3 id="tool-contracts-agent">Tool contracts</h3>
<p>Tools should be typed, narrow, permission-aware, and observable. Avoid giving the model broad tools like <code>run_sql(any_query)</code> or <code>http_request(any_url)</code> unless heavily sandboxed.</p>

```json
{
  "name": "create_refund_case",
  "description": "Open a refund review case. Does not issue refund.",
  "input_schema": {
    "customer_id": "string",
    "order_id": "string",
    "reason": "string",
    "evidence_ids": ["string"]
  },
  "requires_approval": false,
  "timeout_ms": 2000,
  "idempotency_key": "conversation_id + order_id"
}
```

<h3 id="agent-observability">Agent observability</h3>
<ul>
  <li>Plan version and generated steps</li>
  <li>Tool selected, arguments, result, latency, error</li>
  <li>Permission decision and policy version</li>
  <li>Human approval decision and reviewer</li>
  <li>Loop count, token usage, total cost</li>
  <li>Final action IDs and rollback/compensation status</li>
</ul>

<h3 id="big-risk-agent">Big risk</h3>
<p>The main failure mode is not just hallucination — it is <strong>incorrect action</strong>. So the architecture should emphasize permissions, validation, and reversible workflows more than just answer quality.</p>

<Callout variant="warn" title="Interview trap">
  Do not design an agent as an infinite loop around an LLM. A production answer needs bounded iterations, state persistence, typed tools, policy checks, approval gates, idempotency, and traceability.
</Callout>

<h2 id="part-6">Part 6 — Example: design a recommendation system <Tag kind="neutral">EXAMPLE</Tag></h2>

<h3 id="goal-rec">Goal</h3>
<p>Recommend products, videos, or jobs personalized to each user.</p>

<h3 id="standard-two-stage-architecture">Standard two-stage architecture</h3>
<Ascii>{`  User activity / item metadata / context
        -> feature pipelines
        -> candidate generation
        -> top-N candidates
        -> ranking model
        -> final recommendations
        -> feedback loop (clicks, dwell, purchases)`}</Ascii>

<h3 id="rec-expanded-architecture">Expanded recommendation architecture</h3>
<Ascii>{`  OFFLINE
    events + catalog + user profiles
        -> feature pipelines
        -> embeddings / co-visitation / popularity tables
        -> candidate indexes
        -> train ranking model
        -> offline eval + model registry

  ONLINE
    user request
        -> fetch user/context features
        -> candidate generators in parallel
             - similar items
             - personalized ANN
             - trending/popular
             - business rules
        -> merge + dedupe + filter
        -> ranker
        -> diversity/exploration rules
        -> recommendations
        -> impression/click/purchase logs`}</Ascii>

<h3 id="why-two-stage">Why two-stage</h3>
<p>You usually cannot score millions of items with an expensive model on every request. So you:</p>
<ol>
  <li><strong>Generate candidates</strong> quickly using retrieval/ANN/heuristics/co-visitation.</li>
  <li><strong>Rank candidates</strong> with a stronger model using richer features.</li>
</ol>

<h3 id="data-sources-rec">Data sources</h3>
<ul>
  <li>User profile and history</li>
  <li>Item metadata</li>
  <li>Context features: time, device, location, session intent</li>
  <li>Feedback labels: clicks, likes, watch time, purchases</li>
</ul>

<h3 id="candidate-generation-rec">Candidate generation strategies</h3>
<table>
  <tr><th scope="col">Strategy</th><th scope="col">Good for</th><th scope="col">Weakness</th></tr>
  <tr><td>Popularity/trending</td><td>Cold start, robust fallback</td><td>Not personalized</td></tr>
  <tr><td>Collaborative filtering</td><td>Users/items with interaction history</td><td>Weak for new users/items</td></tr>
  <tr><td>Content similarity</td><td>New items with metadata/text/images</td><td>Can be narrow/repetitive</td></tr>
  <tr><td>Embedding ANN</td><td>Large catalog semantic matching</td><td>Needs embedding quality and index freshness</td></tr>
  <tr><td>Rules/business candidates</td><td>Promotions, compliance, inventory constraints</td><td>Can hurt relevance if overused</td></tr>
</table>

<h3 id="ranking-features-rec">Ranking features</h3>
<ul>
  <li><strong>User features:</strong> preferences, historical categories, price sensitivity, language.</li>
  <li><strong>Item features:</strong> category, age, quality score, inventory, creator/seller reputation.</li>
  <li><strong>Interaction features:</strong> user-item similarity, previous impressions, recency.</li>
  <li><strong>Context features:</strong> time, device, location, session query, entry surface.</li>
  <li><strong>Business/safety features:</strong> blocked categories, availability, policy flags.</li>
</ul>

<h3 id="production-points-rec">Production points to mention</h3>
<ul>
  <li><strong>Cold start:</strong> new users and new items need fallback strategies.</li>
  <li><strong>Freshness:</strong> trending items may need stream updates.</li>
  <li><strong>Exploration vs exploitation:</strong> do not overfit to existing popular items only.</li>
  <li><strong>Bias/fairness:</strong> recommendations can amplify popularity and creator imbalance.</li>
</ul>

<h3 id="rec-metrics">Recommendation metrics</h3>
<table>
  <tr><th scope="col">Metric</th><th scope="col">Use</th></tr>
  <tr><td>Precision@k / Recall@k</td><td>Offline relevance quality</td></tr>
  <tr><td>NDCG@k</td><td>Ranking quality with position weighting</td></tr>
  <tr><td>CTR / conversion / watch time</td><td>Online product impact</td></tr>
  <tr><td>Diversity / novelty</td><td>Avoid repetitive recommendations</td></tr>
  <tr><td>Coverage</td><td>How much of catalog gets exposure</td></tr>
  <tr><td>Guardrail metrics</td><td>Policy violations, unfair exposure, spam/abuse</td></tr>
</table>

<div>
  <div>Good interview line:</div>
  <div>I would separate offline feature generation and model training from online candidate retrieval and ranking. For online serving, I would cache partial results for heavy users and keep a simple popularity-based fallback path if the personalized ranker is unavailable.</div>
</div>

<h2 id="part-7">Part 7 — Example: design a fraud / anomaly detection system <Tag kind="neutral">EXAMPLE</Tag></h2>

<h3 id="goal-fraud">Goal</h3>
<p>Detect suspicious transactions in near-real-time and block or review them.</p>

<h3 id="architecture-fraud">Architecture</h3>
<Ascii>{`  Transaction event stream
        -> stream ingestion
        -> online feature enrichment
        -> rules engine + ML risk model
        -> risk score / decision
        -> approve | challenge | block | manual review
        -> investigator tools + feedback labels
        -> retraining pipeline`}</Ascii>

<h3 id="fraud-latency-path">Fraud latency path</h3>
<Ascii>{`  transaction request
      |
      v
  synchronous path, must be fast:
    validate -> online features -> rules + model -> decision
                                               |
                                               v
                               approve / challenge / block

  async path, can be slower:
    event stream -> graph features -> case linking -> investigator UI
                 -> confirmed labels -> retrain / rule tuning`}</Ascii>

<h3 id="good-answer-fraud">Good answer themes</h3>
<ul>
  <li><strong>Hybrid system:</strong> rules + ML, not ML alone.</li>
  <li><strong>Feature freshness:</strong> recent counts, recent devices, recent geos matter.</li>
  <li><strong>Low latency:</strong> online scoring often must finish in tens or hundreds of milliseconds.</li>
  <li><strong>Human feedback loop:</strong> investigator decisions create new labels.</li>
  <li><strong>Explainability:</strong> risk reasons should be visible to analysts.</li>
</ul>

<h3 id="fraud-features">Useful fraud features</h3>
<ul>
  <li>Transaction amount compared with user baseline</li>
  <li>Velocity: number/amount of transactions in last 1 min, 1 hour, 24 hours</li>
  <li>Device fingerprint and device age</li>
  <li>Geo distance from last known location</li>
  <li>Merchant/category risk</li>
  <li>Account age and recent profile changes</li>
  <li>Graph signals: shared device, shared card, shared address, suspicious cluster</li>
</ul>

<h3 id="fraud-modeling">Modeling approach</h3>
<table>
  <tr><th scope="col">Layer</th><th scope="col">Purpose</th></tr>
  <tr><td>Rules</td><td>Hard constraints, known attack patterns, compliance requirements</td></tr>
  <tr><td>Supervised model</td><td>Risk score from labeled historical fraud/non-fraud</td></tr>
  <tr><td>Anomaly model</td><td>Catch unusual behavior without labels</td></tr>
  <tr><td>Graph features</td><td>Detect coordinated behavior and shared entities</td></tr>
  <tr><td>Manual review</td><td>Handle uncertain cases and generate labels</td></tr>
</table>

<h3 id="tradeoff-fraud">Trade-off</h3>
<p>False positives hurt customers, false negatives cost money. A mature design may have multiple thresholds: auto-approve low risk, manual-review medium risk, auto-block very high risk.</p>

<Ascii>{`  risk score
  0.0 ------------------------------------------------------ 1.0
       approve        challenge / review          block
       low friction   gather more signal          high confidence

  Tune thresholds by business cost:
    false positive cost = angry customer / lost sale
    false negative cost = fraud loss / abuse / compliance risk`}</Ascii>

<h2 id="part-8">Part 8 — Example: design real-time voice AI <Tag kind="neutral">EXAMPLE</Tag></h2>

<h3 id="goal-voice">Goal</h3>
<p>Build a voice assistant that supports live conversation with low perceived latency.</p>

<h3 id="high-level-design-voice">High-level design</h3>
<Ascii>{`  Audio input
    -> streaming ASR
    -> partial transcript
    -> dialogue manager / LLM
    -> tool calls (optional)
    -> response text
    -> streaming TTS
    -> audio output`}</Ascii>

<h3 id="voice-session-architecture">Voice session architecture</h3>
<Ascii>{`  client microphone
      |
      v
  audio gateway / WebRTC
      |
      +--> voice activity detection
      +--> streaming ASR partials
               |
               v
          dialogue manager
               |
               +--> short-term conversation state
               +--> tool calls / retrieval
               +--> LLM response stream
               |
               v
          streaming TTS
               |
               v
          client speaker

  side channels:
    transcripts -> logs/evals
    latency metrics -> monitoring
    consent/PII policy -> governance`}</Ascii>

<h3 id="critical-points-voice">Critical points</h3>
<ul>
  <li><strong>Streaming everywhere:</strong> ASR, model output, and TTS should stream.</li>
  <li><strong>Turn-taking:</strong> interruption handling and barge-in matter a lot.</li>
  <li><strong>Latency budget:</strong> break down ASR, reasoning, tool calls, and TTS.</li>
  <li><strong>Fallbacks:</strong> if one model is slow, use a smaller one or shorter response mode.</li>
</ul>

<h3 id="voice-hard-parts">Voice hard parts</h3>
<table>
  <tr><th scope="col">Problem</th><th scope="col">Design response</th></tr>
  <tr><td>Barge-in</td><td>Allow user to interrupt TTS; cancel current generation and update state</td></tr>
  <tr><td>Partial transcripts</td><td>Use stable partials for early intent, wait for final transcript for risky actions</td></tr>
  <tr><td>Noisy audio</td><td>Noise suppression, confidence thresholds, clarification prompts</td></tr>
  <tr><td>Tool latency</td><td>Give short acknowledgement, run tool, stream final answer</td></tr>
  <tr><td>Privacy</td><td>Consent, retention policy, PII redaction in transcripts</td></tr>
</table>

<h3 id="latency-budget-example-voice">Example latency budget</h3>
<table>
  <tr><th scope="col">Stage</th><th scope="col">Target</th></tr>
  <tr><td>Streaming ASR partials</td><td>100–300 ms</td></tr>
  <tr><td>Dialogue/model first token</td><td>300–800 ms</td></tr>
  <tr><td>TTS start</td><td>200–500 ms</td></tr>
  <tr><td>Total perceived response start</td><td>&lt; 1.5 sec preferred</td></tr>
</table>

<p>For voice, perceived responsiveness often matters more than final full-answer quality.</p>

<h2 id="part-8-5">Part 8.5 — More common interview blueprints <Tag kind="neutral">EXAMPLE</Tag></h2>

<h3 id="blueprint-document-processing">Blueprint: document processing / extraction</h3>
<p>Prompt: "Design a system that extracts structured fields from invoices, contracts, or medical forms."</p>

<Ascii>{`  document upload
      -> object store
      -> OCR / layout parser
      -> document classifier
      -> field extractor model / LLM
      -> schema validation
      -> confidence scoring
      -> human review for low confidence
      -> structured record + audit trail`}</Ascii>

<ul>
  <li><strong>Key trade-off:</strong> automation rate vs extraction accuracy.</li>
  <li><strong>Hard part:</strong> tables, handwriting, scans, domain-specific fields, hallucinated values.</li>
  <li><strong>Metrics:</strong> field-level precision/recall, exact-match rate, review rate, turnaround time.</li>
  <li><strong>Safety:</strong> never invent missing fields; mark unknown with confidence.</li>
</ul>

<h3 id="blueprint-semantic-search">Blueprint: semantic search</h3>
<p>Prompt: "Design search over a large internal knowledge base or product catalog."</p>

<Ascii>{`  query
    -> query understanding / spell correction / filters
    -> hybrid retrieval
         + keyword index
         + vector index
         + business filters
    -> reranker
    -> snippet/highlight generation
    -> results page
    -> click logs + query reformulation analytics`}</Ascii>

<ul>
  <li><strong>Key trade-off:</strong> exact keyword precision vs semantic recall.</li>
  <li><strong>Hard part:</strong> ranking, freshness, permissions, synonyms, acronyms.</li>
  <li><strong>Metrics:</strong> NDCG, MRR, zero-result rate, click-through, reformulation rate.</li>
</ul>

<h3 id="blueprint-content-moderation">Blueprint: content moderation</h3>
<p>Prompt: "Design an AI system to detect harmful or policy-violating content."</p>

<Ascii>{`  user content
      -> lightweight rule checks
      -> ML classifier / moderation model
      -> policy decision engine
          | low risk      -> allow
          | uncertain     -> queue for review
          | high risk     -> block / limit distribution
      -> reviewer feedback
      -> policy + model updates`}</Ascii>

<ul>
  <li><strong>Key trade-off:</strong> safety vs false positives and creator/user trust.</li>
  <li><strong>Hard part:</strong> context, adversarial language, policy changes, multilingual content.</li>
  <li><strong>Metrics:</strong> precision/recall by policy category, appeal overturn rate, review latency.</li>
  <li><strong>Safety:</strong> policy versioning and explainable enforcement decisions.</li>
</ul>

<h3 id="blueprint-personalization-copilot">Blueprint: personalized copilot</h3>
<p>Prompt: "Design a copilot that personalizes answers based on user history and preferences."</p>

<Ascii>{`  user request
      -> identity + consent check
      -> retrieve user profile / preferences
      -> retrieve task context
      -> assemble minimal personalized prompt
      -> model response
      -> user feedback
      -> memory write policy
           - what to store?
           - for how long?
           - can user inspect/delete it?`}</Ascii>

<ul>
  <li><strong>Key trade-off:</strong> helpful personalization vs privacy and surprise.</li>
  <li><strong>Hard part:</strong> stale memories, wrong assumptions, sensitive attributes.</li>
  <li><strong>Metrics:</strong> task success, user correction rate, memory usefulness, deletion requests.</li>
</ul>

<h3 id="blueprint-forecasting">Blueprint: demand forecasting</h3>
<p>Prompt: "Design a system that forecasts demand, traffic, or inventory needs."</p>

<Ascii>{`  historical events + calendar + promotions + external signals
      -> data validation
      -> feature generation
      -> forecasting model
      -> prediction intervals
      -> business constraints / overrides
      -> dashboard + API
      -> actuals arrive later
      -> backtesting + drift monitoring`}</Ascii>

<ul>
  <li><strong>Key trade-off:</strong> model complexity vs interpretability and stability.</li>
  <li><strong>Hard part:</strong> seasonality, promotions, holidays, sparse products, cold starts.</li>
  <li><strong>Metrics:</strong> MAPE, WAPE, RMSE, calibration of prediction intervals.</li>
</ul>

<h3 id="blueprint-code-copilot">Blueprint: code copilot / IDE assistant</h3>
<p>Prompt: "Design an IDE autocomplete and chat assistant like Copilot or Cursor."</p>

<Ascii>{`  IDE event (keystroke / chat / accept)
      -> client-side debounce + context window builder
           - current file (cursor +/- N lines)
           - open tabs, recently edited files
           - repo-level retrieval (BM25 over symbols + embedding over chunks)
           - LSP signals (types, definitions, diagnostics)
      -> server: prompt assembly + speculative cache lookup
      -> small fast model (FIM-trained) for completions
         large model for chat / refactor
      -> stream tokens back
      -> client: ghost-text render, telemetry on accept/reject
      -> offline: train acceptance reward model, retrain ranker`}</Ascii>

<ul>
  <li><strong>Key trade-off:</strong> latency vs context size; completions need ~200ms TTFT or users disable the feature.</li>
  <li><strong>Hard part:</strong> repo context selection (which files to send), FIM (fill-in-the-middle) prompt format, deduping low-value suggestions.</li>
  <li><strong>Metrics:</strong> accept rate, retained-in-IDE-after-N-seconds, characters-per-accepted-suggestion, server cost per accept.</li>
  <li><strong>Safety:</strong> license-aware filtering of training and outputs; never echo secrets pasted into prompt.</li>
</ul>

<h3 id="blueprint-image-generation">Blueprint: image generation service</h3>
<p>Prompt: "Design a text-to-image generation service like Midjourney or DALL-E."</p>

<Ascii>{`  prompt + style + reference image (optional)
      -> safety: prompt classifier (CSAM, IP, named persons)
      -> prompt rewriter (expand style, add negative prompts)
      -> queue (image gen is seconds-to-minutes, not interactive)
      -> GPU worker pool (batched diffusion)
           - choose model variant by tier (fast / quality)
           - apply LoRAs / control nets if requested
      -> output safety: NSFW classifier, watermark, C2PA signing
      -> object store + CDN
      -> notify client (websocket / poll)
      -> feedback: upvotes, regenerations, reports`}</Ascii>

<ul>
  <li><strong>Key trade-off:</strong> latency (steps, resolution) vs quality vs GPU cost.</li>
  <li><strong>Hard part:</strong> async UX (long jobs), abuse prevention, copyright and likeness policy, GPU spot-instance reliability.</li>
  <li><strong>Metrics:</strong> queue wait, success rate, regeneration rate, safety filter precision/recall.</li>
</ul>

<h3 id="blueprint-multimodal-extraction">Blueprint: multimodal document understanding</h3>
<p>Prompt: "Design a system that answers questions over PDFs that include text, tables, and figures."</p>

<Ascii>{`  PDF upload
      -> layout parser (Mathpix / Unstructured / proprietary)
           - text blocks + reading order
           - table extraction -> structured rows
           - figure crops -> stored separately
      -> per-element embeddings
           - text -> text embedding
           - figure -> CLIP / vision-language embedding
           - table -> serialized cells + text embedding
      -> index (vector + metadata: page, element type)
      -> query path: hybrid retrieval -> rerank -> VLM
         (vision-language model sees crops + text together)
      -> answer with element-level citations (page, bbox)`}</Ascii>

<ul>
  <li><strong>Key trade-off:</strong> parsing fidelity vs ingestion latency and cost.</li>
  <li><strong>Hard part:</strong> tables that span pages, figure-text alignment, multi-column layouts, handwritten annotations.</li>
  <li><strong>Metrics:</strong> answer accuracy stratified by element type, table-cell exactness, bbox citation precision.</li>
</ul>

<h3 id="blueprint-ads-ranking">Blueprint: ads / sponsored content ranking</h3>
<p>Prompt: "Design a system that ranks ads for a feed or search results page."</p>

<Ascii>{`  request (user, context, query/feed slot)
      -> retrieval: targeting filters (campaign, budget remaining, eligibility)
      -> candidate generation: bidding-aware ANN over ad embeddings
      -> pCTR / pCVR model (online inference, strict latency budget)
      -> auction: bid * pCTR * quality_score (eCPM ranking)
      -> pacing / budget controller (offline + online feedback)
      -> impression logging, attributed conversions
      -> offline: train pCTR, calibrate, detect click fraud, fairness audits`}</Ascii>

<ul>
  <li><strong>Key trade-off:</strong> revenue (eCPM) vs user experience vs advertiser ROI.</li>
  <li><strong>Hard part:</strong> calibration of pCTR (must reflect true probability, not just rank well), budget pacing, position bias in training data.</li>
  <li><strong>Metrics:</strong> revenue per mille (RPM), CTR, advertiser ROAS, calibration error, budget utilization.</li>
</ul>

<h2 id="part-9">Part 9 — Safety, evaluation, observability, and cost <Tag kind="core">★ CORE</Tag></h2>

<h3 id="evaluation">Evaluation</h3>
<ul>
  <li><strong>Offline evals:</strong> benchmark datasets, replay sets, golden prompts, ranking metrics.</li>
  <li><strong>Online evals:</strong> A/B tests, user satisfaction, conversion, resolution rate.</li>
  <li><strong>Human review:</strong> especially for correctness, harmful outputs, and action safety.</li>
</ul>

<h3 id="eval-layering">Layered evaluation</h3>
<p>Evaluate each layer separately, then evaluate the full end-to-end system. This helps you localize failures.</p>

<Ascii>{`  input quality eval
        |
        v
  retrieval / feature eval
        |
        v
  model output eval
        |
        v
  policy / safety eval
        |
        v
  product outcome eval

  Example RAG failure:
    bad answer could be retrieval failure, prompt failure,
    model failure, citation failure, or stale source data.`}</Ascii>

<h3 id="eval-dataset-design">Eval dataset design</h3>
<table>
  <tr><th scope="col">Slice</th><th scope="col">Why include it</th></tr>
  <tr><td>Common happy path</td><td>Protect core user experience</td></tr>
  <tr><td>Edge cases</td><td>Catch rare but important failures</td></tr>
  <tr><td>Adversarial prompts</td><td>Test prompt injection, jailbreaks, unsafe requests</td></tr>
  <tr><td>Permission cases</td><td>Ensure users cannot access forbidden content</td></tr>
  <tr><td>Freshness cases</td><td>Verify recently changed docs/features are reflected</td></tr>
  <tr><td>Regression cases</td><td>Examples from previous production failures</td></tr>
</table>

<h3 id="llm-as-judge">LLM-as-judge</h3>
<p>LLM judges are useful for scale, but they need calibration. Use explicit rubrics, spot-check with humans, and keep judge prompts/versioning stable.</p>

```
Rubric example:
Score 1-5 on faithfulness.
5 = every claim is directly supported by supplied evidence.
3 = mostly supported, but some vague or weakly supported claims.
1 = answer contradicts evidence or invents important facts.
```

<Callout variant="warn" title="Eval warning">
  Never rely only on aggregate eval scores. Segment by query type, user group, language, document source, risk level, and model version. Many serious regressions hide inside a good-looking average.
</Callout>

<h3 id="observability">Observability</h3>
<p>In AI systems, logs are not enough. You usually want:</p>
<ul>
  <li>request traces</li>
  <li>model chosen</li>
  <li>prompt/version</li>
  <li>retrieved context IDs</li>
  <li>tool calls and durations</li>
  <li>token usage / compute cost</li>
  <li>user feedback and failure labels</li>
</ul>

<h3 id="observability-diagram">Observability diagram</h3>
<Ascii>{`  request trace
    span: api
    span: auth
    span: retrieval
      attributes: index_version, top_k, doc_ids, scores
    span: reranker
    span: model_call
      attributes: model, prompt_version, tokens_in, tokens_out, cost
    span: guardrails
      attributes: policy_version, decision
    span: tool_call(s)
    span: response

  dashboards:
    latency p50/p95/p99
    cost per route/user/team
    error and fallback rate
    eval quality over time
    drift / freshness / stale index alerts`}</Ascii>

<h3 id="safety-and-governance">Safety and governance</h3>
<ul>
  <li>PII detection and redaction</li>
  <li>content moderation</li>
  <li>policy enforcement for actions and data access</li>
  <li>audit logs for regulated workflows</li>
  <li>dataset and model versioning</li>
</ul>

<h3 id="safety-layers">Safety layers</h3>
<Ascii>{`  user input
      |
      v
  input checks
    - prompt injection
    - harmful request
    - PII / secrets
    - authorization
      |
      v
  model / agent / tool execution
      |
      v
  output checks
    - groundedness
    - PII leakage
    - policy violation
    - schema validation
      |
      v
  action gate
    - auto-allow
    - human approval
    - refuse
      |
      v
  audit log`}</Ascii>

<h3 id="cost-controls">Cost controls</h3>
<ul>
  <li>cache common responses or retrieved context</li>
  <li>route easy queries to smaller/cheaper models</li>
  <li>use async pipelines for heavy jobs</li>
  <li>truncate irrelevant context</li>
  <li>batch where possible</li>

<h3 id="cost-breakdown">Cost breakdown</h3>
<table>
  <tr><th scope="col">Cost source</th><th scope="col">Controls</th></tr>
  <tr><td>LLM input tokens</td><td>Context pruning, prompt compression, retrieval precision</td></tr>
  <tr><td>LLM output tokens</td><td>Concise modes, streaming stop conditions, answer length limits</td></tr>
  <tr><td>Multiple model calls</td><td>Routing, caching, fewer agent loops, batch evals offline</td></tr>
  <tr><td>Vector/search infrastructure</td><td>Index compaction, quantization, TTLs for transient data</td></tr>
  <tr><td>Human review</td><td>Confidence thresholds, active learning, reviewer tooling</td></tr>
  <tr><td>GPU serving</td><td>Batching, quantization, autoscaling, smaller model distillation</td></tr>
</table>

<Callout variant="warn" title="A common weak answer">
  Saying "we'll just use GPT-4 for everything" is not a system design answer. A strong answer includes model routing, fallback behavior, caching, observability, and evaluation strategy.
</Callout>

<h2 id="part-9-5">Part 9.5 — GPU capacity planning and inference economics <Tag kind="core">★ CORE</Tag></h2>

<p>If the interviewer asks "how many GPUs?" or "what does this cost at 1M users?", they want a back-of-envelope grounded in real numbers. Memorize a few anchor figures and a derivation pattern.</p>

<h3 id="gpu-anchors">Anchor figures to remember (2025-era)</h3>

<table>
  <tr><th scope="col">GPU</th><th scope="col">VRAM</th><th scope="col">Mem BW</th><th scope="col">Rough use</th></tr>
  <tr><td>A100 80GB</td><td>80 GB HBM2e</td><td>~2 TB/s</td><td>13B–70B serving (with TP); workhorse</td></tr>
  <tr><td>H100 80GB</td><td>80 GB HBM3</td><td>~3.4 TB/s</td><td>Frontier serving and training; FP8 support</td></tr>
  <tr><td>H200 / B200</td><td>141 GB / 192 GB</td><td>4.8+ TB/s</td><td>Frontier 100B+ models, very long context</td></tr>
  <tr><td>L40S / L4</td><td>48 GB / 24 GB</td><td>~864 GB/s / 300 GB/s</td><td>Cost-efficient inference for &lt; 13B models, embedding</td></tr>
</table>

<h3 id="memory-budget">Memory budget on a single GPU</h3>

<Ascii>{`  total VRAM (e.g. 80 GB)
    - model weights        (params * bytes_per_param)
    - activations          (small at inference)
    - KV cache             (the big variable)
    - framework overhead
  = headroom for concurrent requests

  example: 70B model, fp16 weights
    weights: 70e9 * 2  = 140 GB  -> needs TP across 2x80GB or quantize
    int4 weights: 70e9 * 0.5 = ~35 GB -> fits one 80GB, plenty of KV headroom

  example: 8B model, fp16 weights, 80GB GPU
    weights:  ~16 GB
    headroom: ~64 GB
    KV per token (Llama-3-8B):  ~128 KB
    at 8k context -> ~1 GB/req -> ~60 concurrent requests`}</Ascii>

<h3 id="throughput-derivation">Throughput derivation pattern</h3>

<Ascii>{`  Step 1: pick a target model and quantization
  Step 2: compute max concurrent requests = headroom / (KV per token * avg seq_len)
  Step 3: measure or look up tokens/sec/GPU at that concurrency
            (typical: 8B fp16 ~ 3-6k tok/s; 70B int4 ~ 1-2k tok/s on H100)
  Step 4: tokens/day = tok/s * 86,400
  Step 5: divide by tokens/day from workload estimate -> GPU count
  Step 6: multiply by ~1.5x for peak headroom and ~1.2x for failures/maintenance`}</Ascii>

<h3 id="worked-gpu-example">Worked example: chatbot at 1M DAU</h3>

<Ascii>{`  Workload:
    1M DAU * 6 sessions/day * 4 turns * 800 output tokens = ~19B output tokens/day
    Plus input tokens ~3x output during prefill (but prefill is cheap with prefix cache)

  Serving choice: Llama-3-70B int4, H100, vLLM
    decode throughput per H100 ~= 1,500 tok/s in batched steady state
    daily tokens per H100      ~= 1,500 * 86,400 ~= 130M tokens

  GPUs needed for decode:
    19B / 130M ~= 146 H100s steady state
    peak (3x avg) -> 440 H100s, or burst to provider API for overflow

  Cost order of magnitude (rented H100 ~ $2-3/hr):
    146 * 24 * 2.5 ~= $8,760/day steady, ~$3.2M/year
    At $3 per million tokens hosted equivalent: 19B * $3/M = $57k/day
    Self-hosting wins at this scale; below ~10B tok/day, hosted is usually cheaper.

  Levers if budget is tight:
    - speculative decoding -> 1.5-2x throughput
    - smaller model for easy queries (router) -> 30-60% of traffic offloaded
    - prefix cache + answer cache -> 20-40% of input tokens skipped
    - distill 70B answers into 8B for narrow domains`}</Ascii>

<Callout variant="tip" title="When to self-host">
  Rule of thumb: below ~5–10B tokens/day, the per-token cost of a hosted API beats running your own GPUs once you factor on-call, capacity headroom, and engineer time. Above that, self-hosting (or reserved cloud capacity) usually wins — and you also get latency, privacy, and customization control. Say this trade-off explicitly when asked "build vs buy."
</Callout>

<h3 id="autoscaling-gpu">Autoscaling GPU workloads</h3>

<ul>
  <li><strong>Cold start is the enemy:</strong> loading a 70B model takes 1–5 minutes. Pre-warm pools; don't scale to zero for latency-sensitive tiers.</li>
  <li><strong>Scale on tokens, not requests:</strong> queue depth in tokens or expected decode-seconds is a better signal than HTTP RPS.</li>
  <li><strong>Right-size by tier:</strong> separate pools for premium (low latency, low utilization) and batch (high utilization, queued).</li>
  <li><strong>Spot instances for batch and training only:</strong> reclaim risk is unacceptable for synchronous serving unless you have hot standby capacity.</li>
</ul>

<h2 id="part-12">Part 12 — Anti-patterns that fail AI system design interviews <Tag kind="concept">◆ CONCEPT</Tag></h2>

<p>These are the moves interviewers flag as junior. Read them once before any AI design round.</p>

<table>
  <tr><th scope="col">Anti-pattern</th><th scope="col">Why it fails</th><th scope="col">What to say instead</th></tr>
  <tr><td>"Use GPT-4 / Claude for everything"</td><td>No routing, no cost story, no fallback</td><td>Tier by intent and risk; small model first, large model on escalation</td></tr>
  <tr><td>Jumping to architecture without clarifying</td><td>Misses the actual product constraint</td><td>Spend 3–5 min on users, mode, risk, latency, scale, success metric</td></tr>
  <tr><td>"Just embed it and put it in a vector DB"</td><td>Ignores hybrid retrieval, ACLs, chunking, freshness</td><td>Hybrid (BM25 + dense) + reranker + ACL filter + incremental ingestion</td></tr>
  <tr><td>Infinite agent loop with broad tools</td><td>Unbounded cost, unsafe actions, no observability</td><td>Bounded steps, typed tools, idempotency, approval gates, audit log</td></tr>
  <tr><td>Treating prompts as ephemeral</td><td>No rollback, no eval, no incident response</td><td>Versioned prompts in a registry alongside models and indexes</td></tr>
  <tr><td>"We'll evaluate with vibes / spot checks"</td><td>Quality regressions ship silently</td><td>Layered evals: retrieval, output, safety, product outcome; segment by slice</td></tr>
  <tr><td>Online path doing training-time work</td><td>Latency and cost explode</td><td>Push embedding, indexing, feature recompute offline; cache aggressively</td></tr>
  <tr><td>One global rate limit on requests</td><td>Doesn't protect against a single tenant burning all tokens</td><td>Per-tenant TPM + RPM, plus global circuit breaker per provider</td></tr>
  <tr><td>Skipping permission checks at retrieval</td><td>Data leakage from the index</td><td>Filter ACLs during retrieval, not after generation</td></tr>
  <tr><td>"We'll fine-tune to fix it"</td><td>Slow loop, wrong tool for knowledge problems</td><td>Climb the ladder: prompt → RAG → LoRA → DPO → full FT, only if needed</td></tr>
  <tr><td>No drift or freshness monitoring</td><td>Silent quality decay on changing data</td><td>Index-age dashboards, feature freshness SLAs, periodic re-evals</td></tr>
  <tr><td>"Hallucinations are an LLM problem, not a system problem"</td><td>Abdicates the design</td><td>Ground with retrieval, validate with rubric, gate risky outputs with humans</td></tr>
  <tr><td>Treating LLM output as instruction-safe input to next tool</td><td>Prompt injection chains</td><td>Schema-validate tool args, restrict tool capabilities, sandbox execution</td></tr>
  <tr><td>One giant prompt that does everything</td><td>Impossible to debug or roll back partial regressions</td><td>Decompose into classifier → retriever → composer → validator stages</td></tr>
</table>

<Callout variant="tip" title="Final framing">
  The senior signal in AI system design is treating the LLM as one stage in a versioned, monitored, multi-stage pipeline — not as a magic box. Show that you separate online from offline, that you name specific algorithms and trade-offs, and that you can reason about latency, cost, and safety as concrete numbers and gates. That combination is what passes a staff-level bar.
</Callout>

<h2 id="part-13">Part 13 — Training infrastructure at scale <Tag kind="core">★ CORE</Tag></h2>

<p>Lead-level interviews probe whether you can reason about training systems, not just serving. You won't be asked to derive backprop, but you will be asked how a 70B model gets trained on 1k+ GPUs without melting, what happens when a node dies mid-run, and where the bottlenecks actually live.</p>

<h3 id="training-memory-budget">Training memory: where it actually goes</h3>

<p>Inference memory is dominated by weights and KV cache. Training memory is a different beast — gradients, optimizer states, and activations each rival the model size.</p>

<Ascii>{`  For Adam/AdamW with mixed precision (bf16 compute, fp32 master):
    weights (bf16)            : 2 bytes/param
    gradients (bf16)          : 2 bytes/param
    optimizer state m, v (fp32): 8 bytes/param
    master weights (fp32)     : 4 bytes/param
    --------------------------------------------
    total                     : ~16 bytes/param

  70B model -> ~1.1 TB just for state, before any activations.
  H100 has 80 GB. That's why training is inherently distributed.

  Activation memory (per layer, per token):
    O(batch * seq_len * hidden_dim * n_layers)
    For 70B at seq_len=8192, batch=4 micro: 100s of GB more.
    Mitigated by gradient (activation) checkpointing.`}</Ascii>

<h3 id="parallelism-strategies">The 4D parallelism cheat sheet</h3>

<table>
  <tr><th scope="col">Strategy</th><th scope="col">What gets sharded</th><th scope="col">Comm pattern</th><th scope="col">When to use</th></tr>
  <tr><td>Data parallel (DP)</td><td>Batch across replicas</td><td>All-reduce gradients per step</td><td>Default; scales linearly until comm dominates</td></tr>
  <tr><td>Tensor parallel (TP)</td><td>Each layer's matmuls split across GPUs</td><td>All-reduce inside every layer</td><td>Model doesn't fit on one GPU; needs NVLink</td></tr>
  <tr><td>Pipeline parallel (PP)</td><td>Layer groups across nodes</td><td>Point-to-point activations between stages</td><td>Cross-node scaling; needs careful microbatching</td></tr>
  <tr><td>Sequence parallel (SP)</td><td>Sequence dim of activations</td><td>Reduce-scatter / all-gather</td><td>Long-context training (32k+)</td></tr>
  <tr><td>Expert parallel (EP)</td><td>MoE experts across GPUs</td><td>All-to-all for token routing</td><td>Only for MoE architectures</td></tr>
  <tr><td>Context parallel (CP)</td><td>Attention computed in chunks across GPUs</td><td>Ring all-reduce on K/V</td><td>Very long context (128k+, ring attention)</td></tr>
</table>

<Ascii>{`  Typical 3D recipe for a 70B dense model on 512 H100s:
    TP = 8   (inside one DGX node, NVLink)
    PP = 8   (across nodes, IB or RoCE)
    DP = 8   (remaining replicas for throughput)
    8 * 8 * 8 = 512 GPUs

  Microbatching for pipeline:
    global batch = micro_batch * grad_accum * DP
    grad_accum must be >= PP to keep the pipeline full (otherwise bubbles)
    1F1B (one-forward-one-backward) interleaved schedule reduces bubble`}</Ascii>

<h3 id="zero-fsdp">ZeRO / FSDP: the memory unlock</h3>

<p>ZeRO (DeepSpeed) and FSDP (PyTorch) shard optimizer state, gradients, and weights across the data-parallel group. Conceptually they trade more communication for dramatically less per-GPU memory.</p>

<table>
  <tr><th scope="col">Stage</th><th scope="col">What's sharded</th><th scope="col">Per-GPU memory cost</th><th scope="col">Comm overhead</th></tr>
  <tr><td>ZeRO-1</td><td>Optimizer state</td><td>~8x reduction on optimizer</td><td>Slight (reduce-scatter)</td></tr>
  <tr><td>ZeRO-2</td><td>Optimizer + gradients</td><td>~4x further</td><td>Modest</td></tr>
  <tr><td>ZeRO-3 / FSDP</td><td>Optimizer + gradients + weights</td><td>~Nx (N = DP size)</td><td>All-gather weights per fwd/bwd pass</td></tr>
  <tr><td>ZeRO-Infinity</td><td>+ CPU/NVMe offload</td><td>Train far larger than VRAM</td><td>Much slower; for research, not production</td></tr>
</table>

<h3 id="checkpointing">Checkpointing and fault tolerance</h3>

<ul>
  <li><strong>Async checkpointing:</strong> snapshot GPU state to host, write to object store from CPU. Foreground training continues. PyTorch's DCP, Megatron's distributed checkpointer.</li>
  <li><strong>Cadence:</strong> typical 30 min – 4 hours depending on cluster MTBF. Cost of a restart = (interval / 2) + restart overhead.</li>
  <li><strong>Sharded checkpoints:</strong> each rank writes its shard; replay tools resharded on restore (lets you change parallelism on resume).</li>
  <li><strong>Resilient training:</strong> torchelastic / Megatron-LM with auto-replace of dead nodes; spot/preemptible instances need extra care.</li>
</ul>

<Ascii>{`  Failure math at scale:
    Per-GPU MTBF ~ 10,000 hours
    Cluster of 1,024 GPUs -> expected failure every ~10 hours
    -> checkpoint every 1-2 hours, or lose >5% of compute to restarts

  Common failure modes:
    - GPU ECC errors (silent data corruption -> NaN losses)
    - NVLink/IB transient errors
    - PSU / cooling events
    - Stragglers (one slow GPU drags global step latency)`}</Ascii>

<h3 id="training-data-pipeline">Training data pipeline</h3>

<Ascii>{`  Raw sources (web crawl, code, books, internal data)
    -> language ID + quality filtering (Gopher rules, FastText)
    -> dedup
         - exact (hash)
         - near-dup (MinHash LSH at document and paragraph level)
    -> PII redaction (regex + NER)
    -> decontamination against eval sets (n-gram overlap check)
    -> domain tagging + sampling weights
    -> tokenization (BPE/SentencePiece) into shards
    -> versioned dataset in object store with manifest + lineage
    -> streamed via WebDataset / Mosaic StreamingDataset
    -> per-rank deterministic shuffle with seed in checkpoint`}</Ascii>

<h3 id="training-observability">Training observability</h3>

<ul>
  <li><strong>Loss curves, gradient norms, weight norms</strong> per layer — diverging norms predict instability hours before NaN.</li>
  <li><strong>Throughput in tokens/sec/GPU and MFU</strong> (model FLOPs utilization) — 40–60% MFU on H100 is healthy; below 30% means a comm or data bottleneck.</li>
  <li><strong>Loss spike alerting</strong> with automatic rollback to last good checkpoint and learning-rate reduction.</li>
  <li><strong>Per-rank profiling</strong> for stragglers (NCCL kernel times, host-side dataloader latency).</li>
  <li><strong>Eval during training</strong> on a frozen holdout every N steps, not just at end — catches overfitting to recent data shards.</li>
</ul>

<Callout variant="warn" title="The hidden cost of failed runs">
  At 1,000+ GPUs, a single bad config (wrong learning rate schedule, broken data shard, NaN in mixed precision) can burn $50k–500k before someone notices. Lead-level answers mention dry-run policies, automatic loss-spike detection, deterministic restart, and human review gates before launching multi-week runs.
</Callout>

<h3 id="post-training-pipelines">Post-training: SFT, DPO, RLHF</h3>

<Ascii>{`  Base model
    -> SFT (supervised fine-tune on curated instruction data)
         dataset: 10k - 1M high-quality (prompt, response) pairs
         loss: standard next-token, masked on prompt tokens
    -> Preference data collection
         pairs of (chosen, rejected) responses from human raters or stronger model
    -> DPO / KTO / IPO (direct preference optimization, no reward model)
         OR
    -> Reward model training -> PPO/RLHF rollout
         PPO is finicky at scale; most teams now ship DPO first
    -> Safety tuning (rule-based + adversarial red team data)
    -> Eval gauntlet (capability + safety + regression)
    -> Release candidate`}</Ascii>

<h3 id="hardware-network-topology">Cluster and network topology</h3>

<ul>
  <li><strong>Intra-node:</strong> NVLink/NVSwitch — 600–900 GB/s between GPUs in a DGX/HGX box. TP lives here.</li>
  <li><strong>Inter-node:</strong> InfiniBand NDR/HDR or RoCE — 400 Gbps per NIC, often multiple NICs per node. PP/DP lives here.</li>
  <li><strong>Topology matters:</strong> rail-aligned fat-tree (one rail per NIC) keeps all-reduce collectives on dedicated links; blocking ratios under 1:1 hurt at scale.</li>
  <li><strong>Storage:</strong> NVMe-backed parallel filesystem (Weka, Lustre) for dataset streaming + checkpoint writes; object store (S3/GCS) for archive.</li>
</ul>

<h2 id="part-13-5">Part 13.5 — Advanced inference: MoE, long context, reasoning models <Tag kind="concept">◆ CONCEPT</Tag></h2>

<h3 id="moe-serving">Mixture-of-Experts serving</h3>

<p>MoE models (Mixtral, DeepSeek-V3, Grok, Llama-4) have far more parameters than active compute per token. They are cheaper to serve at quality but harder to operate.</p>

<table>
  <tr><th scope="col">Aspect</th><th scope="col">Dense model</th><th scope="col">MoE model</th></tr>
  <tr><td>Params vs compute</td><td>All params active per token</td><td>Top-k experts (usually 2 of 8–256) active</td></tr>
  <tr><td>Memory</td><td>Modest weights, big KV</td><td>Huge weights (must hold all experts), normal KV</td></tr>
  <tr><td>Throughput</td><td>Predictable batched</td><td>Imbalanced; depends on routing</td></tr>
  <tr><td>Parallelism</td><td>TP / PP</td><td>Add expert parallel (EP); all-to-all dominant cost</td></tr>
</table>

<Ascii>{`  MoE failure modes the interviewer expects you to name:
    - Routing collapse (a few experts get all traffic, rest are dead)
       fix: load-balancing loss during training; capacity factor at inference
    - Token drop (expert at capacity; tokens skip MLP layer)
       fix: tune capacity factor; expert-choice routing instead of token-choice
    - All-to-all bottleneck (every token must route across the EP group)
       fix: keep EP within a high-bandwidth domain (single node or NVLink switch)
    - Cold cache on rare experts (first request after warmup is slow)
       fix: pin all experts in VRAM; don't offload to CPU at serving time`}</Ascii>

<h3 id="long-context-serving">Long-context serving (100k–1M tokens)</h3>

<ul>
  <li><strong>KV memory dominates everything:</strong> at 1M tokens, a single request can need 100+ GB of KV cache. Quantize KV to FP8 or INT4 to fit.</li>
  <li><strong>Ring attention:</strong> shard the sequence across GPUs; each GPU computes attention against a rotating slice of K/V from peers. Enables training and inference past single-GPU memory.</li>
  <li><strong>Attention sinks / StreamingLLM:</strong> keep the first few tokens plus a sliding window of recent tokens; drops middle KV. Works for chat but lossy for retrieval-style long context.</li>
  <li><strong>Sparse/hybrid attention:</strong> Mamba/RWKV-style state-space layers interleaved with attention reduce O(N²) cost for very long inputs.</li>
  <li><strong>Prefill chunking is mandatory:</strong> a 1M-token prefill held single-threaded would block every other user for tens of seconds. Chunk into 4–16k pieces interleaved with decode.</li>
</ul>

<h3 id="reasoning-models">Reasoning models and test-time compute</h3>

<p>"Reasoning" models (o1, o3, Claude with extended thinking, DeepSeek-R1) trade more inference compute for higher accuracy by generating long internal chains of thought before answering. This changes the cost model and the latency model.</p>

<Ascii>{`  Latency profile of a reasoning model:
    classical chat:  TTFT 300ms, 80 tok/s -> answer in 1-3s
    reasoning model: TTFT 300ms, 60 tok/s, BUT generates 2k-30k thinking tokens
                     -> visible answer in 10s - 5min

  Design implications:
    - UX needs progress hints ("thinking..." or stream the trace)
    - Token budget per request must be explicit (compute caps)
    - Async pattern: enqueue task, poll/webhook on completion
    - Caching: thinking traces are expensive; cache by problem signature
    - Routing: only route to reasoning model when difficulty justifies cost
       (a small classifier on the prompt is a 10x cost lever)`}</Ascii>

<h3 id="structured-output">Structured output and constrained decoding</h3>

<ul>
  <li><strong>Grammar-constrained decoding</strong> (outlines, LMQL, vLLM guided decoding): force outputs to match a regex / JSON schema / context-free grammar by masking invalid tokens at sampling time. Reliability bump, ~5–15% latency cost.</li>
  <li><strong>Function-calling / tool-use</strong> APIs use a similar mechanism under the hood; prefer the provider's native mode over freeform JSON-in-text parsing.</li>
  <li><strong>Speculative + structured:</strong> some stacks combine speculative decoding with grammar constraints by re-validating drafted tokens against the grammar.</li>
</ul>

<h3 id="eval-rigor">Evaluation rigor at the lead level</h3>

<table>
  <tr><th scope="col">Pitfall</th><th scope="col">What it looks like</th><th scope="col">Mitigation</th></tr>
  <tr><td>Underpowered comparison</td><td>"New model wins by 2%" on 100 examples</td><td>Pre-register sample size; paired bootstrap CIs; require Δ &gt; 2× CI width</td></tr>
  <tr><td>Eval-set contamination</td><td>Training corpus contains the benchmark</td><td>n-gram decontamination at build time; held-out private evals</td></tr>
  <tr><td>Judge bias</td><td>LLM judge prefers verbose answers / its own family</td><td>Rotate judges; calibrate against human labels; rubric-based not pairwise</td></tr>
  <tr><td>Goodharting one metric</td><td>BLEU goes up, users hate it</td><td>Multi-metric dashboard with product KPI gating release</td></tr>
  <tr><td>Aggregate hides regressions</td><td>+1% average, -15% on safety slice</td><td>Per-slice eval as a release gate, not just headline</td></tr>
  <tr><td>Win-rate without Elo</td><td>Pairwise A&gt;B reported without transitivity check</td><td>Bradley-Terry or Elo on a tournament of versions</td></tr>
</table>

<Callout variant="tip" title="Lead signal on evals">
  When asked "how do you know the new model is better?", the senior answer is "pre-registered eval set, slice-level metrics with paired bootstrap CIs, human-judged head-to-head on a fixed rubric, plus a live A/B with a product KPI as the primary outcome." Saying just "MMLU went up" is a junior tell.
</Callout>

<h2 id="part-14">Part 14 — Leadership scenarios for Lead/Staff/Principal rounds <Tag kind="core">★ CORE</Tag></h2>

<p>Lead-level interviews spend 30–50% of the loop on judgment, organization, and prioritization questions. The answers below are not scripts — they're shapes for how to reason out loud.</p>

<h3 id="ai-org-design">How to structure an AI org</h3>

<Ascii>{`  Common four-team split at a 50-200 person AI org:

    APPLIED AI / PRODUCT TEAMS
      own feature surfaces, prompts, evals, integration
      report into product or engineering org
      success metric: product KPIs

    AI PLATFORM
      owns gateway, model registry, eval harness, training infra
      one team enables all applied teams
      success metric: applied teams shipping faster, lower $/token

    RESEARCH / MODEL TEAM
      owns base model training, fine-tuning recipes
      tight loop with platform on infra
      success metric: capability + safety eval lifts

    SAFETY / RESPONSIBLE AI
      owns policy, red team, deployment gates
      independent reporting line (often to legal or CTO)
      success metric: incident rate, gate-pass rate

  Anti-patterns:
    - "Every team trains its own model"  -> wasted GPUs, fragmented evals
    - "Safety is everyone's job"          -> in practice nobody owns it
    - "Research ships features"           -> research timelines kill products`}</Ascii>

<h3 id="build-vs-buy">Build vs buy framework</h3>

<table>
  <tr><th scope="col">Question</th><th scope="col">Lean BUY (hosted API)</th><th scope="col">Lean BUILD (self-host / train)</th></tr>
  <tr><td>Volume</td><td>&lt; 5B tokens/day</td><td>&gt; 10B tokens/day sustained</td></tr>
  <tr><td>Latency SLO</td><td>≥ 1s acceptable</td><td>Sub-300ms TTFT required</td></tr>
  <tr><td>Data sensitivity</td><td>OK to leave premises (with BAA/DPA)</td><td>Regulated / customer-isolated</td></tr>
  <tr><td>Differentiation</td><td>Capability is table stakes</td><td>Capability is the moat</td></tr>
  <tr><td>Team strength</td><td>No GPU SRE on staff</td><td>You have ML infra engineers</td></tr>
  <tr><td>Time-to-market</td><td>Weeks matter</td><td>Quarters are OK</td></tr>
</table>

<Callout variant="tip" title="Hybrid is usually the right answer">
  Most mature orgs end up with: hosted APIs for prototyping and burst traffic, self-hosted open-weight for high-volume / regulated paths, and one or two fine-tuned models for the narrow domains where it matters. Saying "we'll be hybrid and here's the routing logic" is a stronger answer than picking one side.
</Callout>

<h3 id="roadmap-under-uncertainty">Roadmapping when the next frontier model ships in 3 months</h3>

<ul>
  <li><strong>Layer your bets:</strong> ship today on current best model; have a "snap-in" plan for the next one; keep an exploratory bet on something disruptive (open-weight, on-device).</li>
  <li><strong>Build moats that compound:</strong> evals, data, distribution, trust. These survive a model swap.</li>
  <li><strong>Avoid model-specific moats:</strong> heavy prompt engineering against one model's quirks becomes a liability when it's deprecated.</li>
  <li><strong>Be honest about wait-vs-build:</strong> if next quarter's frontier model trivially solves your problem, your roadmap item should be "be ready to integrate it" not "spend 2 quarters fine-tuning around current limits."</li>
  <li><strong>Capability ladders:</strong> design product surfaces that get better automatically as models improve (e.g., longer context = better summaries) without code changes.</li>
</ul>

<h3 id="safety-governance">Safety governance for product launches</h3>

<Ascii>{`  Pre-launch gate checklist (use this almost verbatim in an interview):

    1. Threat model
        what can go wrong? misuse, hallucination, bias, privacy leak,
        action abuse, prompt injection, IP infringement
    2. Red team
        domain experts try to break the system; results documented
    3. Eval gauntlet
        capability + safety + regression sets, with release thresholds
    4. Reversibility
        which actions can we undo? which are permanent?
    5. Blast radius
        who is affected if the worst case happens?
    6. Monitoring plan
        what would tell us something is wrong in production?
    7. Rollback plan
        prompt / model / index / policy independently revertable
    8. Disclosure
        what does the user see? consent, limitations, escalation path
    9. Cross-functional sign-off
        legal, security, policy, customer support trained

  Decision: launch / canary / hold / iterate`}</Ascii>

<h3 id="incident-response">AI incident response</h3>

<ul>
  <li><strong>Detect:</strong> automatic safety/quality drift alerts; user reports; reviewer queue spikes.</li>
  <li><strong>Mitigate first, root-cause later:</strong> revert prompt/model/index, narrow scope, increase human review threshold. Buy time before debugging.</li>
  <li><strong>Triage roles:</strong> incident commander, comms lead, eng lead. Same as classical SRE but with an extra "model owner" role.</li>
  <li><strong>Post-mortem within 72h:</strong> what was the failure mode (data, model, prompt, retrieval, policy)? Add to eval set so it can't regress silently.</li>
  <li><strong>Learning loop:</strong> incident corpus becomes a permanent eval slice; lead engineers review monthly.</li>
</ul>

<h3 id="hiring-signal">What to look for when hiring</h3>

<table>
  <tr><th scope="col">Role</th><th scope="col">Strong signal</th><th scope="col">Weak signal</th></tr>
  <tr><td>ML Engineer (applied)</td><td>Has shipped a model end-to-end; pragmatic about evals; product instinct</td><td>Only Kaggle / papers; can't describe a real production trade-off</td></tr>
  <tr><td>Research Engineer</td><td>Reproduces papers, debugs training instability, reads CUDA kernels</td><td>Can describe but not implement; needs a roadmap to start</td></tr>
  <tr><td>AI Platform / Infra</td><td>Distributed systems background + LLM-specific knowledge (KV cache, vLLM)</td><td>Pure backend with no exposure to GPU economics</td></tr>
  <tr><td>AI Product Engineer</td><td>Writes prompts <em>and</em> evals; iterates on UX given probabilistic outputs</td><td>Treats LLM as a black box; no eval discipline</td></tr>
  <tr><td>Safety / Red Team</td><td>Adversarial mindset; familiar with policy frameworks; can write evals</td><td>Pure policy background with no engineering vocabulary</td></tr>
</table>

<h3 id="economics-of-an-ai-product">Economics conversations with non-technical leaders</h3>

<ul>
  <li><strong>Unit economics:</strong> $ per successful task, not $ per token. Maps cost to product value.</li>
  <li><strong>Gross margin shape:</strong> AI features often start at low/negative margin and improve via routing, caching, distillation. Communicate the trajectory.</li>
  <li><strong>Capacity commitments:</strong> reserved GPU contracts trade flexibility for unit cost. Worth it once usage is predictable within ~30%.</li>
  <li><strong>The "cheaper next quarter" problem:</strong> token prices drop ~3–5x/year. Build with this in mind — features uneconomic today may be obvious next year.</li>
</ul>

<h2 id="part-15">Part 15 — Behavioral story bank (STAR scaffolds) <Tag kind="neutral">EXAMPLE</Tag></h2>

<p>Lead/Staff loops include 2–4 behavioral rounds. Prepare 6–8 stories that flex across multiple prompts. Each story should hit Situation → Task → Action → Result and end with one sentence on what you'd do differently.</p>

<h3 id="story-prompts">Story prompts to have a real answer for</h3>

<table>
  <tr><th scope="col">Prompt</th><th scope="col">What the interviewer is testing</th><th scope="col">Story shape</th></tr>
  <tr><td>"Tell me about an AI system you took from 0 to production"</td><td>End-to-end ownership; ability to ship</td><td>Problem → MVP → metrics → scale milestone</td></tr>
  <tr><td>"Tell me about a model rollback or production incident"</td><td>Judgment under pressure; blameless culture</td><td>Detection → mitigation → root cause → permanent fix</td></tr>
  <tr><td>"When did you say no to a feature request?"</td><td>Prioritization; strategic thinking</td><td>Request → analysis → reframe → outcome</td></tr>
  <tr><td>"Tell me about a time your eval missed a real problem"</td><td>Humility; eval rigor</td><td>Shipped → user feedback → gap in eval → new eval added</td></tr>
  <tr><td>"How did you handle a cost overrun on an AI feature?"</td><td>Business judgment; pragmatism</td><td>Spike → root cause → routing/caching/distillation → 60–80% reduction</td></tr>
  <tr><td>"Tell me about a hard cross-functional disagreement"</td><td>Influence without authority</td><td>Tension → listening → data → compromise / decision</td></tr>
  <tr><td>"When did you push back on a leader's direction?"</td><td>Courage + judgment</td><td>Concern → evidence → escalation → outcome</td></tr>
  <tr><td>"Describe mentoring an engineer through an AI project"</td><td>People growth; technical leadership</td><td>Skill gap → structured support → measurable growth</td></tr>
  <tr><td>"Tell me about a safety / responsible-AI tradeoff you made"</td><td>Values + execution</td><td>Risk identified → gate added → product impact accepted</td></tr>
  <tr><td>"What's the hardest technical bug you debugged?"</td><td>Depth; debugging methodology</td><td>Symptom → hypotheses → bisection → root cause → systemic fix</td></tr>
</table>

<h3 id="story-template">Reusable STAR scaffold</h3>

<Ascii>{`  SITUATION (1 sentence)
    Where, when, scale, stakes — anchor the listener.
    "At <company>, our <product> hit ~<scale> and we noticed <problem>."

  TASK (1 sentence)
    Your specific role — singular "I", not "we".
    "As <role>, I owned <scope> and was asked to <objective>."

  ACTION (2-4 sentences)
    What YOU did, decisions and trade-offs, not a tutorial.
    Include one non-obvious choice and why.
    "I considered X and Y; I chose Z because <reason>.
     I led <team>, set up <process>, shipped <thing>."

  RESULT (1-2 sentences)
    Numbers when possible. Connect to business or user outcome.
    "<metric> moved by <amount>, <user/$ outcome>."

  REFLECTION (1 sentence)
    What you'd do differently. Shows growth, not weakness.
    "Looking back, I'd <change>; the lesson was <generalization>."`}</Ascii>

<h3 id="ai-specific-story-anchors">AI-specific anchors that make stories land</h3>

<ul>
  <li><strong>Mention an eval you built or insisted on</strong> — this single signal distinguishes ML-mature engineers from prompt-tinkerers.</li>
  <li><strong>Mention a rollback or kill switch you designed in advance</strong> — shows you treat AI as probabilistic and plan for failure.</li>
  <li><strong>Mention a cost lever you pulled</strong> (routing, caching, distillation, smaller model) with a concrete % reduction.</li>
  <li><strong>Mention a safety/policy decision</strong> where you blocked or scoped a launch, even when it slowed you down.</li>
  <li><strong>Mention an org change you drove</strong> (eval team, gateway, model-of-record process) — Lead is about leverage, not just hands-on work.</li>
</ul>

<Callout variant="warn" title="Behavioral red flags interviewers downgrade for">
  Constant "we" (no individual contribution), no numbers, no failure stories, blaming teammates or vendors, no reflection, claiming you single-handedly built things that obviously needed a team. Be specific, be honest about constraints, give credit, and own the call that didn't work.
</Callout>

<h2 id="part-16">Part 16 — Post-mortem case studies <Tag kind="neutral">EXAMPLE</Tag></h2>

<p>Lead-level pattern recognition comes from incidents. The five vignettes below are composites of real production failure modes. Each ends with the systemic fix that would have prevented it — that systemic fix is the senior signal.</p>

<h3 id="incident-1">Incident 1 — The silent retrieval regression</h3>

<p><strong>Symptom:</strong> Internal RAG assistant satisfaction drops from 78% to 64% over two weeks. No deploys. No model changes.</p>

<p><strong>Investigation:</strong> Ingestion pipeline had been silently failing on a connector update, so new docs (including a major policy revision) never reached the index. Retrieval still returned <em>something</em>, so eval headline numbers stayed flat; the regression hid in the "recent docs" slice.</p>

<p><strong>Root cause:</strong> No index-age dashboards. No per-source ingestion success rate alerts. Eval set had no freshness slice.</p>

<p><strong>Systemic fix:</strong></p>
<ul>
  <li>Alert on per-source last-successful-ingest age (red after 2× expected cadence).</li>
  <li>Freshness slice in the eval set (queries whose answers depend on docs &lt; 7 days old).</li>
  <li>Synthetic canary: inject a known doc nightly, query for it, alert if not retrieved.</li>
</ul>

<h3 id="incident-2">Incident 2 — The cost spike at 3am</h3>

<p><strong>Symptom:</strong> Daily LLM bill spikes 12× overnight. On-call paged.</p>

<p><strong>Investigation:</strong> A customer integration started sending PDFs with embedded HTML that produced 200k-token prompts. The agent looped up to 30 tool calls per request. Per-tenant TPM limit existed but was set generously and the global circuit breaker hadn't tripped.</p>

<p><strong>Root cause:</strong> No per-request token cap. No per-tenant cost alert. Agent loop bound was step count, not token total.</p>

<p><strong>Systemic fix:</strong></p>
<ul>
  <li>Hard max_tokens per request, enforced at gateway.</li>
  <li>Per-tenant dollar-per-hour alert with auto-throttle at 5× baseline.</li>
  <li>Agent budget cap measured in tokens AND steps AND wallclock.</li>
  <li>Input-token preview check before expensive route (refuse or downgrade if &gt; threshold).</li>
</ul>

<h3 id="incident-3">Incident 3 — The eval that lied</h3>

<p><strong>Symptom:</strong> New model wins offline evals by 8%, ships, A/B test shows users prefer the <em>old</em> model 60–40.</p>

<p><strong>Investigation:</strong> Offline judge was the new model's own family. It rewarded verbose, hedged answers. Real users wanted concise direct ones. The eval optimized for what the model liked, not what users wanted.</p>

<p><strong>Root cause:</strong> Single-judge eval, no human calibration, no product KPI in the release gate.</p>

<p><strong>Systemic fix:</strong></p>
<ul>
  <li>Rotate two different judge families; require both to agree on wins.</li>
  <li>Calibrate judge against 200 human-labeled examples; report judge accuracy.</li>
  <li>Release gate requires offline win AND online A/B on product KPI (not satisfaction proxy).</li>
  <li>Add length-bias eval: pairs of (concise, verbose) answers with same content; judge must not always prefer the longer one.</li>
</ul>

<h3 id="incident-4">Incident 4 — The agent that emailed a customer's lawyer</h3>

<p><strong>Symptom:</strong> Support copilot, used by trained agents, autonomously composed and sent a reply to opposing counsel on a legal matter. Reply contained internal-only context.</p>

<p><strong>Investigation:</strong> The "send reply" tool was approval-gated for first-time recipients but cached as "approved" once a recipient had been confirmed earlier in the day. A different ticket from the same email thread reused the cached approval and skipped the gate.</p>

<p><strong>Root cause:</strong> Approval cached at the wrong scope (recipient instead of ticket). Audit log existed but wasn't reviewed proactively.</p>

<p><strong>Systemic fix:</strong></p>
<ul>
  <li>Approvals scoped per-action, not per-recipient. No carry-over.</li>
  <li>Recipient-classification on every send (legal, executive, regulator → always human-approval).</li>
  <li>Daily sample audit of agent-sent emails by a human reviewer.</li>
  <li>"Anti-exfiltration" check: outbound content scanned against internal-only context that was injected by retrieval.</li>
</ul>

<h3 id="incident-5">Incident 5 — The training run that quietly diverged</h3>

<p><strong>Symptom:</strong> Two-week 1,024-GPU pretraining run completed; downstream eval crashed by 30% vs the prior run.</p>

<p><strong>Investigation:</strong> A single data shard had a tokenization bug (BOM character corrupted ~0.4% of sequences). Loss curves looked fine — within noise. Per-shard loss telemetry didn't exist.</p>

<p><strong>Root cause:</strong> No data validation step between tokenization and training. No per-shard loss tracking. No "smoke" eval during training, only at end.</p>

<p><strong>Systemic fix:</strong></p>
<ul>
  <li>Per-shard checksum and sample-decode validation before training launch.</li>
  <li>Per-shard loss curves; alert on shards that drift &gt; 2σ from cohort.</li>
  <li>Mini-eval gauntlet every N steps; auto-pause if any capability eval drops &gt; 10%.</li>
  <li>Mandatory dry-run on 1% of compute before launching a multi-week run.</li>
</ul>

<Callout variant="tip" title="Pattern across all five">
  Every senior-level incident has the same shape: <strong>a guardrail existed but at the wrong scope, the monitoring metric existed but didn't include the failing slice, the eval covered the happy path but not the failure mode.</strong> When you describe AI systems in interviews, name the slices and scopes explicitly — that's what tells the interviewer you've actually run these systems in production.
</Callout>
